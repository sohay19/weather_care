## 0. 문서 목적과 범위

이 문서는 수치 임계값을 다시 정하지 않는다. 이미 채택한 공식 기준과 앱 내부 판단이 사용자에게 어떤 문장으로 보이는지를 항목별로 정한다.

- 수치 기준 문서: `어떤 자료와 조건으로 언제 판정하는가`
- 이 문서: `판정 결과를 어떤 근거·확실성·어조·길이로 말하는가`
- 제품 코드: 이 문서에서 표현이 채택되고 메시지 계약과 이행 우선순위가 정해진 뒤 별도 변경한다.

항목 하나를 검토할 때 `현재 구현`, `문제`, `권장안`, `허용 예시`, `금지 예시`, `자료가 없거나 충돌할 때의 문구`, `화면·알림별 길이`, `검증 시나리오`를 함께 정한다.

## 0-1. 현재 앱에서 사용할 수 있는 데이터 경계

현재 앱이 자동 판단에 사용할 수 있는 개인 정보는 사용자가 선택한 위치와 알림 시각·종류 설정뿐이다. 공식 기상·대기·재난·도로 자료처럼 위치와 시간으로 조회할 수 있는 공공 데이터와, 그 자료에서 계산한 값만 사용자 상태 판단에 사용한다.

다음 정보는 현재 앱에 입력·연동 기능이 없으므로 존재한다고 가정하지 않는다.

- 침실·실내 온습도와 침구·냉난방기·가습기·제습기의 실제 상태
- 일정·출발시각·이용경로·활동장소와 행동 완료 여부
- 창문·빨래·우산·마스크·차량·배관의 보유·사용·현재 상태
- 질환·민감군·복용약·의료진 계획·반려견의 품종·건강·행동 기록

이 정보가 필요한 문구·체감기준·개인화 분기는 현재 정책에서 사용하지 않는다. 생활행동은 `외출한다면`, `실외 빨래가 있다면`, `산책을 계획한다면`처럼 확인되지 않은 상태를 조건으로 밝힌 일반 제안만 허용한다. 현재 앱이 알 수 없는 상태를 사실처럼 말하거나 특정 개인에게 발생할 체감·증상·결과를 예측하지 않는다.

## 1. 진행 방식

이전 수치·기준 검토와 같은 방식으로 한 항목씩 진행한다.

1. 현재 코드·기준서·화면 문구의 상태를 확인한다.
2. 체감기준별 표현 3종이나 사용자 선호에 따라 결과가 달라지는 정책 판단은 `권장안 N-N`으로 제시한다.
3. 사용자가 선택·수정·확정하면 제목을 `채택 N-N`으로 바꾸고 다음 판단항목으로 진행한다.
4. 뒤 항목은 앞에서 채택한 표현 원칙을 상속한다. 상충하면 자동으로 덮지 않고 상충 지점을 먼저 알린다.
5. 수치 근거가 필요한 경우 관련 수치 기준 항목을 참조한다. 문구를 자연스럽게 만들기 위해 임계값이나 공식단계를 새로 만들지 않는다.

상태 표기는 다음과 같다.

| 상태 | 의미 |
| --- | --- |
| `채택` | 사용자가 확정했으며 뒤 항목이 상속하는 기준 |
| `권장안` | 현재 검토 중이며 아직 제품 기준으로 확정되지 않음 |
| `대기` | 순서가 오지 않아 상세 검토하지 않음 |
| `재검토 필요` | 앞 기준·공식 제품·구현이 바뀌어 다시 확인해야 함 |

## 2. 기존 대화에서 확정된 최상위 표현 원칙

다음 원칙은 개별 항목 검토보다 우선한다.

1. 공식 기관이 발표·발효·관측·예보·해제한 사실은 기관·대상·시각·공간범위가 확인된 경우 확정형으로 표현한다.
2. 앱 내부에서 계산한 체감, 피해 가능성, 활동 영향, 행동 선택, 개인 상태 판단은 모두 가능성이 드러나는 표현을 사용한다.
4. 공식 수치나 같은 단위의 단순 산술비교는 계산범위에서 사실로 말할 수 있다. 그 수치가 생활에 미치는 영향은 가능성형으로 분리한다.
5. 공식 행동요령은 기관이 안내한 내용임을 밝히고 확정형으로 전달할 수 있다. 앱이 고른 행동도 채택 기준·대상·시각이 분명하고 사용자가 바로 실행할 수 있는 저부담 예방행동이면 `챙기세요/들여놓으세요/피하세요`처럼 직접 제시할 수 있다. 행동으로 얻을 결과와 안전은 가능성형으로 남긴다.
6. 명칭은 `블랙아이스(도로살얼음)`를 사용한다. 친화적인 명칭을 괄호 앞에 두며 다른 맞춤법·띄어쓰기 변형을 만들지 않는다.
7. 결측·오래된 자료·공간 불일치·기관 간 충돌은 `안전/좋음/현상없음`이 아니라 확인 곤란과 자료상태로 말한다.
8. 예보와 앱 내부판단은 사용자가 선택한 위치를 대상으로 하는 것이 기본이므로 사용자 문장에 위치를 반복해서 쓰지 않는다. 공식 발표구역, 인접 격자, 다른 지역처럼 기본 위치와 공간범위가 다를 때만 구체적인 위치를 밝힌다.

## 3. 현재 문구 구현 상태

### 3.1 구현 자산

- 준비물 추천 카탈로그는 7개 유형을 여러 후보 문장으로 제공하며 `ko-KR-2026.08.2` 버전을 가진다.
- 생활 메시지 카탈로그는 36개 유형에 제목·설명·일부 contextKey와 placeholder를 제공한다.
- 메인 브리핑은 7개 장면, 20개 템플릿과 장면별 10개 표현 조각을 조합한다.
- 알림은 추천 제목·설명을 다시 조합하고 중요 알림에는 `이동할 때 주의하세요`를 일괄 추가한다.
- 같은 입력에 재현 가능한 후보 선택, context별 변형, placeholder 누락 시 fallback이 마련돼 있다는 점은 유지할 가치가 있다.

### 3.2 구조적 한계

- 대부분 `title + description` 또는 완성된 한 문장만 저장한다. 공식 사실, 앱 해석, 행동 제안, 근거·시각이 분리되지 않는다.
- 문장별로 `OFFICIAL_FACT`, `CALCULATED_FACT`, `INTERNAL_POSSIBILITY`, `OFFICIAL_GUIDANCE`, `APP_SUGGESTION`, `DATA_STATUS` 같은 역할 메타데이터가 없다.
- 같은 유형의 후보끼리 확실성 강도가 다르다. 예를 들어 `비를 만날 수 있어요`와 `오후 비가 예상돼요`, `마스크가 도움이 될 수 있어요`와 `마스크를 챙겨요`가 같은 후보군에서 교체된다.
- `오늘은 실내 건조가 안전해요`, `새벽 동파 위험이 있어요`, `산책은 ○○가 좋아요`, `이동하기 좋아요`처럼 현재 자료만으로 안전·위험·적합성을 확정하는 표현이 남아 있다.
- `하세요`, `해주세요`, `줄여요`, `미루세요` 같은 명령형과 `도움이 될 수 있어요` 같은 선택형이 섞여 있다. 공식 행동요령인지 앱 제안인지 화면에서 알 수 없다.
- 기관명, 발표/관측시각, 적용구역, 유효시간, 원자료 상태가 문구와 연결되지 않는다. 공식 사실을 표시할 구조도 없고 내부 문장이 공식 안내처럼 보일 수 있다.
- 후보 선택용 seed가 문체뿐 아니라 확실성·행동 강도까지 바꿀 수 있다. 알림 빌더가 설명 뒤에 명령형을 붙여 검수된 원문 의미도 달라질 수 있다.
- 수치 기준서의 각 채택 항목에는 좋은 문구 예시가 있으나 코드 카탈로그와 단일 계약으로 연결되지 않아 서로 다른 표현이 생긴다.

### 3.3 대표적인 현재 표현과 검토 방향

| 현재 표현 | 현재 문제 | 검토 방향 |
| --- | --- | --- |
| `오늘은 실내 건조가 안전해요` | 앱이 안전을 확정 | 실외 건조 영향 가능성과 실내 선택지를 분리 |
| `새벽 동파 위험이 있어요` | 공식 단계인지 내부 가능성인지 불명확 | 공식 저온예보와 노출배관 동결 가능성을 분리 |
| `산책은 18~19시가 좋아요` | 개체·경로·노면·보호자 조건 없이 적합성 확정 | 비교범위와 부족한 조건을 밝히고 상대적 선택 가능성으로 표현 |
| `비가 모두 그쳤어요` | 관측·예보·대상시간과 완전성이 없음 | 공식 관측/예보와 앱 episode 종료를 구분 |
| `민감하다면 마스크를 챙기세요` | 앱은 사용자가 민감군인지 알 수 없음 | 공식 민감군 행동요령을 일반 안내로 표시하고 개인 분류는 만들지 않음 |
| `폭설 주의 알림` | 공식 대설특보와 자체 준비물 알림이 혼동될 수 있음 | 공식 제품명은 원기관 상태에만 사용하고 내부 알림명은 별도화 |

## 4. 권장 검토 순서

먼저 모든 항목이 공유할 표현문법을 정한 뒤 기존 수치 기준서와 같은 순서로 현상·생활 항목을 검토한다.

### 4.1 공통 표현문법

1. `1-1` 한 항목 안의 정보 배치
2. `1-2` 근거 역할과 확실성 어미
3. `1-3` 공식 발표·발효·연장·변경·해제 문구
4. `1-4` 공식 관측·예보와 앱 산술비교 문구
5. `1-5` 내부 체감·피해 가능성·활동 영향 문구
6. `1-6` 공식 행동요령과 앱 행동제안 문구
7. `1-8` 결측·오래된 자료·충돌·미지원 문구
8. `1-9` 위치·시간·대상·출처 표시 순서
9. `1-10` 제목·요약·상세·근거 줄의 길이와 역할
10. `1-11` 푸시알림·잠금화면·접근성 읽기 문구
11. `1-12` 명칭·용어·존댓말·친근감·금지 표현
12. `1-13` 중복 병합·우선순위·메시지 계약·자동검증

### 4.2 기온·체감

`2-1 실제 기온`, `2-2 체감온도`, `2-3 덥고 춥고 끈적한 체감`, `2-4 폭염·고온`, `2-5 한파·저온` 순서로 검토한다.

### 4.3 강수·적설·노면

`3-1 강수확률`, `3-2 시간당 강수량`, `3-3 누적 강수량`, `3-4 호우·집중호우`, `3-5 소나기`, `3-6 강수 시작·종료`, `3-7 강설 가능성`, `3-8 시간당 적설`, `3-9 누적 적설`, `3-10 대설·폭설`, `3-11 도로 결빙`, `3-12 블랙아이스(도로살얼음)`, `3-13 서리·차량 성에`, `3-14 동파` 순서로 검토한다.

### 4.4 바람·습도

`4-1 풍속`, `4-2 강풍`, `4-3 돌풍`, `4-4 보행·자전거·운전 영향`, `4-5 우산 사용 영향`, `4-6 실외 습도`, `4-7 실외 고온다습 체감`, `4-8 건조특보와 실외 습도` 순서로 검토한다.

### 4.5 자외선·대기환경

`5-1 자외선지수`, `5-2 자외선 일반 안내`, `5-3 선크림`, `5-4 양산·모자`, `5-5 PM10`, `5-6 PM2.5`, `5-7 민감대상 공식 안내`, `5-8 마스크`, `5-9 오존`, `5-10 오존 야외활동 공식 안내`, `5-11 대기 정체`, `5-12 외기와 환기`, `5-13 꽃가루 공식정보` 순서로 검토한다.

### 4.6 생활행동

현재 앱 설정으로 켜고 끌 수 있는 우산·양산·겉옷·마스크·물·선크림 준비와, 공식 날씨를 이유로 하는 조건부 빨래·환기·창문·외출·활동·이동·밤 날씨 확인 문구를 검토한다.

### 4.7 출력·운영 표현

현상별 검토가 끝나면 단계명·색상·점수 노출, 준비물 중요도, 즉시/사전 알림, 브리핑, 여러 위험의 병합, 시간대·episode·해제, 지역·계절 문구를 전체 카탈로그에 일괄 대조한다.

## 5. 공통 표현 권장안

### 채택 1-1. 한 항목 안의 정보 배치

카드와 알림은 `직접행동 → 내부 영향 가능성 → 공식 사실·현재 상태 → 근거·자료상태` 순으로 표시한다. 직접행동을 만들 수 없으면 내부 영향 가능성을 먼저 표시하고, 둘 다 없으면 공식 사실을 첫 문장으로 사용할 수 있다.

### 채택 1-2. 근거 역할과 확실성 어미

- 공식 발표·예보: `기상청은 … 예보했어요`, `… 발표했어요`
- 공식 발효·관측·통제: `… 발효 중이에요`, `… 관측됐어요`, `… 통제하고 있어요`
- 앱 계산: `… 계산됐어요`, `… 분석됐어요`
- 앱의 체감·영향·피해: `~할 수 있어요`, `~할 가능성이 있어요`, `~할 위험이 있어요`
- 직접행동: 이유와 조건이 확인된 경우 `~하세요`

공식 사실은 기관이 확인한 범위에서 확정형으로 말한다. 앱 내부 판단은 공식 단계명을 만들거나 발생을 확정하지 않는다.

### 채택 1-3. 공식 발표·발효·변경·해제

발생가능성·예비특보·발효 전 발표는 사용자에게 알리지 않고 내부 재조회에만 사용한다. 실제 발효·변경 발효·해제, 실제 관측·통제·운휴가 확인됐을 때만 안내한다. 변화 없는 공식 `없음`은 표시하지 않는다.

### 채택 1-4. 관측·예보·앱 비교

같은 요소·위치대응·대상시간·단위일 때만 비교한다. 관측은 관측시각, 예보는 대상시각을 문장에 포함한다.

- `오후 2시 수원에서 기온 31.2℃가 관측됐어요. 오후 2시 예보기온 29℃보다 관측기온이 2.2℃ 높아요`
- `오후 2시 수원에서 기온 31.2℃가 관측됐어요. 오후 2시 예보내용과 유사하게 관측됐어요`
- `오후 2시에는 비가 내리고 있을 수 있다고 예상되나, 기상청은 오후 2시 강수없음으로 예보했어요. 앱의 현재 강수판단과 예보가 달라요`

### 채택 1-5. 체감·피해·활동 영향

진짜 느낌·의견은 `느껴질 수 있어요`, `느낌이 들 수 있어요`, `~함을 느낄 수도 있어요`, `~고 느낄 수도 있어요`를 문맥에 맞춰 사용한다. 쌓임·젖음·미끄러짐·파손처럼 실제 일어날 수 있는 사건은 `~할 수 있어요`로 표현한다. 체감기준 하나마다 승인문구 3종을 둔다.

### 채택 1-6. 앱 행동제안

행동 앞에 이유를 밝힌다. 앱이 알 수 없는 생활상태는 문장 안에 조건을 붙인다.

- `비가 올 수 있으니, 외출한다면 우산을 챙기세요`
- `눈이 내릴 수 있으니, 실외 빨래가 있다면 오후 5시 전에 실내로 들여놓으세요`
- `산책로가 얼 수 있으니, 반려견과 산책할 계획이라면 다른 시간대의 날씨를 비교하세요`
- `○○지하차도가 통제 중이니, 우회할 수 있다면 도로기관이 안내한 △△도로를 이용하세요`

일정·경로·건강·반려견·실내상태·준비완료를 앱이 알고 있다고 표현하지 않는다. 더 나은 시간이나 공식 우회로가 확인되지 않으면 구체적인 시각·도로를 제안하지 않는다.

현재 연결된 국가교통정보센터 돌발상황정보에는 별도의 공식 우회도로 필드가 없다. 따라서 실제 전면 통제는 `○○도로 전면 통제가 시행 중이니, 출발 전에 다른 경로와 대중교통 운행정보를 확인하세요`, 일부 차로 통제는 `○○도로 일부 차로가 통제 중이니, 출발 전에 교통정보를 확인하세요`로 안내한다. 통제 사실은 행동 다음에 `국가교통정보센터는 오후 2시부터 ○○도로 전면 통제가 시행 중이라고 안내했어요`처럼 표시한다.

### 채택 1-7. 자료상태

- 기관이 명시한 없음: 이전 자료에서 달라졌을 때만 `마지막으로 확인한 소나기 예보와는 달리 오후 3시 강수없음으로 예보됐어요`
- 앱 미수신: `자료를 받아오지 못해 오후 2~8시 예상 누적량을 계산하기 어려워요`
- 품질오류: `자료에 오류가 있어 오후 2~8시 예상 누적량을 계산하기 어려워요`
- 이전 자료: `마지막 관측은 오후 1시 50분 자료예요 · 현재 상태는 달라졌을 수 있어요`
- 출처 차이: `강수량, 초단기예보는 오후 4~5시 20~40mm, 단기예보는 같은 시간 30~50mm로 예상했어요`

미수신·오류·이전 자료를 `0`, `없음`, `안전`, `해제`로 바꾸지 않는다.

### 채택 1-8. 위치·시간·출처

선택한 위치가 문장의 기본 대상이므로 `현재 위치 주변에`를 반복하지 않는다. 공식 구역·관측지점·도로구간이 다르면 실제 이름과 범위를 표시한다. 시간은 `오늘`, `낮 동안`, `오늘 밤`, `내일 새벽`, `오전 6~9시`처럼 실제 범위를 사용하고 시각만으로 `출근길`, `퇴근길`, `취침 중`을 만들지 않는다.

### 채택 1-9. 알림·접근성·중복

공식 즉시행동을 가장 먼저 표시한다. 같은 위치·현상·대상시간·행동은 한 번만 알리고 의미 있는 공식 변경이나 행동 변경이 있을 때 갱신한다. 색·아이콘만으로 단계를 전달하지 않고 읽기문구에도 기관·행동·시간을 포함한다.

### 채택 1-10. 고정 명칭

- `블랙아이스(도로살얼음)`을 앱 항목명으로 사용한다.
- `새로 쌓인 눈`을 카드 제목으로 사용하되 본문에서는 `새로`를 반복하지 않는다.
- `신적설`, `AWS`, `TMP` 같은 내부·전문용어는 사용자 대표문장에 사용하지 않는다.

## 6. 기온·체감 문구

### 채택 2-1. 실제 기온 문구

#### 이번 항목에서 정하는 것

2-1은 기온값 자체를 어떤 사실문장으로 표시할지 정한다. 덥다·춥다·끈적하다 같은 체감판정과 폭염·한파 행동기준은 이 값과 분리하며 다음 항목에서 다룬다.

1. 관측기온과 예상기온·공식 예보문구를 어떤 명칭과 동사로 구분하는지
2. `현재 기온`이라는 말을 언제 사용할 수 있는지
3. 시간대 기온, 오늘 최저·최고기온, 제공구간의 최솟값·최댓값을 어떻게 구분하는지
4. 관측과 당시 예보, 이전 발표와 최신 발표, 어제 같은 시각을 어떻게 비교하는지
5. 결측·이전자료·품질오류·출처 차이가 있을 때 0℃로 대체하지 않고 어떻게 안내하는지
6. `℃`, 소수점, 영하값과 접근성 읽기문구를 어떻게 통일하는지
7. 실제 기온을 여덟 생활항목의 근거로 사용할 때 어떤 현상을 단독으로 추정하지 않는지

#### 기존 수치 기준에서 상속할 내용

수치 기준 문서의 [채택 2-1 실제 기온(TMP) 구간 표현](./수치_기준_근거자료_선정_항목.md#채택-2-1-실제-기온tmp-구간-표현)을 그대로 상속한다.

- 기상청 단기예보 `TMP`와 최저·최고기온은 숫자 사실로 표시한다.
- 실제 기온값 자체에는 고정된 `춥다/덥다` 감각구간을 붙이지 않는다.
- 한국인의 온열감은 실제 기온이 아니라 별도 체감지수와 연구기준으로 판단한다.
- 실제 발표된 폭염·한파특보와 기온 숫자를 분리한다. 한 시점 값만으로 특보 발표·발효를 만들지 않는다.
- 실제 기온, 기상청 체감온도, 한국형 체감지수를 하나의 `temperature` 값으로 섞지 않는다.

#### 현재 상태

현재 서버와 앱의 기온표시는 다음 문제가 있다.

- 서버가 사용하는 날씨 Provider는 기상청 단기예보이다. `current`는 관측자료가 아니라 현재시각 30분 전 이후 구간에서 가장 앞선 `TMP` 예보를 복사해 만든다.
- 이 예보 snapshot의 `forecastAt`을 `observedAt`에도 함께 저장한다. 후속 화면이 필드명만 보고 관측기온으로 오해할 수 있다.
- Flutter 홈은 이 값을 출처·발표시각·대상시각 없이 `현재 기온 28.0°C`처럼 표시한다.
- 시간별 화면은 같은 값을 정수 `28°C`, 홈은 소수 한 자리 `28.0°C`로 표시해 원자료가 같아도 정밀도가 달라 보인다.
- `current.minTemperature/maxTemperature`는 공식 `TMN/TMX`가 있으면 그 값을 사용하지만, 없으면 내려받은 시간대 `TMP`의 최솟값·최댓값을 대신 사용한다. 응답에는 공식 일 최저·최고인지 제공구간 계산값인지 구분하는 역할필드가 없다.
- Flutter의 `CurrentWeather.temperature`와 `HourlyWeatherItem.temperature`는 필수 숫자이며 JSON 값이 없으면 `0`으로 바뀐다. 자료 미수신이 실제 0℃처럼 표시될 수 있다.
- 주간화면은 최저·최고값을 `--`로 처리할 수 있지만 일별 값의 출처·발표시각과 공식/계산 역할은 표시하지 않는다.
- `어제보다 높아요/낮아요` 비교는 현재값과 과거값의 관측·예보 역할, 지점·격자, 대상시각이 같은지 확인하지 않는다.
- 기온을 `temperature`, 체감온도를 `apparentTemperature`로만 보존해 이미 채택한 `airTemperature/kmaApparentTemperature/koreanPerceivedTemperature` 역할분리가 구현되지 않았다.

#### 권장 원칙

**기온은 출처·자료역할·대상장소·대상시각이 붙은 숫자 사실로 말한다. 공식 관측은 `관측됐어요`, 공식 예보는 `예보했어요/예보됐어요`, 센서값은 `측정됐어요`, 앱이 같은 역할의 값을 비교한 결과는 비교범위 안에서만 확정형으로 표현한다. 실제 기온 숫자만으로 덥다·춥다·안전하다·위험하다·특보가 발표됐다고 말하지 않는다.**

카드·푸시에서 다른 채택기준으로 만든 직접행동이나 영향 가능성이 있으면 그것을 먼저 표시하고, 기온 사실은 상세 상단과 근거에 둔다. 기온만 확인되고 행동·영향을 근거 있게 만들 수 없으면 기온 사실 자체를 첫 노출 fallback으로 사용할 수 있다.

#### 화면 명칭과 자료역할

화면의 중립 항목명은 `기온`으로 사용한다. `실제 기온`은 체감온도와 구분하는 설명용 명칭으로 사용할 수 있지만, 예보값을 실제로 관측된 값처럼 보이게 하는 제목으로 사용하지 않는다.

| temperatureRole | 사용자용 명칭 | 필수 시공간·출처 | 고정 동사 |
| --- | --- | --- | --- |
| `OFFICIAL_OBSERVATION` | `관측기온` | 관측시각·관측지점·관측기관 | `관측됐어요` |
| `OFFICIAL_FORECAST` | 요약은 `예상기온`, 사실문장은 `기온 …로 예보` | 발표시각·대상시각·예보구역·기관/제품 | `예보했어요`, `예보됐어요` |
| `OFFICIAL_DAILY_MIN_FORECAST` | `오늘 최저기온 예보` | 발표시각·대상날짜·예보구역·공식 TMN | `예보했어요` |
| `OFFICIAL_DAILY_MAX_FORECAST` | `오늘 최고기온 예보` | 발표시각·대상날짜·예보구역·공식 TMX | `예보했어요` |

| `OFFICIAL_OBSERVED_EXTREME` | `관측된 최저/최고기온` | 관측지점·집계기간·완료 여부 | `관측됐어요` |


#### 관측기온 문구

공식 관측은 실제 관측지점과 시각을 함께 말한다.

- `오후 2시 수원에서 기온 31.2℃가 관측됐어요`
- `오늘 오전 6시까지 수원에서 관측된 가장 낮은 기온은 22.1℃예요`
- `어제 수원의 최저기온은 21.8℃, 최고기온은 32.4℃로 관측됐어요`

관측지점 값을 사용자 GPS 위치 전체의 직접관측으로 확대하지 않는다.

- 사용하지 않음: `현재 위치는 31.2℃예요`
- 권장: `오후 2시 수원에서 기온 31.2℃가 관측됐어요`
- 공간설명: `수원에서 관측한 값이며 현재 위치의 기온과 차이가 날 수 있어요`

마지막 문장은 관측지점과 사용자 위치가 다를 때의 앱 내부 공간영향 설명이므로 가능성형으로 유지한다.

#### 예상기온·공식 예보 문구

공식 예보는 대상시각과 발표주체를 분명히 한다.

- `기상청은 수원의 오후 3시 기온은 32℃라고 예보했어요`
- `오전 11시 발표에는 수원의 오후 3시 기온이 32℃로 예보됐어요`
- `기상청은 오늘 수원의 최저기온을 22℃, 최고기온을 33℃로 예보했어요`
- `오후 1시 30℃에서 오후 4시 33℃까지 오를 것으로 예보됐어요`
- `오후 4시부터 기온이 내려가 오후 9시에는 25℃로 예보됐어요`

`현재시간과 가장 가까운 예보`도 관측값이 아니다. 현재 코드처럼 첫 예보 슬롯을 대표값으로 사용하면 다음처럼 표시한다.

- 사용하지 않음: `현재 기온 32℃`
- 권장: `오후 3시 예상기온 32℃`
- 출처를 포함한 문장: `기상청은 수원의 오후 3시 기온은 32℃라고 예보했어요`

#### `현재 기온` 사용조건

`현재 기온`은 다음 조건을 모두 충족할 때만 요약 label로 사용할 수 있다.

2. 원 관측·측정시각이 freshness 정책 안에 있고 절대시각을 표시할 수 있다.
3. 관측지점·실내공간 등 값의 공간범위를 함께 확인할 수 있다.
4. 예보값·과거값·일 최저/최고값·결측대체값이 아니다.

요약 label을 쓰더라도 상세 사실은 `오후 2시 수원에서 기온 31.2℃가 관측됐어요`처럼 원역할을 표시한다. 장비지점 기준 괄호문구는 붙이지 않고 관측망·지점번호·현재 위치와의 거리는 상세근거에 표시한다. 자료가 오래됐으면 `현재`를 제거한다.

- `마지막 기온 관측은 오후 1시 50분 자료예요 · 현재 상태는 달라졌을 수 있어요`
- `오후 2시 관측기온 자료를 받아오지 못했어요`

#### 최저·최고기온 문구

공식 일 최저·최고예보와 앱이 제공된 시간대 값을 계산한 결과를 구분한다.

| 값의 근거 | 권장 문구 | 사용하지 않는 문구 |
| --- | --- | --- |
| 공식 `TMN/TMX` | `기상청은 오늘 수원의 최저기온을 22℃, 최고기온을 33℃로 예보했어요` | 출처 없는 `오늘 22/33℃` |
| 일부 시간대 TMP 최솟값 | `오전 6시~오후 11시 예상기온 가운데 가장 낮은 값은 22℃예요` | `오늘 최저기온 22℃` |
| 일부 시간대 TMP 최댓값 | `오전 6시~오후 11시 예상기온 가운데 가장 높은 값은 33℃예요` | `오늘 최고기온 33℃` |
| 하루가 끝나기 전 관측최솟값 | `오늘 오후 4시까지 관측된 가장 낮은 기온은 22.1℃예요` | `오늘 최저기온은 22.1℃였어요` |
| 공식 일 관측통계 | `어제 수원의 최고기온은 32.4℃로 관측됐어요` | `어제는 32.4℃였어요` |

제공구간이 하루 전체가 아니면 `오늘 최저/최고기온`이라고 확대하지 않는다. 공식 TMN/TMX가 없을 때 시간대 TMP로 만든 fallback에는 `extremeRole=DERIVED_SLOT_MIN/MAX`와 계산범위를 반드시 남긴다.

#### 관측과 당시 예보가 다를 때

관측값과 예보값은 역할이 다르므로 둘 중 하나를 오류로 단정하지 않고 같은 장소·대상시각의 값을 병렬로 표시한다.

`오후 2시 수원에서 기온 31.2℃가 관측됐어요. 예보기온 29℃보다 관측기온이 2.2℃ 높아요`

비교조건은 다음과 같다.

- 관측지점과 예보격자의 대응관계가 확인돼야 한다.
- 관측시각과 예보 대상시각이 같아야 한다.
- 최신예보가 아니라 그 시각 이전에 발표돼 당시 사용 가능했던 예보와 비교한다.
- 차이는 `관측값 - 당시 예보값`으로 계산하고 절댓값·방향을 보존한다.
- 화면 비교문장에는 첫 문장에서 관측 대상시각·장소·관측값을 밝히고, 둘째 문장에서 예보값과 관측값의 높고 낮은 방향을 밝힌다. 같은 대상시각을 둘째 문장에 반복하거나 예보 발표시각을 본문에 넣지 않는다. `관측과 당시 예보가 2.2℃ 달라요`처럼 대상시각과 방향이 없는 요약은 사용하지 않는다.
- 예보 발표시각과 예보 대상시각은 화면 문구에서 생략하더라도 비교근거 데이터에는 보존한다.
- `예보가 틀렸어요`, `실제보다 낮아요`처럼 공간·시각범위를 생략한 평가문구를 사용하지 않는다.

#### 예보 발표본이 바뀌었을 때

같은 예보제품·대상지역·대상시각끼리 비교한다.

- `오후 2시 발표 예보는 오전 11시 발표 예보보다 오후 5시 기온을 2℃ 높게 예보했어요`
- `오전 11시 발표에는 오후 5시 31℃, 오후 2시 발표에는 33℃로 예보됐어요`
- `오후 5시 예상기온이 31℃에서 33℃로 변경됐어요`

마지막 문장은 두 발표본의 동일 대상시각 값이 실제로 바뀐 계산사실이다. 이것을 `오후 5시에 더 더울 거예요`로 바꾸지 않는다. 온열감·영향문구는 별도 체감기준을 통과한 경우에만 가능성형으로 생성한다.

#### 어제·이전값과 비교할 때

비교문구는 같은 역할·지점/격자·기준시각·집계구간끼리만 만든다.

- 관측 비교: `오후 2시 수원 기온은 어제 같은 시각보다 2.1℃ 높게 관측됐어요`
- 예보 비교: `오늘 오후 3시 예상기온은 어제 오후 3시 예상기온보다 3℃ 높아요`
- 일 최고예보 비교: `오늘 최고기온 예보는 어제 최고기온 예보보다 2℃ 높아요`
- 표시 정밀도 안에서 같은 값: `표시 정밀도에서는 어제 같은 시각과 같아요`

관측값과 예보값, 현재시각 예보와 어제 일평균, 서로 다른 지점·격자를 `어제보다` 한 문장으로 비교하지 않는다. 현재 저장된 daily snapshot의 역할이 불명확하면 비교문구를 만들지 않고 역할자료를 먼저 보완한다.

#### 숫자·단위·읽기문구

| 값 | 화면 | 접근성 읽기 | 원칙 |
| --- | --- | --- | --- |
| 양의 정수 | `32℃` | `섭씨 32도` | `32°C`, `32°`, `32 도`와 혼용하지 않음 |
| 영하 정수 | `-2℃` | `영하 2도` | 음수부호를 빠뜨리지 않음 |
| 0 | `0℃` | `0도` | 결측과 구분되는 정상값 |
| 소수 한 자리 | `31.2℃` | `섭씨 31.2도` | 원자료·승인된 반올림에서 소수정밀도를 보존 |
| 범위 | `22~33℃` | `22도에서 33도` | 최저·최고 역할 label을 함께 표시 |
| 변화량 | `2.1℃ 높음` | `2.1도 높음` | 온도차에는 `섭씨`를 반복하지 않아도 됨 |

원자료가 정수인데 `32.0℃`로 정밀도를 늘리지 않고, 원자료가 소수 한 자리인데 화면마다 임의로 정수와 소수로 바꾸지 않는다. 공식값과 계산값에는 각각 적용한 반올림규칙과 원값을 보존한다.

`최저 22℃ · 최고 33℃`는 시각적으로 분리된 요약 label에서 사용할 수 있다. 음성에서는 `오늘 최저기온 22도, 최고기온 33도`처럼 역할을 모두 읽는다. 숫자만 `22/33`으로 표시하거나 읽지 않는다.

#### 자료가 없거나 오래됐을 때

| 자료상태 | 권장 문구 |
| --- | --- |
| 앱 미수신 | `오후 4시 예상기온 자료를 받아오지 못했어요` |
| 관측 미수신 | `오후 2시 관측기온 자료를 받아오지 못했어요` |
| 품질오류 | `오후 2시 기온은 자료에 오류가 있어 확인이 어려워요` |
| 이전 관측 | `마지막 기온 관측은 오후 1시 50분 자료예요 · 현재 상태는 달라졌을 수 있어요` |
| 이전 예보 | `마지막으로 받은 예상기온은 오전 11시 발표자료예요 · 최신 예보는 달라졌을 수 있어요` |
| 일부 시간대 | `오후 6~8시 예상기온 자료가 없어 이 시간대의 가장 높은 기온을 계산하기 어려워요` |
| 출처 차이 | `오후 2시 수원에서 기온 31.2℃가 관측됐어요. 예보기온 29℃보다 관측기온이 2.2℃ 높아요` |

기온 자료가 없을 때 `0℃`, `--℃`, `현재 기온 없음`, `기온 정상`으로 바꾸지 않는다. 화면 공간이 부족하면 값 대신 `자료 확인 중/일부 자료/이전 자료` label을 표시하고 상세에 원시각과 원인을 둔다.

#### 여덟 생활항목과 연결할 때

실제 기온은 다음 항목의 보조근거가 될 수 있지만 단독 결론으로 확대하지 않는다.

| 항목 | 실제 기온으로 할 수 있는 것 | 실제 기온만으로 만들지 않는 문구 |
| --- | --- | --- |
| 강풍 | 같은 시간대 기온 사실을 상세근거로 함께 표시 | `기온이 낮아 강풍이 위험해요` |
| 블랙아이스(도로살얼음) | 노면자료가 없을 때 최근 수분과 함께 낮은 신뢰도의 보조환경으로만 사용 | `기온이 영하라 블랙아이스(도로살얼음)가 생겼어요` |
| 자외선 | 기온과 자외선지수를 별도 사실로 표시 | `기온이 높아 자외선이 강해요` |
| 비와 우산 준비 | 예상기온과 강수예보를 같은 시간축에 표시 | `기온이 내려가 비가 와요` |
| 빨래 회수 | 건조·회수 판정의 여러 입력 중 하나로 사용 | `기온이 높아 빨래가 잘 말라요` |

실제 기온과 다른 입력을 결합해 내부 영향을 만들 때도 결과는 `~수 있어요`, `~할 위험이 있어요`로 표시한다. 실제 관측문장과 공식 예보문장은 확정형으로 유지하고 한 문장 안에서 내부 결과를 확정하지 않는다.

#### 첫 노출과 상세 예시

**다른 기준에서 직접행동이 생성된 경우**

- 첫 노출: `산책을 계획한다면 오후 8시 이후를 선택하세요`
- 상세 상단 기온사실: `기상청은 수원에 오후 4시 기온 32℃를 예보했어요`
- 근거: `기상청 단기예보 · 오전 11시 발표 · 오후 4시 수원 격자`

**기온 사실만 확인된 경우**

- 카드: `오후 3시 예상기온 32℃`
- 상세 상단: `기상청은 수원의 오후 3시 기온은 32℃라고 예보했어요`
- 영향·행동: 기준을 통과한 다른 근거가 없으면 생성하지 않음

**관측자료가 오래된 경우**

- 첫 노출: `외출 전에 최신 기온을 다시 확인하세요`
- 자료상태: `마지막 기온 관측은 오후 1시 50분 자료예요 · 현재 상태는 달라졌을 수 있어요`
- 상세: 마지막 관측지점·원시각과 다음 확인상태 표시

#### 금지 표현과 권장 대체

| 사용하지 않는 표현 | 문제 | 권장 대체 |
| --- | --- | --- |
| 예보값을 `현재 기온`으로 표시 | 예보를 관측처럼 보이게 함 | `오후 3시 예상기온 32℃` |
| `실제 32℃` | 무엇과 비교한 실제인지 불명확 | `오후 2시 수원에서 기온 31.2℃가 관측됐어요` 또는 `오후 3시 예상기온 32℃` |
| `오늘은 33℃예요` | 현재·최고·어느 시간대인지 없음 | `오후 3시 기온이 33℃로 예보됐어요` |
| `32℃라 더워요` | 실제 기온에서 개인체감 확정 | 별도 체감지수 근거 + `덥게 느껴질 수 있어요` |
| `영하라 도로가 얼었어요` | 실제 기온을 노면온도·결빙관측으로 대체 | 노면·수분 근거 + 가능성문장 또는 `노면자료 없음` |
| `기온이 높아 폭염주의보예요` | 한 값으로 공식 특보 생성 | 실제 특보 발표·발효를 별도 사실로 표시 |
| `어제보다 높아요` | 비교 역할·장소·시각 없음 | `오후 2시 수원 기온은 어제 같은 시각보다 2.1℃ 높게 관측됐어요` |
| 결측을 `0℃`로 표시 | 정상 영점과 결측 혼동 | `오후 4시 예상기온 자료를 받아오지 못했어요` |
| 일부 슬롯의 min/max를 `오늘 최저/최고`로 표시 | 계산범위를 하루 전체로 확대 | `오전 6시~오후 11시 예상기온 가운데 가장 낮은/높은 값` |
| `관측과 예보 중 더 정확한 값` 자동선택 | 역할·공간·목적이 다른 자료를 서열화 | 두 값을 출처·시각과 병렬표시 |

#### 실제 기온 데이터계약

- 식별: `temperatureId`, `temperatureRole`, `sourceProduct`, `providerRef`, `providerField`
- 값: `value`, `unit=C`, `sourcePrecision`, `displayPrecision`, `roundingRule`
- 관측: `observedAt`, `stationRef`, `stationLabel`, `observationAreaRole`
- 예보: `issuedAt`, `targetTime`, `validFrom`, `validTo`, `gridRef`, `forecastAreaLabel`
- 일 극값: `extremeRole`, `targetDate`, `aggregationStart`, `aggregationEnd`, `aggregationComplete`
- 비교: `comparisonRole`, `leftTemperatureId`, `rightTemperatureId`, `difference`, `sameRole`, `sameTimeBasis`, `sameSpatialBasis`
- 상태: `availability`, `freshness`, `qualityState`, `qualityFlags`, `fetchedAt`
- 문구: `factTextKey`, `factArgs`, `spokenText`, `evidenceRefs`
- 버전: `schemaVersion`, `temperaturePolicyVersion`, `catalogVersion`

`observedAt`과 `forecastAt/targetTime`을 같은 값으로 중복 채우지 않는다. 예보 snapshot은 `targetTime`, 관측 snapshot은 `observedAt`을 사용한다. UI가 두 역할을 하나의 `CurrentWeather.temperature`로 받지 않도록 역할과 기준시각을 필수로 전달한다.

#### 현행 구현에 필요한 후속 변경

1. 서버의 예보 `current` 명칭을 `currentForecast` 또는 명확한 `OFFICIAL_FORECAST` 역할로 바꾸고 `observedAt=forecastAt` 복사를 제거해야 한다.
2. 실제 현재 관측기온을 제공하려면 별도 공식 관측 Provider·관측지점 매핑·freshness 정책을 추가해야 한다.
3. `temperature`를 optional로 유지하고 Flutter에서도 `double?`로 받아 결측을 0℃로 바꾸지 않아야 한다.
4. 공식 TMN/TMX와 시간대 TMP 계산 min/max에 서로 다른 `extremeRole`과 계산범위를 추가해야 한다.
5. 홈·시간별·주간 화면의 `°C`, 정수·소수 표기를 공통 `℃` formatter와 source precision 정책으로 통일해야 한다.
6. 비교기능은 같은 관측/예보 역할·지점/격자·대상시각이 확인된 경우에만 차이문구를 생성해야 한다.
7. `airTemperature`, `kmaApparentTemperature`, `koreanPerceivedTemperature`를 분리하고 실제 기온값에 체감 label을 직접 붙이지 않아야 한다.

이번 단계에서는 제품 코드를 변경하지 않는다.

#### 검증 시나리오

1. 단기예보 첫 TMP가 `현재 기온`이나 `관측됐어요`로 표시되지 않는지 확인한다.
2. 공식 관측기온은 관측시각·관측지점과 `관측됐어요`를 포함하는지 확인한다.
3. 요약 예상기온은 대상시각을 포함하고, 상세 공식 예보문장은 발표시각·대상시각·예보구역과 `예보했어요/예보됐어요`를 포함하는지 확인한다.
4. 0℃가 정상값으로 표시되고 결측 null이 0℃로 변환되지 않는지 확인한다.
5. 원자료 정밀도와 승인된 반올림규칙에 따라 `32℃/31.2℃`가 화면 전체에서 일관되는지 확인한다.
6. `°C/°/℃`가 혼용되지 않고 접근성에서 `섭씨/영하`로 자연스럽게 읽히는지 확인한다.
7. 공식 TMN/TMX와 제공된 시간대 TMP의 min/max가 서로 다른 extremeRole로 표시되는지 확인한다.
8. 하루 일부만 있을 때 `오늘 최저/최고기온`으로 확대하지 않는지 확인한다.
9. 진행 중인 하루의 관측최솟값·최댓값에 `오후 4시까지 관측된` 집계범위가 표시되는지 확인한다.
10. 관측과 당시 예보 비교가 같은 장소·대상시각을 사용하고 두 역할·값을 병렬표시하는지 확인한다.
11. 예보변경 비교가 같은 제품·지역·대상시각의 서로 다른 발표본끼리 이뤄지는지 확인한다.
12. 어제 비교가 관측/예보 역할·지점/격자·기준시각·집계구간이 같을 때만 생성되는지 확인한다.
13. 실제 기온값 자체에 `덥다/춥다/안전/위험/폭염주의보/한파주의보`를 붙이지 않는지 확인한다.
15. 자료 미수신·품질오류·이전자료·일부 시간대·출처 차이가 각각 다른 상태문구로 표시되는지 확인한다.
16. 카드·푸시에서 다른 기준의 직접행동/영향이 먼저 보이고 상세 상단에서 기온의 관측/예보 역할을 확인할 수 있는지 확인한다.
17. 행동·영향 근거가 없을 때 기온 공식사실만 표시하고 일반 행동문구를 채워 넣지 않는지 확인한다.
18. 서버와 Flutter가 temperatureRole·원시각·공간역할·source precision을 잃지 않는지 확인한다.

### 채택 2-2. 체감온도 숫자·계산출처 문구

#### 이번 항목에서 정하는 것

2-2는 체감온도 숫자가 어디에서 왔고 어떤 자료로 계산됐는지를 사용자에게 어떻게 설명할지 정한다.

1. 기상청이 직접 제공한 체감온도와 앱이 기상청 계산방식으로 계산한 값을 어떻게 구분하는지
2. 관측자료로 계산한 현재시각 체감온도와 예보자료로 계산한 예상 체감온도를 어떻게 표시하는지
3. 실제 기온·습도·바람 중 필요한 입력이 없거나 계산조건에 해당하지 않을 때 어떻게 안내하는지
4. 일부 시간대의 가장 높은/낮은 계산값을 `최고/최저 체감온도`로 확대하지 않는 방법
6. 카드·상세·푸시·접근성에서 계산값과 체감 가능성 문장을 어떤 순서로 보여주는지

`조금 덥게/덥게/많이 덥게/선선하게/쌀쌀하게/춥게/끈적하게 느껴질 수 있어요`처럼 사람이 느낄 수 있는 표현은 다음 2-3에서 별도로 정한다. 폭염·한파 피해와 행동문구는 2-4·2-5에서 다룬다.

#### 기존 수치 기준에서 상속할 내용

수치 기준 문서의 [채택 2-2 체감온도 산출식](./수치_기준_근거자료_선정_항목.md#채택-2-2-체감온도-산출식)을 상속한다.

- 기상청 체감온도는 공식 위험·행동 기준을 설명하는 숫자에 사용한다.
- 한국형 PT는 한국인이 어떻게 느낄 수 있는지 판단하는 별도 내부지수로 사용한다.
- 실제 기온은 `airTemperature`, 기상청 계산방식의 체감온도는 `kmaApparentTemperature`, 한국형 체감지수는 `koreanPerceivedTemperature`로 분리한다.
- 한국형 체감지수의 입력이 부족하면 기상청 체감온도에 한국형 경계를 대신 적용하지 않는다.
- 한 시점의 계산값만으로 폭염주의보·폭염경보·한파주의보·한파경보가 발표·발효됐다고 표현하지 않는다.

[체감온도 계산·표현 기준](./체감온도_표현_기준.md)에 기록된 `20/28℃` 프록시와 현재 Main label은 과거 임시 구현이다. 이후 채택된 수치 기준은 기상청 체감온도 숫자와 한국형 체감문구를 분리하므로 2-2는 이후 채택기준을 우선하고 현행 Main 표현을 후속 교체대상으로 다룬다.

#### 현재 상태

- 서버와 앱의 기상청 직접조회는 같은 계절별 계산방식을 구현하고 같은 입력에서 같은 값을 만들도록 회귀테스트를 두고 있다.
- 현재 값은 기상청이 체감온도 예보값을 직접 내려준 것이 아니라 단기예보의 기온·습도·바람을 앱이 기상청 계산방식에 넣어 만든 값이다.
- 서버와 Flutter는 이 값을 모두 `apparentTemperature`로 저장한다. 계산출처, 계절 계산모드, 관측/예보 입력역할, 입력누락 여부, 공식제공값 여부를 구분하지 못한다.
- 여름은 습도가 없으면 실제 기온을 체감온도로 반환하고, 겨울은 바람자료가 없거나 적용조건을 충족하지 않으면 실제 기온을 반환한다. 입력누락과 정상적인 계산조건 비해당이 같은 숫자로 보일 수 있다.
- 홈은 예보자료로 계산한 값을 시각·출처 없이 `체감 온도 32.7°C`로 표시한다.
- 상세는 같은 값을 `체감 33°C`, 준비물 근거는 다음 24시간 최댓값을 `최고 체감온도 35.2°C`로 표시한다. 현재값·시간대값·구간 최댓값이 같은 필드명으로 섞인다.
- 서버의 aggregate snapshot은 다음 24시간의 체감온도 최댓값을 `apparentTemperature`에 넣으면서 current snapshot의 다른 시각정보를 유지한다. 최댓값의 실제 발생시각이 사라질 수 있다.
- Main은 기상청 계산값 하나에 한국형 PT 임시경계와 `더위 주의/경계/위험한 더위`, 근거가 부족한 한랭 label을 함께 적용한다.
- `weatherBrief`는 체감온도 값이 없으면 실제 기온을 대신 사용한다. 문구에서는 대체 여부가 드러나지 않는다.
- 어제 비교도 두 값의 계산방식·공식제공/앱계산·관측/예보 입력·대상시각이 같은지 확인하지 않는다.

#### 권장 원칙

**체감온도 숫자는 `공식 제공값`인지 `앱이 기상청 계산방식으로 계산한 값`인지 먼저 구분한다. 앱 계산값은 사용한 기온·습도·바람의 관측/예보 역할과 대상시각을 함께 보존하고 `계산했어요/계산됐어요`라고 확정적으로 안내한다. 그 숫자를 사람이 실제로 느끼는 감각·피해·활동영향으로 바꿀 때는 별도 한국형 체감기준과 대상조건을 사용하고 가능성형으로 표현한다.**

#### 숫자 역할과 고정명칭

| apparentTemperatureRole | 화면 명칭 | 사용자문장 역할 |
| --- | --- | --- |
| `KMA_OFFICIAL_OBSERVATION_BASED` | `기상청 관측자료 기준 체감온도` | 기상청이 관측입력과 계산결과를 공식 제공한 범위에서 확정형 |
| `KMA_OFFICIAL_FORECAST` | `기상청 체감온도 예보` | 기상청 공식 제공자료가 실제 있을 때만 `예보했어요` |
| `APP_KMA_METHOD_FROM_OBSERVATION` | `관측자료로 계산한 체감온도` | `기상청 계산방식으로 … 계산했어요` |
| `APP_KMA_METHOD_FROM_FORECAST` | 요약은 `예상 체감온도` | `기상청 계산방식에 예상자료를 적용해 … 계산했어요` |
| `KOREAN_PERCEIVED_TEMPERATURE` | 기본 화면에 숫자 미노출 | 2-3의 `~하게 느껴질 수 있어요` 선택에만 사용 |

현재 앱의 계산값에는 `기상청은 … 체감온도를 예보했어요`를 사용하지 않는다. 기상청 단기예보 입력을 사용했어도 체감온도 숫자 자체는 앱이 계산했기 때문이다.

#### 예보자료로 계산한 예상 체감온도

카드의 기본 요약은 다음처럼 표시한다.

- `오후 3시 예상 체감온도 34.1℃`
- `오늘 오후 1~5시 예상 체감온도 33~35.2℃`

상세에서는 계산주체와 입력역할을 밝힌다.

- `기상청 계산방식에 수원의 오후 3시 예상 기온·습도·바람을 적용한 체감온도는 34.1℃예요`
- `오전 11시 발표 예보자료로 수원의 오후 3시 예상 체감온도를 34.1℃로 계산했어요`
- `오후 3시 예상기온은 32℃이고 예상 체감온도는 34.1℃예요`

세 번째 문장은 두 계산값을 병렬로 보여주는 계산사실이다. `실제보다 2.1℃ 더 더워요`처럼 사용자의 체감을 확정하지 않는다.

#### 관측자료로 계산한 체감온도

공식 관측입력을 앱이 계산한 경우 체감온도 자체가 관측됐다고 표현하지 않는다.

- `오후 2시 수원에서 관측된 기온·습도·바람을 기상청 계산방식에 적용한 체감온도는 33.4℃예요`
- 요약: `오후 2시 수원의 관측자료로 계산한 체감온도는 33.4℃예요`
- 근거: `수원 관측지점 · 오후 2시 기온·습도·바람 · 기상청 계산방식`

사용하지 않는 문구는 다음과 같다.

- `오후 2시 체감온도 33.4℃가 관측됐어요`
- `수원의 실제 체감온도는 33.4℃예요`
- `사람들이 33.4℃로 느꼈어요`

#### 기상청이 직접 제공한 값이 있을 때

기상청 공식 제품에서 체감온도를 직접 제공하고 원문 역할이 확인된 경우에만 공식 동사를 사용할 수 있다.

- 공식 예보: `기상청은 수원의 오후 3시 체감온도는 34℃라고 예보했어요`
- 공식 관측자료 기준값: `기상청이 제공한 오후 2시 수원의 관측자료 기준 체감온도는 33.4℃예요`

공식 제공값과 앱 계산값이 함께 있으면 공식값을 먼저 표시하고 앱 계산값은 검증·보조근거로 둔다. 두 값이 다르면 계산방식·입력시각·공간범위를 확인하고 임의로 평균내지 않는다.

#### `현재 체감온도` 사용조건

예보자료로 계산한 값을 `현재 체감온도`라고 표시하지 않는다.

- 사용하지 않음: `현재 체감온도 34.1℃`
- 권장 요약: `오후 3시 예상 체감온도 34.1℃`
- 권장 상세: `오전 11시 발표 예보자료로 수원의 오후 3시 예상 체감온도를 34.1℃로 계산했어요`

`현재 체감온도`는 기상청이 공식 제공한 현재 관측자료 기준 계산값 또는 freshness 정책을 통과한 관측 기온·습도·바람으로 앱이 계산한 값에서만 요약 label로 사용할 수 있다. 이 경우에도 상세에서 관측지점·원시각·공식제공/앱계산 역할을 확인할 수 있어야 한다.

계산결과가 실제 기온과 같더라도 이유를 구분한다.

| `SAME_AS_AIR_OUTSIDE_SCOPE` | `기상청 계산조건에 해당하지 않아 오후 3시 예상 체감온도는 예상기온과 같은 18℃예요` | 표시 가능 |

| `MISSING_HUMIDITY` | `오후 3시 습도 자료를 받아오지 못해 예상 체감온도를 계산하기 어려워요` | 미표시 |
| `MISSING_WIND` | `오후 3시 바람 자료를 받아오지 못해 예상 체감온도를 계산하기 어려워요` | 해당 계절·조건에서 바람이 필수면 미표시 |
| `INVALID_INPUT` | `오후 3시 체감온도 계산에 사용한 자료에 오류가 있어 확인이 어려워요` | 미표시 |
| `STALE_INPUT` | `체감온도 계산에 사용한 마지막 자료는 오후 1시 50분 자료예요 · 현재 상태는 달라졌을 수 있어요` | 현재값처럼 미표시 |

입력누락을 계산조건 비해당으로 바꿔 실제 기온을 그대로 반환하지 않는다. 여름 습도, 겨울의 필요한 바람자료가 없으면 해당 체감온도 계산을 보류하고 어떤 자료가 없는지 표시한다.

#### 일부 시간대의 최솟값·최댓값

제공된 시간범위와 해당 값의 시각을 함께 보존한다.

- `오후 1~5시 예상 체감온도 가운데 가장 높은 값은 오후 4시 35.2℃예요`
- `오늘 밤 11시~내일 오전 6시 예상 체감온도 가운데 가장 낮은 값은 내일 오전 5시 -4.1℃예요`

사용하지 않는 문구는 다음과 같다.

- `오늘 최고 체감온도 35.2℃` — 하루 전체·공식 일 최고인지 확인되지 않음
- `최저 체감 -4.1℃` — 날짜·시간범위·입력역할 없음
- `지금부터 24시간 최고 체감` — 시작·종료 절대시각과 발생시각 없음

공식 일 최고 체감온도 예보가 별도 제품으로 제공된 경우에만 `기상청은 오늘 수원의 최고 체감온도를 35℃로 예보했어요`처럼 공식 역할을 표시한다.

#### 실제 기온과 체감온도의 차이

같은 시간·장소·관측/예보 입력을 사용한 값끼리만 비교한다.

- `오후 3시 예상기온은 32℃이고 예상 체감온도는 34.1℃예요`
- `오후 3시 예상 체감온도는 예상기온보다 2.1℃ 높게 계산됐어요`
- `오후 2시 관측자료로 계산한 체감온도는 관측기온보다 1.4℃ 낮게 계산됐어요`

차이값은 계산범위 안에서 확정형으로 말할 수 있다. 사용자가 실제로 더 덥거나 춥게 느낄지는 다음 2-3 기준으로 `~하게 느껴질 수 있어요`라고 표현한다.

#### 관측입력 계산값과 당시 예상값이 다를 때

`오후 2시 수원의 관측자료로 계산한 체감온도는 33.4℃이고, 오전 11시 발표 예보자료로 계산했던 오후 2시 예상 체감온도는 32.1℃예요. 두 계산값이 1.3℃ 달라요`

- 같은 계산방식·version과 같은 장소·대상시각끼리 비교한다.
- 당시 예상값과 최신 발표의 미래값을 섞지 않는다.
- `예상보다 더 더웠어요`, `예보가 틀렸어요`처럼 체감·정확도를 단정하지 않는다.

#### 어제·이전값과 비교할 때

- `오늘 오후 3시 예상 체감온도는 어제 오후 3시 예상 체감온도보다 2.3℃ 높아요`
- `오후 2시 관측자료로 계산한 체감온도는 어제 같은 관측지점·시각보다 1.2℃ 낮게 계산됐어요`
- `오후 2시 발표 예보는 오전 11시 발표 예보보다 오후 5시 예상 체감온도를 1.5℃ 높게 계산했어요`

계산방식 version, 관측/예보 입력역할, 지점/격자, 대상시각이 같을 때만 비교한다. 계산방식이 바뀌었으면 이전값을 새 산식으로 재계산할 수 있는 경우에만 차이를 표시하고, 그렇지 않으면 `계산방식이 달라 직접 비교하기 어려워요`라고 안내한다.

#### 숫자·단위·읽기문구

| 값 | 화면 | 접근성 읽기 |
| --- | --- | --- |
| 예상 체감온도 | `오후 3시 예상 체감온도 34.1℃` | `오후 3시 예상 체감온도 섭씨 34.1도` |
| 영하 체감온도 | `오전 5시 예상 체감온도 -4.1℃` | `오전 5시 예상 체감온도 영하 4.1도` |
| 실제 기온과 함께 | `예상기온 32℃ · 예상 체감온도 34.1℃` | `예상기온 32도. 예상 체감온도 34.1도.` |
| 차이 | `예상기온보다 2.1℃ 높음` | `예상기온보다 2.1도 높음` |

화면 단위는 `℃`로 통일하고 `°C`, `°`, `체감 34`와 혼용하지 않는다. 계산결과는 소수점 첫째 자리까지 보존하되 원입력 정밀도·공식 반올림규칙보다 더 정밀한 숫자를 만들지 않는다.

체감온도는 사람의 체온이 아니다. 접근성 읽기와 상세설명에서 `체온 34.1도`, `몸 온도 34.1도`로 바꾸지 않는다.

#### 기상청 체감온도와 한국형 체감문구의 분리

| 값 | 사용자에게 보여주는 역할 | 2-2에서 만들지 않는 것 |
| --- | --- | --- |
| 기상청 계산방식의 앱 계산값 | 예상/관측입력 체감온도 숫자와 계산근거 | 공식 발표·관측으로 승격 |
| 한국형 체감지수 | 2-3의 감각 가능성 문장 선택 | 기상청 공식값·특보단계로 변환 |
| 실제 폭염·한파특보 | 발표·발효·변경·해제의 공식사실 | 한 시점 계산값으로 새 특보 생성 |

한국형 체감지수 입력이 없으면 `더움/추움` 문구만 보류하고 기상청 방식으로 정상 계산된 숫자는 표시할 수 있다.

- 숫자: `오후 3시 예상 체감온도 34.1℃`
- 감각상태: `한국형 체감 판단에 필요한 자료를 충분히 확보하지 못했어요`

숫자자료가 없는데 감각문구만 일반 fallback으로 만들거나, 기상청 체감온도 숫자에 한국형 구간을 대신 적용하지 않는다.

#### 여덟 생활항목과 연결할 때

| 항목 | 사용할 수 있는 범위 | 체감온도 숫자만으로 만들지 않는 문구 |
| --- | --- | --- |
| 강풍 | 사람의 한랭 체감 보조근거로 사용하고 풍속 사실은 별도 표시 | `체감온도가 낮아 강풍이 발생했어요` |
| 블랙아이스(도로살얼음) | 사람의 체감정보로만 유지 | `체감온도가 영하라 블랙아이스(도로살얼음)가 생겼어요` |
| 자외선 | 자외선지수와 별도 시간축에 표시 | `체감온도가 높아 자외선이 강해요` |
| 비와 우산 준비 | 비를 맞을 때 느낄 수 있는 영향의 보조입력으로 사용 | `체감온도가 낮아 비가 와요` |
| 빨래 회수 | 사람용 체감지수로만 유지 | `체감온도가 높아 빨래가 잘 말라요` |

#### 첫 노출과 상세 예시

**체감 관련 행동기준을 통과한 경우**

- 첫 노출 행동: `산책을 계획한다면 오후 8시 이후를 선택하세요`
- 영향: `오후 4시 산책에서는 더위가 보호자에게 부담이 될 수 있어요`
- 상세 숫자: `오후 4시 예상 체감온도 35.1℃`
- 계산근거: `기상청 계산방식 · 오전 11시 발표 예상 기온·습도·바람 · 수원 오후 4시`

**체감온도 숫자만 계산된 경우**

- 카드: `오후 3시 예상 체감온도 34.1℃`
- 상세: `기상청 계산방식에 수원의 오후 3시 예상 기온·습도·바람을 적용한 체감온도는 34.1℃예요`
- 체감·행동: 2-3~2-5 기준을 통과하지 않았거나 입력이 부족하면 생성하지 않음

**계산입력이 부족한 경우**

- 첫 노출: `외출 전에 최신 체감온도를 다시 확인하세요`
- 자료상태: `오후 3시 습도 자료를 받아오지 못해 예상 체감온도를 계산하기 어려워요`
- 상세: 사용 가능한 예상기온·바람과 누락된 습도·마지막 자료시각을 분리 표시

#### 금지 표현과 권장 대체

| 사용하지 않는 표현 | 문제 | 권장 대체 |
| --- | --- | --- |
| 앱 계산값에 `기상청이 예보했어요` | 계산주체를 공식기관으로 바꿈 | `기상청 계산방식으로 … 계산했어요` |
| 예보입력 계산값을 `현재 체감온도`로 표시 | 예상값을 현재 관측처럼 보이게 함 | `오후 3시 예상 체감온도 34.1℃` |
| `체감온도 34.1℃가 관측됐어요` | 입력관측과 계산결과 혼동 | `관측자료를 적용한 체감온도는 34.1℃예요` |
| `실제 체감온도` | 개인감각을 객관값처럼 확정 | 공식제공/앱계산 역할 + `체감온도` |
| `34.1℃로 느껴져요` | 숫자지수와 개인응답 혼동 | 숫자는 계산사실, 감각은 `덥게 느껴질 수 있어요`로 분리 |
| 누락입력에서 실제 기온 대입 | 계산완료처럼 보임 | `습도/바람 자료를 받아오지 못해 계산하기 어려워요` |
| 일부 시간대 max를 `오늘 최고 체감온도`로 표시 | 계산범위를 하루 전체로 확대 | 시간범위 + 가장 높은 값 + 발생시각 |
| `더위 주의/경계/위험한 더위`를 감각 label로 사용 | 공식위험·앱행동·감각 혼동 | 2-3 감각문구와 2-4 위험·행동문구 분리 |

#### 체감온도 데이터계약

- 식별: `apparentTemperatureId`, `apparentTemperatureRole`, `sourceProduct`, `providerRef`
- 값: `value`, `unit=C`, `sourcePrecision`, `displayPrecision`, `roundingRule`
- 계산: `calculationOrigin`, `calculationStatus`, `formulaKey`, `formulaVersion`, `seasonMode`, `calculatedAt`
- 입력: `airTemperatureRef`, `humidityRef`, `windSpeedRef`, `inputRole`, `requiredInputs`, `missingInputs`
- 시간·공간: `issuedAt`, `observedAt`, `targetTime`, `validFrom`, `validTo`, `stationRef/gridRef`, `areaLabel`
- 구간극값: `aggregationStart`, `aggregationEnd`, `extremeAt`, `aggregationComplete`
- 비교: `leftId`, `rightId`, `sameFormulaVersion`, `sameInputRole`, `sameSpatialBasis`, `sameTimeBasis`, `difference`
- 상태: `availability`, `freshness`, `qualityState`, `qualityFlags`
- 표현: `summaryTextKey`, `calculationFactTextKey`, `spokenText`, `evidenceRefs`
- 버전: `schemaVersion`, `apparentTemperaturePolicyVersion`, `catalogVersion`

`apparentTemperature` 하나만 내려주지 않고 `KMA_OFFICIAL/APP_KMA_METHOD/KOREAN_PERCEIVED/INDOOR` 역할을 필수로 보존한다. 계산값은 모든 입력 evidenceRef와 formulaVersion을 가져야 한다.

#### 현행 구현에 필요한 후속 변경

1. 서버와 Flutter의 `apparentTemperature`를 역할별 필드 또는 tagged value로 바꾸고 공식제공/앱계산/한국형/실내 지수를 분리해야 한다.
2. 예보입력 계산값에 `APP_KMA_METHOD_FROM_FORECAST`와 대상시각·발표시각·기온/습도/바람 evidenceRefs를 추가해야 한다.
3. 계산조건 비해당과 입력누락을 구분해 여름 습도·겨울 필수 바람자료 누락 시 실제 기온을 조용히 대입하지 않아야 한다.
4. aggregate snapshot에 구간 최댓값을 현재 `apparentTemperature`로 덮어쓰지 말고 값·시간·집계범위를 별도 보존해야 한다.
5. `weatherBrief`에서 체감온도 결측을 실제 기온으로 대체할 때 체감판정으로 사용하지 않고 별도 기온경로로 처리해야 한다.
6. 홈·상세의 `현재 체감온도/체감/최고 체감온도`를 관측/예상/구간극값 역할문구로 교체해야 한다.
7. `°C`를 `℃`로 통일하고 카드·상세·접근성의 시간·정밀도·읽기문구를 공통 formatter로 처리해야 한다.
8. 기상청 계산값에 PT 임시경계와 폭염 위험단계를 함께 적용하는 Main label을 제거하고 2-3 감각판정과 2-4 위험·행동판정으로 분리해야 한다.
9. 어제 비교는 같은 formulaVersion·입력역할·지점/격자·대상시각일 때만 생성해야 한다.
10. 앱 계산값이 공식 기상청 예보·관측처럼 렌더링되지 않는 catalog lint를 추가해야 한다.

이번 단계에서는 제품 코드를 변경하지 않는다.

#### 검증 시나리오

1. 현재 단기예보 입력으로 만든 값이 `기상청이 체감온도를 예보했어요`로 표시되지 않는지 확인한다.
2. 예보입력 계산값이 `오후 3시 예상 체감온도 34.1℃`와 대상시각을 포함하는지 확인한다.
3. 상세에서 `기상청 계산방식`, 예상 기온·습도·바람, 발표시각·예보구역을 확인할 수 있는지 확인한다.
4. 관측입력 계산값이 `체감온도가 관측됐어요`가 아니라 `관측자료를 적용해 계산했어요`로 표시되는지 확인한다.
5. 공식 체감온도 예보가 실제 존재할 때만 `기상청은 … 예보했어요`를 사용하고, 관측자료 기반값은 체감온도 자체가 관측된 것처럼 표현하지 않는지 확인한다.
6. 예보입력 계산값이 `현재 체감온도`로 표시되지 않는지 확인한다.
7. 계산조건 비해당과 기온·습도·바람 입력누락이 서로 다른 calculationStatus와 문구인지 확인한다.
8. 입력누락 때 실제 기온을 체감온도로 조용히 복사하지 않는지 확인한다.
9. 구간 최솟값·최댓값에 시작·종료시각과 실제 발생시각이 표시되는지 확인한다.
10. 일부 시간대 max를 `오늘 최고 체감온도`로 확대하지 않는지 확인한다.
11. 실제 기온과 체감온도의 차이는 같은 공간·시간·입력역할에서만 계산되는지 확인한다.
12. 관측입력 계산값과 당시 예상값이 같은 계산방식·장소·대상시각으로 비교되는지 확인한다.
13. 어제·이전 발표 비교에서 formulaVersion·입력역할·공간·시간이 다르면 비교문구를 만들지 않는지 확인한다.
14. 기상청 체감온도 숫자와 한국형 감각문구가 별도 필드·근거·문장역할로 유지되는지 확인한다.
15. 한 시점 계산값으로 폭염·한파특보 발표·발효를 생성하지 않는지 확인한다.
16. 기상청 계산값 하나에 `더위 주의/경계/위험한 더위`와 감각 label을 동시에 붙이지 않는지 확인한다.
18. 0℃와 결측이 구분되고 화면은 `℃`, 접근성은 `섭씨/영하`로 읽는지 확인한다.
19. 카드·푸시에서는 채택된 직접행동/영향이 먼저 보이고 상세 상단에서 계산값·역할·근거를 확인할 수 있는지 확인한다.
20. 행동·영향 기준을 통과하지 못했으면 숫자사실만 표시하고 일반 당부를 채워 넣지 않는지 확인한다.

### 채택 2-3. 실외의 덥고 춥고 습한 체감 문구

기상청 예보·관측의 기온·습도·풍속과 채택된 체감온도 계산값으로 설명할 수 있는 실외 체감만 사용한다. 실내환경, 실제 옷차림, 활동 여부나 개인 반응을 알고 있다고 가정하지 않는다. 시간·그늘·활동·신체 노출을 확인하지 못한 경우에는 그 조건을 단정하지 않고 일반 가능성형만 사용한다.

### 채택 2-4. 폭염·고온 피해·행동 문구

공식 특보·영향예보·기온·체감온도와 해당 지역의 시간대만 사용한다. 사용자의 운동일정, 질환, 냉방상태, 증상은 추정하거나 입력받은 것으로 가정하지 않는다.

- 공식 사실: `수원에는 폭염경보가 발효 중이에요`
- 내부 가능성: `오후 2~5시에 실외 운동을 하면 온열질환이 발생할 수 있어요`
- 직접행동: 실제로 부담이 더 낮은 시간이 확인됐을 때만 `가능하다면 오후 2~5시 실외 운동을 다른 시간대로 옮기세요`
- 대체시간이 없을 때: `오후 2~5시에는 실외 운동을 줄이고 시원한 곳에서 쉬세요`
- 폭염중대경보가 실제 발효됐을 때: `야외 보행·운동·작업을 즉시 중단하세요`
- 공식 응급안내: `의식이 흐리거나 의식을 잃었다면 즉시 119에 신고하세요 · 물은 마시게 하지 마세요`
- 고령자 돌봄 일반안내: `오전 6시 전에 주변 어르신 거주지의 난방 상태와 안부를 확인하세요`

응급문구는 날씨만으로 증상이 발생했다고 판단해 자동 노출하지 않는다. 질병관리청의 일반 응급정보나 사용자가 직접 연 도움말에서만 제공한다.

고온 체감은 2-3의 실외 온열·고온다습 기준별 3종만 재사용한다. 실제 발한·피부상태·수분섭취 결과를 아는 것처럼 말하지 않는다.

### 채택 2-5. 한파·저온 피해·행동 문구

공식 한파특보·영향예보와 해당 지역의 기온·바람·예상 체감온도만 사용한다. 사용자의 외출일정, 질환, 의복, 신체상태, 돌봄대상 등록 여부는 추정하지 않는다.

- 공식 사실: `수원에는 한파경보가 발효 중이에요`
- 내부 가능성: `오전 6~9시에 실외에 오래 머물면 한랭질환이 발생할 수 있어요`
- 직접행동: `오전 6~9시 외출 전에 모자·목도리·장갑을 챙기세요`
- 시간조정: 실제로 부담이 더 낮은 시간이 확인됐을 때만 `가능하다면 이른 아침 실외 운동을 기온이 더 높은 시간대로 옮기세요`
- 고령자 돌봄 일반안내: `오전 6시 전에 주변 어르신 거주지의 난방 상태와 안부를 확인하세요`
- 공식 응급안내: `의식이 흐리거나 저체온증이 의심되면 즉시 119에 신고하세요`

응급문구는 사용자의 증상을 앱이 판정해 자동 노출하지 않는다. 공식 도움말에서 일반 정보로 제공한다. 추위 체감은 2-3의 다섯 기준별 3종만 재사용한다.

## 7. 강수·적설·노면 문구

### 채택 3-1. 강수확률과 현재 강수

- 공식 예보: `기상청은 수원의 오후 2~3시 강수확률을 60%로 예보했어요`
- 현재 강수: 같은 500m 기준시각의 기상청 관측분석자료와 레이더가 모두 강수를 나타낼 때 `오후 2시에는 비가 내리고 있을 수 있어요`
- 행동: 우산 알림이 켜져 있으면 `비가 내리고 있을 수 있어요. 지금 외출한다면 우산을 챙기세요`

두 공간자료가 함께 쓰이면 본문에 출처 괄호를 붙이지 않는다. 하나만 강수를 나타내면 현재 강수 알림을 보류한다. 관측장비 지점값은 현재 위치 강수 알림에 사용하지 않는다.

### 채택 3-2. 시간당 강수량과 생활영향

관측분석 강수량을 주값으로 표시하고 레이더는 확인자료로 보존한다. 같은 500m 셀·시간·품질이 유효할 때만 결합한다. 낮은 값은 대표값으로 사용하지 않는다.

| 시간당 강수량 | 승인문구 3종 |
| --- | --- |
| `3mm 미만` | ① `오후 3~4시에는 가벼운 빗방울이 떨어질 수 있어요`<br>② `오후 3~4시에는 약한 빗방울이 내릴 수 있어요`<br>③ `오후 3~4시에는 이슬비처럼 약한 비가 내릴 수 있어요` |
| `3~5mm 미만` | ① `오후 3~4시에는 옷이나 머리카락이 조금 젖을 만큼 비가 올 수도 있어요`<br>② `오후 3~4시에는 빗방울에 옷이나 머리카락이 조금씩 젖을 수 있어요`<br>③ `오후 3~4시에 우산 없이 걸으면 옷이나 머리카락이 조금 젖을 수 있어요` |
| `5~15mm 미만` | ① `오후 3~4시에는 우산이 없으면 옷과 신발이 젖을 수 있어요`<br>② `오후 3~4시에는 안경이나 차량 유리에 빗물이 맺혀 앞이 흐리게 보일 수 있어요`<br>③ `오후 3~4시에 걸어서 이동한다면 옷과 신발이 비에 젖을 수 있어요` |
| `15~30mm 미만` | ① `오후 3~4시에는 우산을 써도 옷이 젖을 수 있어요`<br>② `오후 3~4시에는 보행로 곳곳에 물이 고일 수 있어요`<br>③ `오후 3~4시에는 낮은 곳에 물이 차기 시작할 수 있어요` |
| `30~50mm 미만` | ① `오후 3~4시에는 배수가 좋지 않은 보행로에서 신발이 젖을 수 있어요`<br>② `오후 3~4시에는 물고임이 많은 구간에서 이동이 불편할 수 있어요`<br>③ `오후 3~4시에는 차량 운행이 어려워질 수 있어요` |
| `50mm 이상` | ① `오후 3~4시에는 정상적으로 걷기 어려울 수 있어요`<br>② `오후 3~4시에는 차량 운행이 어려워질 수 있어요`<br>③ `오후 3~4시에는 극심한 교통정체가 발생할 수 있어요` |

장소 특성이 필요한 문구는 공식 침수취약구간·도로정보가 있을 때만 사용한다. 개인 보행·운전 여부는 조건부로 표현한다.

### 채택 3-3. 누적 강수량

- 분석 누적: `오늘 0시부터 오후 2시까지 누적 강수량은 18mm로 분석됐어요`
- 실제 분석값 0mm: `오늘 0시부터 오후 2시까지 누적 강수량은 0mm예요`
- 공식 예상 누적: `기상청은 수원에 오후 2시부터 오후 8시까지 25~40mm의 비가 더 내릴 것으로 예보했어요`
- 앱 합산: `기상청의 시간별 예보를 합산하면 수원에는 오후 2시부터 오후 8시까지 25~40mm가 예상돼요`
- 예보 감소: `오후 3~9시 예상 누적량은 20~30mm예요. 오전 11시 발표 예보의 25~40mm보다 줄었어요`
- 자료 간 차이: `오늘 0시~오후 2시 누적 강수량, 18mm/25mm` `(기상청 관측분석자료/기상청 레이더)`

`미만·범위·이상`을 보존하고 누락구간은 0으로 채우지 않는다. 관측분석과 레이더의 평균·낮은 값은 사용자 대표 누적량으로 만들지 않는다.

### 채택 3-4. 호우·강한 비

호우 발생가능성·예비특보·발효 예정은 사용자에게 표시하지 않는다. 실제 발효·변경·해제와 실제 긴급재난문자만 공식 사실로 안내한다.

- 직접행동: `호우경보가 발효 중이니, 하천변과 지하차도에 접근하지 마세요`
- 내부 가능성: `오늘 저녁에는 시간당 30~50mm의 비가 집중될 수 있어요`
- 공식 사실: `수원에는 호우경보가 발효 중이에요`

### 채택 3-5. 소나기·낙뢰·돌풍·우박

공식 현상코드가 소나기일 때만 `소나기`를 사용한다. 행동문장에는 원인을 먼저 둔다.

- `소나기가 내릴 수 있으니, 외출한다면 우산을 챙기세요`
- `소나기가 내릴 수 있으니, 실외 빨래가 있다면 비가 시작되기 전에 실내로 들여놓으세요`
- `오후 3시 전, 낙뢰를 피해 야외활동을 마치고 안전한 건물이나 자동차 안으로 이동하세요`
- `돌풍이 부니, 외출해야 한다면 우산 대신 비옷을 준비하세요`
- `우박이 시작되기 전에 야외활동을 마치고 건물 안으로 이동하세요`
- 공식 관측: `기상청은 오후 2시 수원에서 낙뢰를 관측했어요`

### 채택 3-6. 비의 시작·이어짐·그침

`오늘은`, `낮 동안은`, `밤사이`, `새벽에는` 같은 시점과 `비가 와서`, `비 때문에`, `비가 내려`, `비가 이어지고`, `빗물에`를 의미에 맞게 조합한다. 주어 없이 `비가 이어진다~`로 시작하지 않는다.

- 시작: `40분 안에 이슬비처럼 약한 비가 시작될 수 있어요`
- 이어짐: `밤사이 비가 이어지고 도로에 물이 고일 수 있어요`
- 잠시 그침: `오후 4~5시에는 비가 잠시 그칠 수 있어요`
- 다시 시작: 앞선 강수와 무강수 상태가 모두 확인된 경우에만 `오후 6시부터 비가 다시 시작될 수 있어요`
- 종료: 현재 두 공간자료의 무강수와 후속예보를 함께 확인한 뒤에만 `비가 그쳤을 수 있어요`

### 채택 3-7. 강수형태와 변화

기상청이 발표한 `비`, `비/눈`, `눈`, `빗방울`, `눈날림`, `소나기`를 원자료 범위에서 사용한다. 한 현상에서 다른 현상으로 달라지면 `오후 5시부터 비가 눈으로 바뀔 수 있어요`라고 표시한다. 변화 없는 `강수없음`은 알리지 않는다.

### 채택 3-8. 눈과 새로 쌓인 눈

카드 제목은 `새로 쌓인 눈`으로 사용하고 본문에서는 `새로`를 반복하지 않는다. `신적설`은 내부 원자료명으로만 보존한다.

| 시간당 적설량 | 승인문구 3종 |
| --- | --- |
| `0.1~0.5cm 미만` | ① `오후 5~6시에는 바닥에 눈이 아주 얇게 쌓일 수 있어요`<br>② `오후 5~6시에는 바닥에 눈이 살짝 내려앉을 수 있어요`<br>③ `오후 5~6시에는 눈이 쌓이기 시작할 수 있어요` |
| `0.5~1.5cm 미만` | ① `오후 5~6시에는 바닥이 눈으로 덮일 수 있어요`<br>② `오후 5~6시에는 눈이 쌓일 수 있어요`<br>③ `오후 5~6시에는 바닥의 색이 눈으로 달라졌다고 느낄 수도 있어요` |
| `1.5~3cm 미만` | ① `오후 5~6시에는 눈이 꽤 쌓일 수 있어요`<br>② `오후 5~6시에는 바닥이 눈으로 넓게 덮일 수 있어요`<br>③ `오후 5~6시에는 발이 눈에 들어갈 수 있어요` |
| `3cm 이상` | ① `오후 5~6시에는 짧은 시간 동안 눈이 빠르게 쌓일 수 있어요`<br>② `오후 5~6시에는 바닥에 쌓인 눈이 빠르게 늘어날 수 있어요`<br>③ `오후 5~6시에는 제설 전 도로에 눈이 빠르게 쌓일 수 있어요` |

실제 상태변화는 `~할 수 있어요`를 사용하고, 사람이 눈 덮인 정도를 어떻게 인식하는 문장에만 `느낄 수도 있어요`를 사용한다.

### 채택 3-9. 적설 관측·예보 비교

오차가 `0.5cm 이내`면 `오후 5~6시 예보내용과 유사하게 관측됐어요`라고 표시한다.

1. `오후 6시 수원에서 최근 3시간 동안 눈 4.2cm가 쌓인 것으로 관측됐어요. 예상량 3.8cm와 유사하게 관측됐어요`
2. `오후 6시 수원에서 최근 3시간 동안 눈 4.2cm가 쌓인 것으로 관측됐어요. 예상량 3cm보다 관측된 양이 1.2cm 많아요`
3. `오후 6시 수원에서 최근 3시간 동안 눈 6.2cm가 쌓인 것으로 관측됐어요. 예상범위보다 관측된 양이 1.2cm 많아요`
4. `오후 6시 수원에서 현재 쌓인 눈은 4.6cm로 관측됐어요. 오후 3시에 관측된 2.1cm보다 2.5cm 많아요`

### 채택 3-10. 대설과 적설 행동

특보·안전안내문자는 실제 발효·발송됐을 때만 알린다.

- 더 나은 이동시간이 확인됨: `눈이 많이 내릴 수 있으니, 가능하다면 오후 5시 전에 이동을 마치세요`
- 내부 영향: `오후 5~6시에는 눈이 많이 쌓여 도로 이동이 어려워질 수 있어요`
- 공식 예보: `기상청은 수원에 오후 5~6시 눈이 5cm 이상 쌓일 것으로 예보했어요`
- 더 나은 시간 없음: `눈이 많이 쌓일 수 있으니, 외출 전에 도로 통제와 대중교통 운행정보를 확인하세요`
- 노후된 시설 일반안내: `눈이 빠르게 쌓이고 있으니, 노후된 시설이 있다면 안전한 위치에서 상태를 확인하세요`

시설의 존재·노후도·현재 상태를 앱이 안다고 표현하지 않는다. 공식 대피·통제가 있으면 연구기반 일반안내보다 먼저 표시한다.

### 채택 3-11. 도로 결빙

노면수분과 노면온도, 측정오차를 사용한다. 대기기온·체감온도·강수확률만으로 판정하지 않는다.

| 조건 | 처리 | 기본 문구 |
| --- | --- | --- |
| 노면수분 있음 + 온도 오차범위 전체가 `0℃ 이하` | 결빙조건 뚜렷 | `오전 6~8시에는 젖은 도로가 얼 수 있어요` |
| 노면수분 있음 + 온도 오차범위가 `0℃에 걸침` | 결빙 가능 | `오전 6~8시에는 젖은 도로에 얼음이 생길 가능성이 있어요` |
| 노면수분 있음 + 온도 오차범위 전체가 `0℃ 초과` | 판정 없음 | 기본 노출 없음 |
| 노면자료 없음 + 실제 영하기온·최근 강수 확인 | 확인 필요 | `기온과 최근 강수는 확인됐지만 노면자료가 없어 도로가 얼었는지 확인하기 어려워요` |

결빙조건이 뚜렷한 경우의 문구 3종:

1. `오전 6~8시에는 젖은 도로가 얼 수 있어요`
2. `오전 6~8시에는 노면의 물기가 얼음으로 바뀔 수 있어요`
3. `오전 6~8시에는 도로에 얼음이 생길 수 있어요`

오차범위가 0℃에 걸치는 경우의 문구 3종:

1. `오전 6~8시에는 노면의 물기가 있다면 얼게 될 가능성이 있어요`
2. `오전 6~8시에는 젖은 도로에 얼음이 생길 가능성이 있어요`
3. `오전 6~8시에는 도로에 남은 물이 얼 수도 있어요`

관측값 `0.8℃`, 오차범위 `0.0~1.6℃` 예시는 `노면의 물기가 있다면 적은 확률로 얼 수도 있어요`로 표시한다.

### 채택 3-12. 블랙아이스(도로살얼음)

앱 항목명은 `블랙아이스(도로살얼음)`이다. 기상청 원자료명 `도로살얼음 발생 가능 정보`와 공식 `정보없음 0·관심 1·주의 2·위험 3` 단계는 출처·구간·기준시각과 함께 보존한다. 표준노드링크의 시작·종료 좌표는 내부에서 보존하되 방향명이 제공되지 않으면 사용자용 방향을 추정하지 않는다.

- 공식 발생: `도로관리기관은 오전 6시 ○○교 수원방향에 블랙아이스가 발생했다고 알렸어요`
- 공식 관측: `오전 6시 ○○교 수원방향에서 블랙아이스가 관측됐어요`
- 공식 단계: `기상청은 오전 6시 ○○교 수원방향의 도로살얼음 발생 가능성을 주의 2단계로 안내했어요`
- 내부 위험: `오전 6~8시에는 블랙아이스가 생길 위험이 있어요`
- 내부 가능: `오전 6~8시에는 블랙아이스가 생길 수 있어요`
- 자료부족: `노면온도·수분·형성경로 자료가 없어 블랙아이스 가능성을 판단하기 어려워요`

내부판정은 같은 도로구간의 노면수분·노면온도와 `비·눈 뒤 재결빙`, `어는 강수`, `안개·이슬·서리` 중 확인된 형성경로가 함께 있을 때만 생성한다. 사용자의 이용경로·이동시간은 가정하지 않는다.

행동은 이유를 앞에 둔다.

- `블랙아이스가 관측됐으니, 해당 구간에서는 속도를 줄이고 충분한 안전거리를 두세요`
- `블랙아이스가 생길 수 있으니, 운전한다면 출발 전에 최신 도로정보를 확인하세요`
- 공식 우회로가 확인됨: `우회할 수 있다면 블랙아이스가 관측된 ○○교를 피해 도로기관이 안내한 △△도로를 이용하세요`

### 채택 3-13. 서리·차량 성에 문구의 제한

기상청의 지역 서리 관측·예측은 공식 사실로 표시할 수 있다. 현재 앱에는 차량 등록, 주차환경, 차량 유리 표면온도, 차량 실내 온습도 자료가 없으므로 특정 차량의 성에·김서림 상태나 발생 가능성은 판정하지 않는다.

- 공식 관측: `수원에서 서리가 관측됐어요`
- 공식 예측: `기상청은 오늘 밤 수원에 서리가 내릴 수 있다고 예측했어요`
- 조건부 일반행동: `서리가 예상되니, 야외에 주차한 차량이 있다면 출발 전에 유리 상태를 확인하세요`

지역 서리 확률을 차량 성에 확률, 블랙아이스(도로살얼음) 확률 또는 사용자 차량의 상태로 바꾸지 않는다.

### 채택 3-14. 동파 문구의 제한

공식 한파특보·영향예보와 지역 기온은 사실로 표시할 수 있다. 현재 앱은 수도계량기·배관의 노출, 보온, 설비유형, 실제 온도를 알 수 없으므로 특정 거주지의 동파 가능성을 판정하지 않는다.

- 공식 사실: `수원에는 한파경보가 발효 중이에요`
- 조건부 일반행동: `기온이 크게 내려갈 수 있으니, 노출된 수도관이 있다면 보온 상태를 확인하세요`

`수도관이 얼 수 있어요`, `동파될 가능성이 있어요`는 해당 시설 상태를 확인할 수 있는 별도 입력이나 센서가 생기기 전까지 개인 알림으로 사용하지 않는다.

## 8. 바람·습도 문구

### 채택 4-1. 풍속 표현

#### 공식 숫자·단계 문구

| 풍속 | 기상청 공식 표현 | 예보문구 | 관측문구 |
| ---: | --- | --- | --- |
| `0~4m/s 미만` | 약한 바람 | `기상청은 오후 3시 수원에 풍속 3m/s의 약한 바람을 예보했어요` | `오후 2시 수원 관측소에서 10분 평균풍속 3.2m/s가 관측됐어요` |
| `4~9m/s 미만` | 약간 강한 바람 | `기상청은 오후 3시 수원에 풍속 6m/s의 약간 강한 바람을 예보했어요` | `오후 2시 수원 관측소에서 10분 평균풍속 6.2m/s가 관측됐어요` |
| `9~14m/s 미만` | 강한 바람 | `기상청은 오후 3시 수원에 풍속 11m/s의 강한 바람을 예보했어요` | `오후 2시 수원 관측소에서 10분 평균풍속 11.2m/s가 관측됐어요` |
| `14m/s 이상` | 매우 강한 바람 | `기상청은 오후 3시 수원에 풍속 15m/s의 매우 강한 바람을 예보했어요` | `오후 2시 수원 관측소에서 10분 평균풍속 15.2m/s가 관측됐어요` |

- 앱 미수신: `자료를 받아오지 못해 오후 3시 예상 풍속을 확인하기 어려워요`
- 품질오류: `오후 2시 풍속자료에 오류가 있어 확인하기 어려워요`
- 이전 자료: `마지막 풍속 관측은 오후 1시 50분 자료예요 · 현재 상태는 달라졌을 수 있어요`
- 관측과 예보 차이: `오후 2시 수원 관측소에서 10분 평균풍속 11.2m/s가 관측됐어요. 예보풍속 9m/s보다 관측풍속이 2.2m/s 높아요`

### 채택 4-2. 강풍 문구

#### 공식 사실과 내부 피해 가능성

- 일반 예보: `기상청은 오후 3시 수원에 풍속 11m/s의 강한 바람을 예보했어요`
- 실제 발효: `수원에는 강풍주의보가 발효 중이에요`
- 실제 변경: `기상청은 수원의 강풍주의보를 강풍경보로 변경했어요`
- 실제 해제: `수원의 강풍주의보가 해제됐어요`
- 공식 관측: `오후 2시 수원 관측소에서 최대순간풍속 18.2m/s가 관측됐어요`
- 실제 피해: `오후 2시 ○○도로에서 간판 낙하가 발생했어요`

발생가능성 정보·예비특보·발효 전 발표는 내부 재조회에만 사용하고 사용자에게 알리지 않는다. 예보값이 공식 기준을 넘었더라도 앱이 강풍주의보·경보를 생성하지 않는다.

| 내부조건 | 영향 가능성 | 직접행동 |
| --- | --- | --- |
| 평균풍속 예보 `9m/s 이상` 또는 최대순간풍속 `10m/s 이상` | `가벼운 야외 물건이 바람에 움직일 수 있어요` | `강한 바람이 불 수 있으니, 화분이나 야외 물건을 실내로 옮기거나 고정하세요` |
| 최대순간풍속 `10m/s 이상` + 미고정·노후 시설 또는 노출환경 | `고정되지 않은 물건이나 노후된 시설물이 바람의 영향을 받을 수 있어요` | `강한 바람이 불 수 있으니, 간판·수목·공사장 주변을 피하세요` |
| 같은 시공간의 10분 평균 `14m/s 이상` + 최대순간 `23m/s 이상` | `시설물이 파손되거나 낙하물이 생길 수 있어요` | `시설물이나 낙하물에 피해를 입을 수 있으니, 야외 보행·운동·작업을 중단하고 안전한 건물 안으로 이동하세요` |
| 실제 강풍특보 발효 | 공식 행동요령을 우선 | `강풍특보가 발효 중이니, 야외활동을 줄이고 간판·수목·유리창·공사장 주변을 피하세요` |

내부 피해 가능성은 모두 가능성형으로 표시한다. 실제 피해·통제·특보만 확정형으로 표시하며 `바람이 세니 위험해요`, `균형을 잃어요`, `사고가 발생해요`처럼 근거와 대상을 생략한 표현은 사용하지 않는다.

### 채택 4-3. 돌풍 문구

#### 공식 사실과 내부 영향

- 공식 예보문: `기상청은 오늘 오후 수원에 돌풍 가능성을 예보했어요`
- 최대순간풍속 예측: `기상청은 오후 4시 최대순간풍속 14m/s를 예보했어요`
- 최대순간풍속 관측: `오후 4시 수원 관측소에서 최대순간풍속 18.2m/s가 관측됐어요`
- 실제 돌풍 확인: `기상청은 오후 4시 수원에 돌풍이 발생했다고 확인했어요`

최대순간풍속 하나를 돌풍 발생으로 바꾸지 않고, `돌풍주의보·돌풍경보`라는 공식 단계도 만들지 않는다. 소나기·낙뢰·우박만으로 돌풍을 추가하지 않고 기상청 원 예보에 돌풍이 명시됐을 때만 공식 예보문을 표시한다.

| 내부조건 | 영향 가능성 | 직접행동 |
| --- | --- | --- |
| 공식 돌풍 가능성 + 노출된 야외물건·시설 | `갑자기 강해지는 바람에 야외 물건이나 노출된 시설물이 영향을 받을 수 있어요` | `돌풍이 불 수 있으니, 야외 물건을 고정하고 간판·수목·천막 주변을 피하세요` |
| 최대순간풍속 `10m/s 이상` + 취약·노출조건 | `순간적으로 강해지는 바람에 고정되지 않은 물건이 움직일 수 있어요` | `바람이 갑자기 강해질 수 있으니, 고정되지 않은 물건을 실내로 옮기세요` |
| 소나기·천둥·번개·우박과 돌풍이 공식 예보에 함께 명시 | `소나기와 함께 바람이 갑자기 강해져 야외 시설물이 영향을 받을 수 있어요` | `소나기와 돌풍이 예상되니, 야외활동을 마치고 안전한 건물 안으로 이동하세요` |

### 채택 4-4. 보행·자전거·운전 영향 문구

전국 공통 `안전·주의·위험·통제` 풍속표는 만들지 않는다. 공식 노선 통제·감속·차종제한은 기관이 실제 시행한 경우 확정형으로, 활동별 앱 판단은 활동·노출구간·풍속종류가 일치할 때 가능성형으로 표시한다.

| 활동·조건 | 내부 영향 가능성 | 직접행동 |
| --- | --- | --- |
| 보행 + 평균 `9m/s 이상` 또는 최대순간 `10m/s 이상` + 교량·해안·개방지·도심협곡·취약조건 | `노출된 길에서는 바람에 균형을 잡기 어려울 수 있어요` | `강한 바람이 불 수 있으니, 난간을 이용하고 보폭을 줄여 천천히 이동하세요` |
| 현장 보행자 높이 센서·해당 건물 평가에서 1시간 평균 `15m/s 이상` | `이 건물 주변에서는 바람 때문에 걷기 어려울 수 있어요` | `건물 주변의 바람이 강하니, 가능하다면 건물 안쪽 보행로를 이용하세요` |
| 자전거·개인형 이동장치 + 노출구간·돌풍 | `순간적인 옆바람에 진행 방향이 흔들릴 수 있어요` | 더 나은 대체수단이 확인되면 `옆바람이 강할 수 있으니, 가능하다면 자전거 대신 대중교통을 이용하세요` |
| 버스·박스형 화물차 등 + 현장 횡풍 `7m/s 이상` | `갑작스러운 옆바람에 차로를 유지하기 어려울 수 있어요` | `노출된 구간에서는 속도를 줄이고 급핸들 조작을 피하세요` |
| 승용차 + 현장 횡풍 `13m/s 이상` | `갑작스러운 옆바람에 조향이 흔들릴 수 있어요` | `교량이나 터널 출구에서는 속도를 줄이고 충분한 안전거리를 두세요` |
| 횡풍 + 미끄러운 노면·저시정 | `옆바람과 미끄러운 노면이 겹쳐 조향과 제동이 어려울 수 있어요` | `속도를 줄이고 급가속·급제동·급핸들 조작을 피하세요` |

### 채택 4-5. 우산 사용 영향 문구

| 조건 | 내부 영향 가능성 | 직접행동 |
| --- | --- | --- |
| 평균 `4~9m/s 미만` + 긴 노출·큰 우산·한 손 짐·취약조건 | `바람 때문에 우산을 오래 들면 손목과 팔에 부담이 커질 수 있어요` | `바람이 불고 비가 올 수 있으니, 한 손을 비울 수 있게 짐을 정리하세요` |
| 평균 `9m/s 이상` 또는 최대순간 `10m/s 이상` 또는 공식 돌풍·강풍특보 | `바람에 우산이 흔들려 안정적으로 사용하기 어려울 수 있어요` | `강한 바람과 비가 예상되니, 외출해야 한다면 우산 대신 후드가 있는 방수 겉옷을 준비하세요` |
| 돌풍 + 건물모서리·교량·해안·개방지 | `바람이 갑자기 강해지면 우산이 당겨지거나 방향이 흔들릴 수 있어요` | `돌풍이 불 수 있으니, 외출해야 한다면 우산 대신 비옷을 준비하세요` |
| 시간당 강수량 `15mm 이상` | `비가 강해 우산을 써도 옷이 젖을 수 있어요` | `비가 강하게 올 수 있으니, 방수 겉옷과 젖어도 되는 신발을 준비하세요` |
| 공식 낙뢰 예상·관측 + 야외 우산 사용 | `우산을 들고 야외에 있으면 낙뢰에 노출될 수 있어요` | `낙뢰를 피해 안전한 건물이나 자동차 안으로 이동하세요` |

### 채택 4-6. 실외 습도 사실 문구

- 실외 예보: `기상청은 오후 3시 수원에 상대습도 72%를 예보했어요`
- 실외 관측: `오후 3시 수원에서 상대습도 75%가 관측됐어요`
- 앱 미수신: `오후 3시 습도자료를 받아오지 못했어요`
- 품질오류: `오후 3시 습도자료에 오류가 있어 확인하기 어려워요`
- 이전 자료: `마지막 습도 관측은 오후 1시 자료예요 · 현재 상태는 달라졌을 수 있어요`

실외 상대습도를 집이나 방의 습도로 바꾸지 않는다. 실내 습도·쾌적성·제습 또는 가습 필요성을 생성하지 않는다.

### 채택 4-7-1. 실외 고온다습 체감의 생성조건

같은 위치·시간의 기온·습도와 채택된 실외 체감온도 조건이 함께 충족될 때만 `덥고 습한 후텁지근함`을 생성한다. 피부 끈적임은 `밖에서 움직이면`이라는 조건을 문장에 직접 넣는다. 실내 눅눅함·침구 상태·땀 발생·불쾌감·환기 부족은 판단하지 않는다.

### 채택 4-7-2. 실외 고온다습 체감문구 3종

| 체감기준 | 문구 3종 |
| --- | --- |
| 덥고 습한 후텁지근함 | ① `후텁지근하게 느껴질 수 있어요`<br>② `더운 공기와 습함이 느껴질 수 있어요`<br>③ `덥고 습하다고 느낄 수도 있어요` |

실외 기상자료로 실내 눅눅함·축축함·꿉꿉함을 생성하지 않는다.

### 채택 4-8-1. 건조특보와 실외 습도 사실 문구

공식 건조특보는 실제 발효·해제가 확인됐을 때만 확정형으로 안내한다. 실효습도와 실외 상대습도는 서로 다른 값으로 표시한다.

- 실제 특보: `수원에는 건조주의보가 발효 중이에요`
- 실제 해제: `수원의 건조주의보가 해제됐어요`
- 공식 실효습도: `기상청은 오후 3시 수원의 실효습도를 24%로 발표했어요`
- 실외 예보: `기상청은 오후 3시 수원에 상대습도 28%를 예보했어요`
- 실외 관측: `오후 3시 수원에서 상대습도 27%가 관측됐어요`

실외 습도나 건조특보만으로 눈·입술·코·목·피부의 마름, 정전기, 실내 건조 또는 가습기 필요성을 예측하지 않는다.

### 채택 5-1-1. 자외선지수 공식 단계와 사실 문구

| 자외선지수 | 기상청 공식 단계 | 사용자 사실문구 예시 |
| ---: | --- | --- |
| `0~2` | 낮음 | `기상청은 오후 1시 수원의 자외선지수를 2, 낮음 단계로 예보했어요` |
| `3~5` | 보통 | `기상청은 오후 1시 수원의 자외선지수를 5, 보통 단계로 예보했어요` |
| `6~7` | 높음 | `기상청은 오후 1시 수원의 자외선지수를 7, 높음 단계로 예보했어요` |
| `8~10` | 매우 높음 | `기상청은 오후 1시 수원의 자외선지수를 9, 매우 높음 단계로 예보했어요` |
| `11 이상` | 위험 | `기상청은 오후 1시 수원의 자외선지수를 11, 위험 단계로 예보했어요` |

기상청 예보값, 지상관측값, 위성 산출값, 앱이 계산한 주변 누적노출 참고값을 서로 다른 자료유형으로 표시한다. 공식 단계는 원 숫자와 함께 사용하며 앱이 `안전·주의·심각` 같은 새 단계를 만들지 않는다.

- 앱 미수신: `자료를 받아오지 못해 오후 1시 자외선지수를 확인하기 어려워요`
- 품질오류: `오후 1시 자외선지수 자료에 오류가 있어 확인하기 어려워요`
- 이전 자료: `마지막으로 확인한 자외선지수는 오전 11시 발표자료예요 · 이후 달라졌을 수 있어요`
- 예보변화: `오후 1시 자외선지수는 9, 매우 높음 단계로 예보됐어요. 마지막 예보의 7, 높음 단계보다 올라갔어요`

### 채택 5-1-2. 자외선 직접 체감기준

자외선은 눈으로 보거나 피부에서 강도를 직접 느낄 수 없다. 햇볕의 뜨거움은 주로 복사열·적외선과 기온, 끈적함은 습도·땀, 눈부심은 가시광선의 영향이므로 자외선지수의 체감단계로 사용하지 않는다.

따갑지 않음·선선함·구름·눈부심이 약함을 자외선 노출이 없거나 안전하다는 뜻으로 바꾸지 않는다. 노출 뒤 나타난 붉어짐·화끈거림·따가움은 현재 자외선 강도의 즉시 체감이 아니라 지연된 피부반응 가능성으로 5-2에서 별도 처리한다.

### 채택 5-1-3. 자외선을 직접 체감하기 어려움 문구 3종

| 체감기준 | 문구 3종 | 사용조건 |
| --- | --- | --- |
| 자외선 강도의 직접 체감 어려움 | ① `자외선 강도는 몸으로 바로 느끼기 어려울 수 있어요`<br>② `자외선은 햇볕의 뜨거움과 달라 몸으로 바로 느끼기 어려울 수 있어요`<br>③ `덥게 느껴지는 정도와 자외선 강도는 다를 수 있어요` | 모든 자외선지수 단계에 공통 적용. 뜨거움·따가움·눈부심을 자외선 단계로 변환하지 않음 |

5-1-3은 사용자 확정으로 채택했다.

### 채택 5-2-1. 자외선 노출과 피부반응의 일반 안내

기상청이 단계별로 제공하는 피부화상 가능시간은 출처가 붙은 일반정보로만 표시한다. 예를 들어 `기상청은 자외선지수 높음 단계에서 1~2시간 안에도 피부화상을 입을 수 있다고 안내하고 있어요`라고 안내할 수 있다.

앱은 사용자의 실제 야외 체류시간·피부형·노출부위·의복·선크림 사용 여부를 알 수 없으므로 개인 누적노출량, 남은 안전시간, 화상 예상시각이나 피부 화끈거림·따가움을 생성하지 않는다.

### 채택 5-3. 선크림 준비 문구

공식 자외선지수 단계와 해당 단계의 공식 대응요령을 바탕으로 준비행동만 안내한다.

- `자외선이 강할 수 있으니, 외출한다면 자외선 차단제를 준비하세요`
- 덧바름 간격·사용량·사용부위는 확인된 공식 안내나 제품 표시사항을 일반정보로만 제공한다.

앱은 실제 도포 여부, 제품 종류, 피부형, 땀·물 접촉이나 피부반응을 알 수 없으므로 보호시간·효과·사용결과를 판단하지 않는다.

### 채택 5-4-1. 모자·양산의 사실·행동·체감 생성조건

자외선지수와 사용자가 켠 양산 알림을 연결하되 실제 외출이나 양산 사용을 가정하지 않는다. 일반 제품에 고정된 자외선 차단율·체감온도 감소량을 붙이지 않는다.

- 공식 일반안내: `기상청은 자외선지수 보통 단계부터 모자를 이용하도록 안내하고 있어요`
- 내부 도움 가능성: `그늘이 적은 야외에서는 모자나 양산이 직사광선을 가리는 데 도움이 될 수 있어요`
- 직접행동: `자외선이 강할 수 있으니, 그늘이 적은 야외에 나간다면 모자나 양산을 준비하세요`

공식 예보·관측·특보·통제자료로 외부 조건만 비교하며 개인 일정이나 이용경로가 있다고 가정하지 않는다.

- 외출·운동: `외출한다면`, `야외에서 운동한다면`처럼 조건을 앞에 밝힌다.
- 반려견 산책: `반려견과 산책할 계획이라면`처럼 일반 조건부 행동만 안내하며 품종·건강·발바닥 상태나 개별 안전성을 판단하지 않는다.
- 출퇴근·운전: 공식 통제·대중교통 운행·도로 기상정보를 해당 지역의 일반 정보로 표시한다. 사용자의 이용경로나 대체경로를 알고 있다고 가정하지 않는다.
- 세차·야외행사: `세차한다면`, `야외행사를 준비한다면`처럼 조건부로만 표시하며 예약·운영·완료 상태를 판단하지 않는다.

### 채택 6-20-1. 밤 외부 날씨와 취침 전 확인 문구

기상청의 실제 열대야주의보 발효·해제, 관측된 열대야와 밤 예보·관측만 확정형으로 표시한다. 열대야는 야외 관측소의 밤최저기온이며 침실온도나 수면불편을 뜻하지 않는다.

- 공식 발효: `서울에는 열대야주의보가 발효 중이에요`
- 공식 관측: `서울에서 밤최저기온 25.4℃가 관측돼 열대야가 발생했어요`
- 밤 예보: `기상청은 오늘 밤 기온과 습도가 높을 것으로 예보했어요`
- 조건부 행동: `오늘 밤 기온과 습도가 높게 예보됐으니, 잠들기 전에 침실 상태를 확인하고 필요하면 냉방이나 제습으로 조절하세요`

앱은 침실 온습도·침구·냉난방 상태·실제 취침시각이나 수면결과를 알 수 없으므로 침실 체감, 이불 상태, 손발시림, 숙면 여부를 예측하지 않는다. 수면환경에는 체감문구 3종을 두지 않는다.
