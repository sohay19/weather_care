# 체감온도 계산·표현 기준

- 기준일: 2026-09-22
- 적용 범위: 서버 현재·시간별 체감 계산, Main·Detail·위젯 체감 표시
- 목적: 앱이 자체 체감온도를 만들지 않고 기상청 방식 체감온도만 일관되게 사용한다.

## 1. 데이터 계약

| 역할 | API 필드 | 원칙 |
| --- | --- | --- |
| 실제 기온 | `temperature` | 관측은 APIHub 격자 실황 또는 최근접 AWS, 미래는 기상청 단기예보를 사용한다. |
| 기상청 체감온도 | `kmaApparentTemperature` | 모든 화면·위젯·시간별 예보와 행동 판단에서 사용하는 유일한 체감온도다. |
| 호환 별칭 | `apparentTemperature` | 기존 앱 호환을 위해 기상청 체감온도와 같은 값을 제공한다. |
| 공식 위험 | `activeWarnings` 등 | 실제 발효된 기상청 특보를 별도로 표시한다. |

`perceivedTemperature`, `thermalSensation`, `thermalBrief`, PMV·복사열·옷차림·최근 기온 보정 필드는 계산하거나 응답하지 않는다.

## 2. 기상청 산식

[기상청 기상자료개방포털 체감온도 설명](https://data.kma.go.kr/climate/windChill/selectWindChillChart.do)에 따라 계절을 구분한다.

- 여름철(5~9월): 기온과 상대습도에서 습구온도를 구한 뒤 기상청 여름철 체감온도 산식을 적용한다.
- 겨울철(10~익년 4월): 기온이 10℃ 이하이고 풍속이 1.3m/s 이상일 때 기상청 풍속냉각 산식을 적용한다.
- 계절별 필수 입력이나 적용 조건이 충족되지 않으면 체감온도를 임의로 만들지 않고 자료 없음으로 둔다.
- 결과는 소수점 첫째 자리로 반올림한다.

현재값은 APIHub 10분 격자 실황의 같은 발표시각 `T1H/REH/WSD`를 우선 사용한다. 핵심 필드가 빠졌거나 격자 자료가 지연되면 최근접 AWS의 같은 지점·시각 `TA/HM/WS` 세트 전체로 전환한다. 서로 다른 관측원의 값을 섞지 않는다.

미래값은 기상청 단기예보의 같은 예보시각 `TMP/REH/WSD`를 사용한다. 관측 체감온도와 예보 체감온도는 입력 시각과 자료 역할이 다르므로 화면에서 각각 현재·예상으로 구분한다.

## 3. 화면 표현

- Main, Detail, 시간별 예보, 홈 위젯은 `kmaApparentTemperature`를 우선 표시하고 구버전 응답에서는 `apparentTemperature`를 사용한다.
- 상세 설명에는 여름철은 기온·상대습도, 겨울철은 기온·풍속을 사용한 기상청 방식임을 명시한다.
- 실제 기온과의 차이는 표시된 기상청 체감온도에서 실제 기온을 뺀 값으로만 설명한다.
- 자체 감각 등급이나 사람 중심 체감 문구를 만들지 않는다.
- 더위·추위 브리핑의 장면 선택은 기상청 체감온도와 기존 행동 임계값을 사용하며 공식 특보 발효를 뜻하는 표현은 쓰지 않는다.

## 4. 결측·신선도 원칙

- 필수 입력이 없으면 0으로 대체하거나 실제 기온을 체감온도로 복사하지 않는다.
- 격자 실황은 20분이 넘으면 `SOURCE_DELAYED`, 30분이 넘으면 현재값으로 사용하지 않는다. AWS에도 같은 30분 제한을 적용한다.
- 두 관측원이 모두 없으면 단기예보 `TMP`를 현재 실제기온이나 현재 체감온도로 대신 사용하지 않는다.
- `apparentTemperatureSource`와 `apparentTemperatureFormulaVersion`으로 관측·예보 계산 출처와 산식 버전을 추적한다.

## 5. 적용 한계

- 기상청 날씨누리와 앱의 관측 시각·격자·자료 갱신 시점이 다르면 잠시 값이 다를 수 있다.
- 햇볕, 복사열, 활동량, 의복, 개인의 최근 기온 적응은 숫자에 추가하지 않는다.
- 개인이 실제로 느끼는 정도와 기상청 방식 체감온도는 다를 수 있으나, 앱은 비교 가능성과 일관성을 위해 기상청 방식 값만 제공한다.
