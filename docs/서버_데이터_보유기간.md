# 서버 데이터 보유기간

2026-09-11 사용자가 장기 미사용 설치 정보와 알림 발송 이력의 기간을 **1년**으로 확정했다. 앱 서버의 해당 데이터에 대한 운영 기준이며 법정 의무 보유기간을 주장하거나 정식 개인정보처리방침을 대신하지 않는다.

## 확정 기준

| 대상 | 기준 시점 | 정리 |
| --- | --- | --- |
| 설치 등록·위치·FCM 토큰·설정·발송 상태·인증 정보 | 서버가 마지막으로 확인한 인증된 앱 요청 | 사용이 확인되지 않은 채 1년이 지나면 관련 이력과 함께 삭제 |
| 알림 발송 이력 | 각 행의 실제 `sent_at` | 발송 후 1년이 지나면 삭제. 대상 날짜 `target_date`와 무관 |
| 사용자 직접 삭제 | 본인 확인된 삭제 요청 | 위 기간을 기다리지 않고 해당 설치의 관련 데이터 삭제 |

1년은 한국 시간의 다음 해 같은 날짜·시각까지로 계산한다. 2월 29일은 다음 해 2월 28일 같은 시각으로 계산한다. 365일 고정 간격과 구분하며 경계 시각에 도달하면 정리 대상이다. 정리 전에 인증된 사용이 다시 확인되면 설치의 마지막 사용 시점을 갱신하지만, 과거 발송 이력의 보유기간은 늘리지 않는다.

인증된 날씨 조회·등록·설정 요청 등을 사용 확인으로 삼는다. 비인증 조회, 잘못된 인증값, 서버의 기상 수집·푸시 발송·발송 상태 갱신은 기간을 연장하지 않는다. 네트워크에 연결하지 않은 로컬 이용은 서버에서 확인할 수 없다.

## 기존 데이터 전환

이전 `installations.updated_at`에는 서버 알림 작업의 갱신도 섞여 있어 마지막 앱 사용 시각으로 사용할 수 없다. `0008_data_retention.sql` 적용 당시 존재하는 등록·설정·인증 정보는 **마이그레이션 시각**을 최초 기준으로 삼는다. 이후 인증된 앱 요청부터 실제 확인 시각을 별도로 기록한다. 과거 사용 시각을 추측하거나 오래된 생성 시각만으로 기존 설치를 즉시 삭제하지 않는다.

발송 이력에는 실제 발송 시각이 이미 있으므로 기존 행도 각 `sent_at`부터 계산한다. 시각이 손상돼 해석할 수 없는 행은 추측해 지우지 않고 운영 점검 대상으로 남긴다.

## 자동 정리와 경합

- 기존 10분 주기 Cron에서 알림 처리 전에 실행한다. 지연된 이벤트의 예정 시각 대신 실제 실행 시각을 쓴다.
- 실행당 오래된 설치 최대 100개와 그 관련 행, 추가로 기한이 지난 발송 이력 최대 1,000개를 정리한다. 남은 대상은 다음 실행에서 계속 처리한다. 장애·작업 적체 시 삭제가 지연될 수 있으므로 만료 순간의 즉시 삭제를 약속하지 않는다.
- 활동 기준 행과 관련 데이터 삭제를 DB 트리거·D1 batch 트랜잭션으로 묶었다. 중간 실패는 전체 롤백하며 다음 실행에 재시도한다. 현재 사용 확인과 정리가 겹쳐도 일부 테이블만 삭제하거나 삭제된 식별자가 재생성되지 않도록 SQL 조건을 둔다.
- 스케줄러는 정리 대기 중이어도 보유기간이 지난 설치를 발송 대상에서 제외하고 발송 직전 재확인한다. 이미 외부로 전송 중인 알림은 취소를 보장하지 않는다.
- 운영 결과 로그에는 설치 삭제 수·발송 이력 삭제 수만 남긴다. 이 기능이 별도의 사용자 식별자·위치·토큰 목록이나 영구 삭제표식을 추가하지는 않는다.
- 인증 준비정보 15분·소유권 증명 5분의 기존 기술적 만료는 1년으로 늘리지 않는다.

## 앱에서 다시 이용할 때

등록/설정 요청이 인증 오류를 반환하면 앱은 기존 설치의 상태를 확인한다. 서버가 등록정보 부재를 확인한 경우에만 전송 중지 상태를 기기에 저장한다. 오류·시간초과·다른 인증값을 삭제 완료로 해석하지 않는다. 실제 부재 사유를 식별할 수 없으므로 '1년이 지나 삭제됐다'고 단정하지 않는다.

Setting에는 `서버에 이 설치의 등록정보가 없어요`라고 안내한다. `서버 기능 다시 사용`을 별도로 확인한 뒤 새 ID로 등록한다. 알림은 자동으로 켜지지 않는다. 기기의 지역·체크 기록은 보존한다. 상태 저장 실패 시에도 현재 실행의 자동 전송은 차단하며, 재시작 후 서버 상태를 다시 확인한다.

## 별도 미확정 범위

운영 로그, Cloudflare 백업/복원, Firebase·광고 서비스의 보관·권리 행사, 수동 본인 확인 및 정식 방침 공개는 별도다. 이번 1년 결정을 해당 서비스나 모든 저장소에 일괄 적용하지 않는다. 백업 복원으로 과거 데이터를 되살리지 않는 운영 절차도 다음 항목에서 확인해야 한다.

구현 근거: [D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/), [SQLite 날짜의 연도 이동·floor 처리](https://www.sqlite.org/lang_datefunc.html). 사용자에게 보여 주는 안내는 `SettingsGuide.dataUse`에 반영한다.

## 적용·검증 기록

- 운영 D1 `0008_data_retention.sql` 적용 및 Worker `9588e04b-ec80-46a5-a718-95fc19f84435` 배포 완료. 현재 10분 주기에 연결했다.
- 전체 서버 31개 파일·240개 테스트, 전체 앱 314개 테스트, 서버 타입 검사·배포 사전 검사, Flutter 정적 분석·Android x86_64 debug 빌드 통과.
- 기한 직전/경계, 한국 시간·윤년, 발송 시각·문자열 표기 차이, 활동 재확인/늦은 요청, 일괄 삭제 롤백/재시도, 정리 배치 제한, 지연 Cron의 발송 차단, 등록 부재와 인증 실패 구분, 기기 저장 실패/재시작을 검증했다.
- 운영에서는 새 합성 설치만 생성해 상태 확인·삭제·재시도·재등록 거부를 검증하고 제거했다. 실제 사용자 설치·설정·발송 이력은 각각 1행 유지, 추가된 활동 기준 1행, 기한이 지난 설치/이력 0행을 확인했다. 실제 사용자 정보를 시험 삭제하지 않았다.
- 에뮬레이터에 기존 데이터를 유지한 채 업데이트하고 보유기간 안내 화면을 확인했다. 초기 서버 저장 미확인 표시는 값 변경 없이 기존 설정 저장을 다시 시도해 정상 반영을 확인했다. 이때 마지막 앱 활동 시각 갱신도 확인했다. 테스트용 알림·메일 발송 없음. iOS 빌드·실기기 미검증.
- `0008`의 활동 행 삭제 트리거는 관련 설치 데이터까지 삭제한다. 활동 테이블을 단순 로그처럼 비우지 말 것. 이전 Worker로 롤백하면 자동 정리·활동 갱신이 중단되므로 롤백 시 운영 기준을 별도 검토한다.
