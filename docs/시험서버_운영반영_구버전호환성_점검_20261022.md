# 시험 서버 운영 반영 시 기존 앱 호환성 점검

2026-10-22 한국시간 기준. 실제 운영·시험 릴리스와 DB 마이그레이션 목록을 읽고, 내부 API 응답 및 Git의 과거 앱 코드를 대조했다. 서버 배포나 운영 설정 변경은 수행하지 않았다.

## 결론

현재 시험 서버를 그대로 운영에 적용하면 일부 구버전 앱의 표시와 알림 동작에 문제가 생길 수 있다. 서버 코드에 하위 호환 처리를 보완하고 운영 DB·주소·인증 설정을 유지하는 배포가 필요하다. 기본 API가 HTTP 200이라는 사실만으로 구버전 화면 호환성을 보장할 수 없다.

## 실제 배포 상태

| 항목 | 운영 | 시험 |
| --- | --- | --- |
| 릴리스 | `20261012-juso-202609` | `20261021-test-station-official-gis` |
| 안정 경로 | `/opt/weather-care/weather_care_server` | `/opt/weather-care/weather_care_test_server` |
| DB | `/var/lib/weather-care/weather-care-release.sqlite` | `/var/lib/weather-care/weather-care-test.sqlite` |
| 적용된 마이그레이션 | 0001~0014 | 0001~0017 |
| API 서비스 | active | active |

운영 스케줄러도 active였다. 운영 환경에는 `TEST_ACCESS_KEY`가 설정되어 있지 않았다. 두 릴리스의 package-lock.json은 다르므로 새 코드 배포 시 기존 node_modules를 그대로 재사용해도 된다고 가정하지 않는다.

## 확인한 영향

1. **기존 미래 예보 표시 누락**
   - 같은 서울 격자 요청의 `/api/v1/weather/main`, `/today`에 운영은 `nextForecast`를 반환하지만 시험은 반환하지 않는다.
   - Git의 `13ee2af`와 `72fbd9e` 앱 모델은 이를 읽으며, `72fbd9e`의 Main 미래 예상 날씨 카드는 해당 값으로 기온·체감·습도·바람·자외선 등을 표시한다. 값이 없으면 null로 파싱되므로 이 경로에서 즉시 파싱 예외가 발생하는 구조는 아니지만 표시가 결측 상태로 바뀐다. 앱에서 만든 위젯 스냅샷도 이 값에 의존한다.
   - 이 계약을 사용하는 배포 앱을 위해 서버의 `nextForecast` 필드를 유지하는 것이 필요하다. 모든 설치 앱의 실제 빌드와 위 두 커밋의 일치 여부는 확인하지 않았다.

2. **낙뢰 알림이 기존 사용자에게도 활성화될 수 있음**
   - `0016_lightning_alerts.sql`은 `lightning_enabled`를 `NOT NULL DEFAULT 1`로 추가한다.
   - 시험 서버의 스케줄러에는 10분 간격 낙뢰 수집·전송 작업이 추가되어 있다. 기존 설치의 전체 알림이 켜져 있고 유효한 FCM 토큰·연령 확인·인근 관측 등 조건이 맞으면 새 알림 대상이 될 수 있다.
   - `72fbd9e` 앱은 `LIGHTNING` 주제를 알지 못해 unknown으로 분류하며, 해당 버전에는 낙뢰 전용 끄기 설정이 없다. 기존 전체 알림 설정은 서버가 계속 따른다.
   - 운영 반영 전에 기존 앱 대상의 새 알림 활성화 정책과 구버전의 알림 이동 동작을 확인해야 한다.

3. **시험 설정·DB를 함께 복사할 때의 접속 및 사용자 데이터 문제**
   - 시험 코드는 `TEST_ACCESS_KEY`가 있으면 키 없는 요청을 HTTP 403으로 거부한다. 운영에는 이 변수를 아예 설정하지 않아야 한다. 빈 문자열을 지정하면 현재 검증 코드에서 서버 기동이 실패한다.
   - 시험 DB는 운영 사용자 설치·인증·설정·이력을 보존하기 위한 교체본이 아니다. 운영 주소와 기존 운영 DB·인증·FCM 환경은 유지하고, 운영 DB 백업 후 미적용 0015~0017을 적용해야 한다.
   - 코드가 새 스키마에 의존하므로 마이그레이션 없이 코드만 바꾸면 DB 조회 오류가 발생할 수 있다. Node 시작 시 자동 마이그레이션이 있으므로 백업·적용·기동 순서까지 배포에 포함해야 한다.

4. **위젯의 새 준비물 종류**
   - 일반 Today/Weekly 추천은 `recommendationCatalog`로 기존 15종과 새 18종 경로를 구분한다.
   - `/widget`은 요청과 무관하게 새 18종 경로를 사용하도록 변경되었으며, `schemaVersion`은 양쪽 모두 3이다. 구버전 네이티브 위젯의 새 종류 표시까지 호환된다고 단정할 수 없으므로 별도 확인이나 구버전용 변환이 필요하다.

## 점검 범위와 배포 전 조치

- 운영과 시험에서 Main·Today·Weekly·Widget 총 8개 요청이 모두 HTTP 200이었다. Widget 버전 확인 2개 요청도 성공했다. 서울 표본의 기존 필드 누락을 재귀 비교했으며 `nextForecast`와 일부 브리핑 예보 시각 필드가 없음을 확인했다. 브리핑 시각 필드는 장면에 따라 선택적일 수 있어 별도 장애로 확정하지 않았다.
- 사용자 설치 등록·설정 변경 요청, 실제 푸시, 구버전 APK/IPA 실행, 전체 지역·계절·예외 상황 검증은 하지 않았다. Weekly 표본의 형태 일치도 전체 상태에 대한 보장은 아니다.
- 우선 `nextForecast` 응답 보존, 구버전 대상 낙뢰 알림 정책, 위젯 준비물 호환을 정리한다. 이어 운영 DB 복사본에 마이그레이션과 신서버를 적용하고 실제 배포 앱으로 날씨·설정 저장·위젯·알림 이동을 검증한 뒤 전환한다.
- 서버 재시작·선수집 중 잠깐 응답이 지연되거나 실패할 가능성도 있으므로 기존 서비스의 기동 조건을 반영한 전환과 복구 경로가 필요하다.
- 10월 22일 로컬의 준비물 판단 근거 변경은 현재 시험 릴리스에도 아직 배포되지 않았다. 현재 시험 서버 승격과 로컬 최신 코드 배포는 서로 다른 범위다.
