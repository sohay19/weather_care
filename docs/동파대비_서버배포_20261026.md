## 마이그레이션

시험→운영 순서로 각 사용자 DB를 SQLite 온라인 백업하고 트랜잭션 안에서 `pipe_freeze_enabled INTEGER NOT NULL DEFAULT 0`을 추가했다. `d1_migrations`에 `0002_pipe_freeze_alert.sql` 적용을 기록했다. 통합/D1용 `0019`는 적용하지 않았다.

- 운영 사용자 DB: `/var/lib/weather-care/weather-care-users-production.sqlite`
- 시험 사용자 DB: `/var/lib/weather-care/weather-care-users-test.sqlite`
- 마이그레이션 전후 기존 모든 사용자 테이블의 행 수와 기존 열의 전체 내용 해시가 같음을 동일 트랜잭션에서 확인했다. 설치·인증·FCM 토큰·알림 설정·발송 이력을 보존했다.
- 신규 설정은 기존 189건/31건 모두 OFF다. 기존 앱이 필드를 생략하는 부분 갱신에도 기존 선택을 유지한다.
- SQLite `quick_check=ok`, 외래키 무결성을 확인했다. 재실행 시 적용 이력으로 중복 마이그레이션을 건너뛴다.
- 공용 날씨 DB `/var/lib/weather-care/weather-care-weather.sqlite`의 스키마와 모든 환경/수집 설정 파일의 해시는 그대로다. DB 경로·서비스 정의·패키지·터널 설정은 변경하지 않았다.

## 반영된 동작

Today에 `pipeFreeze` 판단과 `PIPE_FREEZE_GUIDANCE` 생활 안내를 추가했다. 현재 정시부터 48시간의 유효 기온 예보로 앱의 참고 단계를 판단하고, 자료 부족을 낮은 위험으로 만들지 않는다. 기존 기온 캐시만 사용하며 추가 외부 API를 호출하지 않는다. 공식 동파 예보·도로살얼음 판단과 구분한다.

전체/개별 알림이 ON이고 완전한 예보가 주의 이상일 때 설치별 현지 날짜당 한 번 안내한다. 기존 설치는 OFF이므로 이번 배포로 자동 동파 알림을 켜지 않는다. 수동 푸시·실제 사용자 설정 변경은 하지 않았다. 운영 스케줄러의 정상 시작 절차와 기존 정기 작업은 유지한다.

동파 업데이트 전 앱 소스(`4c3b268`)의 모델에 실제 운영 Today JSON을 입력한 호환 검사1개를 통과했다. 기존 앱은 새 생활 항목을 일반 날씨 안내로 읽고 근거 문구를 보존한다. 새 앱은 전용 이름/아이콘, 알림 스위치와 근거 자동 펼치기를 제공한다. 실제 설치 바이너리·모든 과거 버전을 검증했다는 의미는 아니다.

## 백업·복구 및 기록

원본 소스와 사용자 DB 백업은 `/var/backups/weather-care/pipe-freeze-20261026T014913Z/{production,test}`에 있다. 사용자 DB 파일명은 `users-before.sqlite`이며 백업 디렉터리0700/DB0600으로 제한했다. 백업은 서버에만 보존하고 로컬이나 저장소로 내려받지 않았다.

배포 잠금·적용 직전 소스/DB 스키마 대조·파일별 원자 교체·기존 소유권/권한 유지·실패 시 소스 복원 절차를 준비했다. 추가 열은 이전 코드와 호환되므로 코드 복원 시 DB 전체를 덮어써 이후 사용자 변경을 잃지 않도록 한다. 이번 최종 배포에서는 복원을 실행하지 않았다.

첫 시도의 배포 전 검사에서 구형 Today에도 PREPARATION_18 전용 선택 필드를 필수로 요구해 중단했다. DB/소스/서비스 변경 전이었으며 검증 조건을 해당 카탈로그에만 적용하도록 정정한 뒤 완료했다. 같은 임시 디렉터리의 `inspect.py` 이름이 Python 표준 모듈과 겹쳐 오류 출력 과정에 영향을 준 것도 `capture_state.py`로 바꿨다. 초기 합성 런타임 검사의 소유권 없는 설치 시험 자료는 메모리DB에서만 거부됐으며 합성 인증 행을 추가해 재검증했다. 제품 인증 규칙은 변경하지 않았다.
