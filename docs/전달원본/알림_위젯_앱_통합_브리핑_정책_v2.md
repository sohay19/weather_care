## 0. 문서 우선순위와 절대 원칙

이 문서는 위 두 최종 문서를 **변경하지 않고 그대로 사용**한다.

정책이 겹칠 때 우선순위는 다음과 같다.

```text
1. 데이터의 시각·위치·원본·freshness
   -> 날씨 항목별 데이터 출처·API 및 운영 수집 정책

2. 기온·체감온도 계산과 열감각 표현
   -> 한국형 체감온도 v2 설계안

3. 그 결과를 앱·위젯·알림에서 어떤 장면과 문장으로 보여줄지
   -> 본 통합 브리핑 정책
```

본 문서가 상위 두 문서와 충돌하는 방식으로 데이터를 다시 해석하거나 체감온도를 다시 계산해서는 안 된다.

### 0.1 `현재`의 절대 원칙

`현재`, `지금`, `실시간`이라고 표현하는 값은 상위 데이터 정책을 그대로 따른다.

```text
정확한 nx/ny의 최신 APIHub 10분 격자 실황
    ↓ 결측/공급 지연
선택 위치에서 가장 가까운 유효 AWS 관측
    ↓ 사용할 수 없음
OBSERVATION_UNAVAILABLE
```

- 현재 기온은 `T1H`
- 현재 습도는 `REH`
- 현재 풍속은 `WSD`
- 현재 풍향은 `VEC`
- 현재 강수는 `PTY/RN1`
- 현재 체감온도는 가능한 한 동일 `observedAt`·동일 source set의 `T1H+REH+WSD`로 계산한다.
- 단기예보 `TMP`를 현재 기온처럼 조용히 사용하지 않는다.
- 관측이 아닌 값을 현재 문맥에서 보조로 사용할 때는 `FORECAST_PROXY`, `FORECAST_CURRENT_SLOT`, `NOWCAST_FALLBACK` 등을 유지한다.

### 0.2 `미래`·`예상`의 절대 원칙

미래를 설명하는 문장에는 **그 대상 시각의 예보값**을 사용한다.

```text
"오후 4시에는 27℃예요"
-> forecastAt = 오늘 16:00의 TMP

"밤부터 비가 와요"
-> 해당 미래 구간의 PTY/POP/PCP

"내일 낮 자외선이 강해요"
-> 내일 낮에 대응하는 UV 제공 슬롯
```

- 모든 시간별 값은 같은 `forecastAt`을 사용한다.
- 같은 대상 시각이면 가능한 한 동일 forecast bundle / 동일 `issuedAt`을 사용한다.
- 현재 관측값을 미래값으로 복사하지 않는다.
- 이미 지난 예보 슬롯을 `현재`처럼 표현하지 않는다.

### 0.3 위치의 절대 원칙

브리핑도 반드시 요청한 `LocationContext`를 따른다.

```text
Grid identity
  = nx/ny

Region identity
  = adminCode
  + sido
  + sigungu
  + eupMyeonDong
  + midTermLandRegId
  + midTermTaRegId
```

- 격자형 자료는 정확한 `nx/ny`
- 관측소형 자료는 실제 GPS 또는 격자 대표점에서 가장 가까운 유효 관측소
- 중기예보는 `nx/ny`만으로 추측하지 않고 Region identity로 판정
- 브리핑이 사용하는 데이터와 화면에 표시된 지역은 동일한 LocationContext를 가져야 한다.
- 지역이 바뀌면 브리핑 scene도 새 LocationContext에서 다시 선택한다.

# 1. 용어

코드와 기획에서 `brief`, `message`, `title`, `description`, `stateLabel`을 뒤섞지 않는다.

| 용어 | 의미 | 예 |
|---|---|---|
| **브리핑 scene** | 사용자가 지금 알아야 할 하나의 핵심 날씨 상황 | `RAIN`, `UV`, `THERMAL`, `AIR_QUALITY` |
| **브리핑 의미(intent)** | 시간·근거·행동까지 포함한 구조화된 의미 | `오늘 15~17시 비 / 우산 필요` |
| **짧은 브리핑** | 위젯 등 공간이 작은 곳에서 intent를 압축한 한 문장 | `오후 비, 우산 챙기세요.` |
| **기본 브리핑** | 앱 상단·중간 위젯 등에서 쓰는 자연스러운 대표 문장 | `오후 3시부터 비가 올 수 있어요. 우산을 챙기세요.` |
| **긴 브리핑** | 큰 위젯·Detail 등에서 이유나 시간 정보를 조금 더 포함 | `오후 3~5시 비 가능성이 높아요. 외출한다면 우산을 챙기는 게 좋아요.` |
| **체감 표현** | `perceivedTemperature`와 `thermalSensation`을 자연어로 표현 | `선선하고 쾌적해요.` |
| **행동 안내** | 날씨 상황에 따른 행동 제안 | `우산을 챙기세요.` |
| **준비물 추천** | 구조화된 물건 추천 | 우산, 선크림, 겉옷 |
| **근거 문장** | 브리핑 판단의 공식·관측·예보 근거 | `오후 4시 강수확률은 70%예요.` |
| **알림 문구** | 푸시 title/body로 렌더링된 브리핑 | `오후 비 소식` + 본문 |
| **유효기간** | 해당 scene을 사용자에게 보여줘도 되는 시간 범위 | `validFrom`, `validUntil` |

앞으로 기획상 대표 용어는 **브리핑**으로 통일한다.  
`멘트`, `문구`, `표현`은 브리핑을 실제 한국어 문장으로 렌더링한 결과를 가리킬 때만 사용한다.

# 2. 현행 구조의 핵심 문제

기존 구현은 하나의 통합 브리핑 시스템이 아니다.

```text
서버 weatherBrief
앱 Main 자체 체감 문장
추천 문장
Detail 생활 문장
위젯 shortMessage
아침 알림 조합기
사건형 알림 조합기
```

가 서로 독립적으로 존재한다.

그 결과 다음 문제가 발생한다.

1. 같은 시각에 앱과 위젯이 다른 날씨를 대표 메시지로 말할 수 있다.
2. 중간 위젯은 우산을 말하고 큰 위젯은 자외선을 말하는 식으로 의미가 달라질 수 있다.
3. 낮에 생성한 자외선 브리핑이 앱이 다시 열리지 않으면 저녁 위젯에 남을 수 있다.
4. Main에서 끝난 비를 숨겨도 위젯에는 이전 비 문장이 남을 수 있다.
5. 체감온도 표현 기준이 앱과 서버에 중복돼 화면별로 달라질 수 있다.
6. 긴 문장을 단순히 글자 수로 자르면 한국어가 어색해진다.
7. 알림 본문의 마침표 뒤를 기계적으로 줄바꿈하면 자연스러운 문단이 깨질 수 있다.

v2에서는 **문장을 공유하는 것이 아니라 구조화된 의미를 공유하고, 각 채널이 같은 의미를 길이만 다르게 렌더링**한다.

# 3. 최종 통합 구조

```text
[상위 데이터 정책]
  현재 관측 / 미래 예보 / 위치 / freshness
                │
                ▼
[체감온도 v2]
  perceivedTemperature
  thermalSensation
  dominantFactors
  estimatedClothing
                │
                ▼
[Fact Layer]
  현재 사실 + 미래 사건 + 공식 특보 + 생활 조건
                │
                ▼
[Scene Candidate Builder]
  RAIN / SNOW / UV / THERMAL / AIR_QUALITY / WIND ...
                │
                ▼
[Time Relevance Filter]
  지금 이 scene을 보여줘도 되는가?
                │
                ▼
[Priority / Importance Ranker]
  현재 사용자에게 가장 중요한 것은 무엇인가?
                │
                ▼
[Canonical Briefing Intent]
  sceneId / topic / time / evidence / action / validity
                │
        ┌───────┼────────┬──────────┐
        ▼       ▼        ▼          ▼
      앱      위젯     아침알림   사건형알림
   LONG/MED   SHORT      SUMMARY      EVENT
```

**핵심:** 앱·위젯·알림이 각각 다시 날씨를 판단하지 않는다.

# 4. Canonical Briefing Intent

하나의 대표 브리핑은 완성 문장 하나가 아니라 아래 구조로 저장한다.

```text
BriefingIntent {
  briefingId
  locationKey
  sceneId
  topic
  scope                 // CURRENT | NEAR_FUTURE | TODAY | TOMORROW | EVENT
  severity
  confidence

  targetFrom
  targetUntil
  validFrom
  validUntil

  dataRole
  observedAt
  forecastAt
  issuedAt
  sourceLocation
  qualityFlags

  headlineFact
  supportingFact
  dominantFactor
  action
  recommendedItems[]

  thermalSensation
  perceivedTemperature
  officialWeatherAdvisory

  copyVariantKey
}
```

### 4.1 `target`과 `valid`는 다르다

예:

```text
오후 15~17시 비 예보

targetFrom  = 15:00
targetUntil = 17:00

아침부터 우산 준비를 알려줄 수 있다면
validFrom   = 07:00

비가 완전히 끝난 뒤에는 더 이상 대표 브리핑이 아니므로
validUntil  = 17:10 또는 공식적으로 정한 종료 여유시각
```

`targetFrom/targetUntil`은 **날씨가 실제로 해당되는 시각**,  
`validFrom/validUntil`은 **그 정보를 사용자에게 보여줘도 유용한 시각**이다.

### 4.2 scene별 원본 추적

모든 브리핑은 최소 다음을 추적할 수 있어야 한다.

```text
dataRole
observedAt / forecastAt
sourceLocation
qualityFlags
evidenceFields[]
```

브리핑 문장만 DB에 저장하고 원본 시각을 잃어버리는 구조는 사용하지 않는다.

# 5. 브리핑 scene 목록

권장 scene은 다음과 같다.

```text
OFFICIAL_WARNING
CURRENT_PRECIPITATION
HEAVY_RAIN
SNOW
ROAD_ICE
ROAD_CONTROL

RAIN
UV
AIR_QUALITY
OZONE
VISIBILITY

THERMAL_HOT
THERMAL_COLD
THERMAL_COMFORTABLE
THERMAL_CHANGE

WIND
HUMIDITY_HIGH
HUMIDITY_LOW

CLEAR_COMFORTABLE
DEFAULT
```

### 5.1 안전/사건형 scene

다음은 일반 생활 브리핑보다 우선순위가 높다.

- 발효 중인 공식 특보
- 현재 강수 중 중요한 변화
- 대설
- 도로살얼음
- 도로 통제
- 건강상 의미가 큰 폭염/한파 위험

단, **공식 위험과 일상적인 체감 표현은 같은 값으로 합치지 않는다.**

예:

```text
체감:
"습하고 많이 덥게 느껴져요."

공식 위험:
"폭염주의보가 발효 중이에요."
```

# 6. 브리핑 선택은 고정 순번이 아니라 `유효성 → 중요도` 순서

기존처럼 항상 `눈 > 비 > 시야 > 대기질 > 자외선 ...` 첫 항목만 고르는 방식은 완화한다.

먼저 **현재 시각에 유효하지 않은 scene을 모두 제거**하고, 남은 후보에서 중요도를 계산한다.

권장 개념:

```text
importanceScore
  = severity
  + immediacy
  + actionability
  + confidence
  + userImpact
  - repetitionPenalty
```

정확한 점수는 제품용 설정값으로 관리한다.

### 6.1 반드시 먼저 제거할 후보

아래 후보는 중요도 계산에 들어가기 전에 탈락한다.

- `validUntil <= now`
- 사용자가 보고 있는 지역과 LocationContext가 다름
- source가 freshness 기준을 초과함
- 이미 끝난 미래 사건
- 현재 시간에 성립할 수 없는 생활 조건
- 필요한 핵심 데이터가 `UNAVAILABLE`
- 공식 해제된 특보

# 7. 시간 적합성 정책

이 항목이 v2 브리핑의 핵심이다.

**현재 시간을 기준으로 의미가 없어진 브리핑은 다음 데이터 네트워크 갱신을 기다리지 않고 제거한다.**

## 7.1 자외선

자외선 scene은 다음 조건을 모두 만족할 때만 현재 대표 브리핑 후보가 될 수 있다.

```text
1. 현재가 일출 이후 / 일몰 이전
2. 태양고도 > 0
3. 현재 또는 앞으로 남은 낮 시간에 대응하는 UV 슬롯이 존재
4. UV 값이 브리핑 임계값 이상
5. UV 데이터가 해당 날짜/지역에 유효
```

다음이면 즉시 후보에서 제거한다.

```text
now >= sunset
또는
sunElevation <= 0
또는
UV target interval 종료
```

따라서:

```text
16:00
"자외선이 강해요. 햇볕 차단에 신경 쓰세요."

19:30, 일몰 이후
자외선 scene 제거
        ↓
다음 유효 후보 재선택
        ↓
"저녁에는 선선하고 쾌적해요."
또는
"밤부터 바람이 강해질 수 있어요."
```

**낮에 받은 UV 3시간 슬롯이 캐시에 남아 있다는 이유로 밤에 자외선 브리핑을 유지하면 안 된다.**

## 7.2 햇볕/복사열 체감

체감온도 v2에서 강한 햇볕이 `dominantFactor`였더라도 일몰 이후에는:

- 현재 체감 계산을 최신 관측 기준으로 다시 사용
- 과거 낮의 `RADIATION` 원인을 현재 저녁 체감 원인으로 재사용하지 않음
- 문구에서 `햇볕 아래에서는` 표현 제거

## 7.3 비/눈

미래 강수 scene:

```text
validFrom = 사용자가 준비할 가치가 있는 사전 시각
validUntil = targetUntil + 짧은 종료 여유
```

- 예보 시작 전: `오후 4시부터 비가 올 수 있어요.`
- 진행 중이며 실황 확인됨: `지금 비가 내리고 있어요.`
- 종료 후: 비 scene 제거
- 비가 끝났지만 젖은 도로 영향이 남으면 `WET_ROAD` 또는 별도 생활 scene으로 전환

**끝난 비를 계속 `오늘 비가 와요`라고 표현하지 않는다.**

## 7.4 기온·체감온도

현재 체감 브리핑은 상위 체감온도 문서의 최신 `perceivedTemperature`를 사용한다.

- 최신 관측 source set이 갱신되면 scene 재평가
- 햇볕, 비, 풍속 등 dominant factor가 바뀌면 문구 재평가
- 0.1℃ 정도의 의미 없는 차이를 반복 언급하지 않음
- 쾌적한 구간은 적극적으로 `쾌적`, `편안`, `선선하고 편안`으로 표현

## 7.5 대기질·오존

- 최신 유효 측정 또는 대상 날짜 예보가 유효할 때만 후보 유지
- 오래된 측정값으로 `현재 미세먼지가 나빠요`라고 말하지 않음
- 오존은 햇볕과 동일한 개념이 아니므로 일몰됐다는 이유만으로 실제 현재 관측 오존 scene을 임의 삭제하지 않는다.
- 다만 행동 안내는 현재 생활 맥락에 맞게 조정한다.

## 7.6 가시거리

현재 시정 관측 freshness를 통과할 때만 `현재 시야`로 표현한다.

```text
낮:
"시야가 탁해 먼 곳이 잘 보이지 않아요."

밤:
"시야가 좋지 않아요. 운전할 때 주변을 더 살펴주세요."
```

같은 수치라도 시간대에 맞춰 행동 문맥을 자연스럽게 바꿀 수 있다.

## 7.7 준비물

준비물은 parent scene의 유효시간을 따른다.

예:

```text
UV scene 만료
-> 선크림/양산을 현재 대표 준비물에서 제거

RAIN scene 종료
-> 우산을 현재 대표 준비물에서 제거
   단, 앞으로 다시 비가 예정되어 있으면 해당 미래 scene 기준으로 유지 가능
```

Check List에 하루 전체 추천을 남기는 것과 **현재 대표 브리핑에 노출하는 것**은 별개로 관리한다.

# 8. 시간 경계에서 자동 교체

서버에서 새 데이터가 오지 않아도 다음 경계에서는 브리핑을 다시 선택해야 한다.

```text
validFrom
validUntil
targetFrom
targetUntil
sunrise
sunset
UV daylight 종료
공식 특보 발효/종료 시각
다음 예보 사건 시작/종료
현재 source staleAt
```

다음 시각을 계산한다.

```text
nextBriefingBoundary
  = 가장 가까운 미래의
    validFrom / validUntil / sunrise / sunset /
    event start / event end / staleAt 중 최소값
```

`nextBriefingBoundary`가 지나면 **네트워크 호출 여부와 상관없이 scene eligibility를 다시 평가**한다.

# 9. 위젯 정책 — 짧아도 길어도 같은 맥락

## 9.1 절대 원칙

같은 시각·같은 지역에서 위젯 크기가 달라도 아래 값은 같아야 한다.

```text
briefingId
sceneId
topic
targetFrom/targetUntil
action
recommendedItems의 핵심 목적
```

다른 것은 **문장 길이와 세부 설명량뿐**이다.

### 잘못된 예

```text
중간 위젯:
"선크림을 챙기세요."

큰 위젯:
"오후에 비가 와요. 우산을 챙기세요."
```

두 위젯이 서로 다른 primary scene을 선택했으므로 금지한다.

### 올바른 예

Canonical intent:

```text
sceneId = RAIN
target = 15:00~17:00
action = UMBRELLA
```

짧은 위젯:

```text
오후 비, 우산 챙기세요.
```

기본 위젯:

```text
오후 3시부터 비가 올 수 있어요. 우산을 챙기세요.
```

큰 위젯:

```text
오후 3~5시 비 가능성이 높아요. 외출한다면 우산을 챙기는 게 좋아요.
```

세 문장은 **길이는 다르지만 같은 사실·시간·행동**을 말한다.

## 9.2 단순 글자 자르기 금지

현재의:

```text
첫 문장 22자 초과
-> 21자 + ...
```

방식은 최종 방식으로 사용하지 않는다.

서버 또는 공통 renderer가 처음부터 다음 variant를 만든다.

```text
copy.short
copy.medium
copy.long
copy.notificationTitle
copy.notificationBody
```

`short`는 `long`을 자른 문자열이 아니다.

## 9.3 작은 위젯

작은 위젯이 현재처럼 브리핑을 표시하지 않는 것은 허용한다.

다만 향후 브리핑을 추가한다면 별도의 scene을 선택하지 않고 **현재 Canonical intent의 `short` variant**만 사용한다.

## 9.4 중간 위젯

기존처럼:

```text
준비물이 있으면 준비물 문장
없으면 서버 brief
```

로 primary 의미를 다시 고르지 않는다.

최종 방식:

```text
canonicalBriefing.copy.short
```

필요하면 준비물 아이콘을 별도로 보여주되, 문장 자체는 canonical scene의 맥락을 유지한다.

## 9.5 큰 위젯

```text
canonicalBriefing.copy.long
+ 같은 scene 또는 같은 snapshot의 준비물
+ 다음 날씨 정보
```

를 사용한다.

큰 위젯이 더 많은 내용을 보여줄 수는 있지만 **첫 대표 문장은 중간 위젯의 의미와 일치해야 한다.**

---

# 10. 위젯 시간 갱신과 stale 방지

현행의:

```text
Android 자체 주기 = 0
iOS timeline = .never
briefExpiresAt 미저장
```

상태는 시간 민감 브리핑에 적합하지 않다.

## 10.1 Widget Snapshot v2

위젯 스냅샷에 최소 다음을 저장한다.

```text
generatedAt
locationKey

briefingId
sceneId
validFrom
validUntil
nextBriefingBoundary

copy.short
copy.medium
copy.long

briefingTimeline[]
dataFreshUntil
```

### `briefingTimeline` 예

```text
[
  {
    14:00~18:50,
    scene: UV,
    short: "자외선이 강해요. 햇볕을 피하세요."
  },
  {
    18:50~22:00,
    scene: THERMAL_COMFORTABLE,
    short: "저녁에는 선선하고 편안해요."
  }
]
```

위젯이 네트워크를 다시 호출하지 않아도 시간에 맞는 entry를 선택할 수 있다.

## 10.2 Android

스냅샷 저장 시 `nextBriefingBoundary`에 맞춰 위젯 update를 예약한다.

구현 수단은 Android 버전과 배터리 정책을 고려해 결정하되 목표 동작은 다음과 같다.

```text
1. 현재 entry 표시
2. nextBriefingBoundary 도달
3. snapshot의 다음 유효 entry로 전환
4. 최신 서버 자료가 있으면 새 snapshot으로 교체
```

## 10.3 iOS WidgetKit

`.never` 고정 대신 **시간 경계가 포함된 Timeline entry**를 생성한다.

```text
UV entry       -> 일몰 전까지
Evening entry  -> 일몰 이후
Night entry    -> 야간 상황
```

마지막 entry 이후에는 정책에 맞는 `.after(...)` 또는 다음 timeline 요청을 사용한다.

## 10.4 OS가 갱신을 지연할 경우

렌더링 시에도 반드시:

```text
if now >= validUntil:
    현재 문장을 그대로 표시하지 않음
```

을 확인한다.

다음 timeline entry가 있으면 전환하고, 없고 data까지 stale하면:

```text
"최신 날씨를 확인해 주세요."
```

같은 중립 상태를 사용한다.

**만료된 자외선·비·눈·특보 행동 문장을 계속 보여주는 것보다 중립 문구가 낫다.**

# 11. 앱 브리핑 정책

## 11.1 Main 상단

앱 Main 상단은 Canonical Briefing Intent의 기본/긴 variant를 사용한다.

앱이 다시 임계값을 계산해 별도의 대표 scene을 만들지 않는다.

## 11.2 Main `지금 날씨`

체감 표현은 `한국형 체감온도 v2`의 다음 값을 그대로 사용한다.

```text
perceivedTemperature
thermalSensation
dominantFactors
perceivedDifference
estimatedClothingLabel
brief
```

Main이 별도로 `20~27.9℃ = 조금 덥게` 같은 기준을 다시 정의하지 않는다.

## 11.3 Detail

Detail은 대표 브리핑을 반복하는 곳이 아니라 근거를 확장하는 곳이다.

구조:

```text
[현재/예상 상태]
[사용자 영향]
[행동 안내]
[공식/계산 근거]
[자료의 시각·위치·상태]
```

## 11.4 Timeline

Timeline의 각 시간은 그 시간의 `forecastAt`에 해당하는 값으로 별도 local scene을 만들 수 있다.

단, 현재 대표 브리핑과 헷갈리지 않게 **시간 레이블을 항상 명시**한다.

예:

```text
15시
"비가 시작될 가능성이 높아요."

18시
"비가 그치고 바람이 약해져요."
```

## 11.5 Week

Week는 날짜별 장기 요약이므로 현재 브리핑의 scene을 그대로 복사하지 않는다.

- 단기 범위: 해당 날짜/시각 예보
- 이후: 중기예보의 정확한 `regId`와 날짜/오전·오후 범위
- 빈 날짜 카드가 생기지 않도록 상위 운영정책의 on-demand 중기 보강 사용

Week 문장이 필요하다면 `DAILY_SUMMARY` scope로 별도 생성한다.

# 12. 알림 정책

알림도 같은 Fact/Scene/Renderer를 사용하지만 **알림 목적**에 따라 selection scope가 다르다.

## 12.1 아침/설정시각 요약 알림

알림 발송 시각의 최신 snapshot에서 다시 생성한다.

오전에 보내는 알림은 오늘 오후의 상황을 말할 수 있다. 단, 미래라는 표현을 명확히 한다.

예:

```text
제목: 오늘 낮 자외선이 강해요
본문: 오후에는 자외선이 높을 것으로 보여요. 외출한다면 선크림이나 양산을 챙기세요.
```

저녁에 발송되는 요약이라면 이미 끝난 낮 UV를 넣지 않는다.

```text
잘못:
20:00 알림
"오늘 자외선이 강하니 선크림을 챙기세요."

올바름:
"밤에는 기온이 내려가 선선해요. 늦게 나간다면 가벼운 겉옷이 있으면 편해요."
```

## 12.2 사건형 알림

사건형 알림은 Main의 primary scene과 달라도 된다.

이유는 **새로운 중요 사건 자체가 알림의 목적**이기 때문이다.

예:

```text
Main primary: THERMAL_COMFORTABLE

15:20 새 강수 감지
-> CURRENT_PRECIPITATION 사건 알림 발송 가능
```

단, 같은 `CURRENT_PRECIPITATION` scene을 앱·위젯에서도 보여주는 순간에는 같은 사실·시각·행동 의미를 사용한다.

## 12.3 사건 종료 알림

해제/종료 문구는 과거 행동을 다시 권하지 않는다.

```text
"호우주의보가 해제됐어요."
"비는 대부분 그쳤어요. 젖은 도로는 미끄러울 수 있어요."
```

처럼 **종료된 사실 + 남아 있는 영향**만 설명한다.

## 12.4 알림 줄바꿈

FCM 전송 직전에 마침표 뒤 공백을 무조건 `\n`으로 변환하지 않는다.

알림 renderer가 처음부터 구조적으로 생성한다.

```text
title
bodyLine1
bodyLine2
bodyLine3
```

필요한 경우에만 줄바꿈을 넣는다.

# 13. 같은 scene의 길이별 브리핑 규칙

문장 길이는 달라도 아래 정보는 바뀌면 안 된다.

```text
무슨 날씨인지
현재인지 미래인지
언제인지
어떤 행동이 필요한지
```

## 13.1 비

Intent:

```text
scene = RAIN
scope = NEAR_FUTURE
target = 15~17시
action = UMBRELLA
```

Short:

```text
오후 비, 우산 챙기세요.
```

Medium:

```text
오후 3시부터 비가 올 수 있어요. 우산을 챙기세요.
```

Long:

```text
오후 3~5시 비 가능성이 높아요. 외출한다면 우산을 챙기는 게 좋아요.
```

## 13.2 자외선

Intent:

```text
scene = UV
scope = CURRENT/TODAY_DAYLIGHT
action = SUN_PROTECTION
```

Short:

```text
자외선이 강해요. 햇볕을 피하세요.
```

Medium:

```text
낮 동안 자외선이 강해요. 선크림이나 양산을 챙기세요.
```

Long:

```text
낮 동안 자외선이 강할 것으로 보여요. 오래 외출한다면 선크림이나 양산으로 햇볕을 막는 게 좋아요.
```

**일몰 이후 이 세 variant를 모두 동시에 만료한다.**

## 13.3 쾌적한 체감

Intent:

```text
scene = THERMAL_COMFORTABLE
thermalSensation = COMFORTABLE
```

Short:

```text
덥지도 춥지도 않아 쾌적해요.
```

Medium:

```text
기온과 체감 차이가 크지 않고, 덥지도 춥지도 않아 쾌적해요.
```

Long:

```text
기온과 체감 차이가 크지 않아요. 크게 덥거나 춥지 않아 활동하기 편안한 날씨예요.
```

# 14. 자연스러운 한국어 작성 규칙

## 14.1 기본 문체

기본 사용자 문장은 **해요체**로 통일한다.

```text
~예요 / ~해요 / ~있어요 / ~좋아요
```

한 브리핑 안에서:

```text
~합니다 + ~해요
```

를 섞지 않는다.

공식 특보명 자체는 원문 명칭을 유지할 수 있다.

## 14.2 한 문장에 너무 많은 사실을 넣지 않음

권장 최대 구조:

```text
[핵심 상태]
+ [가장 중요한 이유 또는 시간]
+ [필요한 경우 행동]
```

예:

```text
습도가 높아 후텁지근해요. 바람도 약해서 움직이면 더 덥게 느껴질 수 있어요.
```

다음처럼 모든 값을 늘어놓지 않는다.

```text
기온 29도, 습도 81%, 풍속 0.9m/s, 자외선 7이고 체감은 32도로 예상되므로...
```

수치는 근거 UI에서 제공한다.

## 14.3 숫자를 말해야 하는 경우

숫자는 사용자의 판단에 도움이 될 때만 브리핑에 넣는다.

권장:

```text
"오후 4시부터 비가 와요."
"체감은 기온보다 약 3℃ 높아요."
```

생략:

```text
"기온보다 0.1℃ 높아요."
```

체감 차이 표현은 체감온도 v2의 `0.6/1.5/3/5℃` 문구 정책을 따른다.

## 14.4 시간 표현

자연스러운 한국어로 변환한다.

```text
15:00 -> 오후 3시
15:00~17:00 -> 오후 3~5시 / 오후 3시부터 5시 사이
06:00 전후 -> 아침 6시 무렵
sunset 이후 -> 저녁 / 해가 진 뒤
심야 -> 밤늦게
```

피해야 할 표현:

```text
오후 15시
오늘 현재 지금
오후 3시부터 오후 5시까지 오후에
```

## 14.5 인과관계가 있을 때만 `때문에`

나쁜 예:

```text
자외선 때문에 기온이 2℃ 높아요.
```

UV는 전체 복사열과 동일하지 않으므로 금지한다.

좋은 예:

```text
햇볕이 강해 밖에서는 더 덥게 느껴질 수 있어요.
```

체감 원인은 체감온도 v2의 `dominantFactors`를 사용한다.

## 14.6 과도한 단정 금지

예보:

```text
"오후에 비가 올 가능성이 높아요."
"밤에는 바람이 강해질 수 있어요."
```

관측:

```text
"지금 비가 내리고 있어요."
```

예보값을 관측처럼:

```text
"지금 비가 옵니다."
```

라고 단정하지 않는다.

## 14.7 어색한 접속어 방지

다음처럼 논리 관계가 없는 `하지만`, `그런데`, `~지만`을 자동 삽입하지 않는다.

잘못:

```text
실제 기온보다 0.1℃ 높지만, 체감 상 조금 덥게 느껴질 수 있어요.
```

권장:

```text
따뜻하지만 크게 덥지 않아 쾌적해요.
```

또는:

```text
기온과 체감 차이는 거의 없어요.
```

## 14.8 같은 단어 반복 완화

잘못:

```text
비가 올 수 있어요. 비가 오니 우산을 챙기세요.
```

권장:

```text
오후에 비가 올 수 있어요. 외출한다면 우산을 챙기세요.
```

# 15. 문구 다양화

완전 랜덤은 사용하지 않는다.

같은 날씨가 새로고침할 때마다 다른 문장으로 보이면 상태가 바뀐 것처럼 느껴질 수 있다.

체감온도 문서와 동일하게 결정적 seed를 사용한다.

```text
locationKey
+ yyyyMMdd
+ timeContext
+ sceneId
+ thermalSensation
+ dominantFactor
```

단, 기존의 단순 `3시간 시간대`만으로는 일몰처럼 중요한 경계를 놓칠 수 있으므로 `timeContext`에는 다음을 포함한다.

```text
DAYLIGHT
EVENING
NIGHT
EVENT_BEFORE
EVENT_ACTIVE
EVENT_AFTER
```

같은 `briefingId`와 유효구간 안에서는 문장을 안정적으로 유지한다.

scene이 바뀌거나 유효구간이 바뀌면 새로운 문장을 선택할 수 있다.

# 16. 브리핑 유효성 메타데이터

서버 응답 권장 구조:

```json
{
  "briefing": {
    "briefingId": "57-125:20260922:RAIN:1500-1700",
    "sceneId": "RAIN",
    "scope": "NEAR_FUTURE",
    "severity": "MODERATE",
    "confidence": "HIGH",

    "targetFrom": "2026-09-22T15:00:00+09:00",
    "targetUntil": "2026-09-22T17:00:00+09:00",
    "validFrom": "2026-09-22T09:00:00+09:00",
    "validUntil": "2026-09-22T17:10:00+09:00",
    "nextBriefingBoundary": "2026-09-22T15:00:00+09:00",

    "dataRole": "FORECAST",
    "forecastAt": "2026-09-22T15:00:00+09:00",

      "short": "오후 비, 우산 챙기세요.",
```

### 16.1 현재+예보 혼합 화면

하나의 화면에 현재 관측과 미래 예보가 같이 있어도 **문장 단위의 role을 명확히 한다.**

예:

```text
"지금은 맑고 쾌적해요. 오후 5시부터 비가 올 수 있어요."
```

- 첫 문장 = CURRENT / OBSERVATION
- 둘째 문장 = NEAR_FUTURE / FORECAST

서버 내부에서는 두 clause의 source metadata를 각각 추적한다.

# 17. 브리핑 재평가 트리거

브리핑은 다음 이벤트에 다시 계산한다.

## 17.1 데이터 트리거

- 새 10분 격자 실황
- AWS fallback source 변경
- 새 단기예보 발표분
- 새 중기예보 발표분
- 새 UV 발표분
- 새 대기질 측정/예보
- 레이더/강수 상태 변경
- 특보 발효·변경·해제
- 도로살얼음/통제 변경

## 17.2 위치 트리거

- GPS가 다른 `nx/ny`로 이동
- 행정지역이 변경되어 Region identity 변경
- 수동 지역 변경
- 최근접 관측소/측정소가 새 위치 기준으로 변경

## 17.3 시간 트리거

네트워크 자료가 안 바뀌어도 다음에서는 반드시 재평가한다.

- `validFrom`
- `validUntil`
- 일출
- 일몰
- 강수 시작/종료 시각
- 다음 시간대 예보 경계
- source stale 시각
- 공식 이벤트 발효/종료 시각

---

# 18. 데이터 호출 주기와 브리핑 갱신 주기를 분리

브리핑이 1분마다 시계 때문에 바뀐다고 해서 외부 API를 1분마다 호출하지 않는다.

```text
외부 데이터 수집 주기
-> 상위 운영정책 그대로

브리핑 재평가
-> 저장된 최신 데이터 + 현재 시각으로 로컬/서버에서 필요 시 실행
```

예:

```text
18:40 UV 데이터 이미 캐시됨
18:52 일몰

18:52
외부 UV API를 새로 호출하지 않아도
UV scene validUntil이 끝났으므로 제거
-> 다음 scene 선택
```

이 방식은 **시간 적합성을 높이면서 API quota는 증가시키지 않는다.**

---

# 19. 현재 수집 주기와 연결

본 문서에서는 외부 API 주기를 새로 정의하지 않는다.  
다음 상위 정책을 그대로 따른다.

대표 예:

| 데이터 | 상위 정책 수집 주기 |
|---|---:|
| APIHub 10분 격자 실황 | 10분 |
| AWS 최신 fallback snapshot | 5분 |
| AWS 현천/운량 | 10분 |
| 가시거리 | 10분 |
| 레이더 HSR | 5분 |
| 공식 특보 | 5분 |
| 단기예보 | 공식 발표분 8회/일 + cache miss on-demand |
| 중기예보 | 06:15 / 18:15 + cache miss on-demand |
| 자외선 | 3시간 발표 기준 + 신규 areaNo on-demand |
| 에어코리아 실시간 | 시도별 매시 수집 정책 |
| 도로살얼음 | 동절기 API budget 내 동적 주기 |

브리핑 때문에 동일 API를 사용자별로 추가 호출하지 않는다.

# 20. 신규 지역·GPS 이동·서버 재배포와 브리핑

상위 운영정책의 누락 방지 원칙을 그대로 사용한다.

## 20.1 처음 선택한 지역

```text
앱 지역 선택
-> LocationContext 확정
-> 필요한 weather cache 확인
-> cache miss이면 on-demand 보강
-> 데이터가 준비된 뒤 briefing 생성
```

중기 캐시가 없는 신규 지역이라고 해서 Week/브리핑 문장을 빈 상태로 정상 반환하지 않는다.

## 20.2 GPS 이동

`nx/ny` 또는 Region identity가 바뀌면 기존 지역의 briefing을 계속 표시하지 않는다.

```text
oldLocationKey != newLocationKey
-> 기존 briefing invalid
-> 새 위치 자료로 재생성
```

## 20.3 서버 신규 배포

브리핑 문자열 자체를 유일한 영속 데이터로 두지 않는다.

- 원본 weather cache 유지
- structured scene/intents는 필요 시 재생성 가능
- cache miss는 on-demand 보강
- 동일 source 요청은 single-flight
- 서버 재시작 직후에도 이전 지역 문자열을 잘못 재사용하지 않음

# 22. 자동 테스트 기준

## 22.1 위젯 short/long 의미 일치

```text
given:
  canonical scene = RAIN
  target = 15~17시
  action = UMBRELLA

expect:
  mediumWidget.sceneId == largeWidget.sceneId == RAIN
  target range 동일
  action 동일
  short/long 문장 모두 비 + 우산 의미 유지
```

## 22.2 UV 일몰 전후

```text
given:
  UV = 높은 수준
  sunset = 18:47
  다른 후보로 THERMAL_COMFORTABLE 존재

18:40:
  primary scene = UV 가능

18:48:
  UV scene invalid
  primary scene != UV
  "자외선", "선크림", "양산", "햇볕 차단" 현재 행동 문구 제거
  THERMAL_COMFORTABLE 등 다음 유효 scene 선택
```

## 22.3 앱을 열지 않은 위젯

```text
given:
  16:00 snapshot에
    UV entry validUntil = sunset
    evening entry validFrom = sunset

expect:
  앱 미실행 상태에서도 sunset 이후 evening entry 표시
```

## 22.4 비 종료

```text
15~17시 비 예보

16:00:
  "지금 비가 내리고 있어요." 또는 진행중 scene

17:20, 강수 종료 확인:
  이전 비 scene 제거

젖은 도로 위험이 있으면:
  별도 WET_ROAD scene 가능
```

## 22.5 현재/미래 역할

```text
현재:
  T1H/REH/WSD 관측 source set

오후 4시:
  TMP/REH/WSD forecastAt=16:00

expect:
  "지금 25℃"에 TMP 사용 금지
  "오후 4시 27℃"에 현재 T1H 복사 금지
```

## 22.6 LocationContext 변경

```text
구로동 -> 항동 이동

expect:
  old briefingId/locationKey 즉시 무효
  항동 LocationContext 기준 데이터 재선택
  중기예보는 항동 행정지역의 resolved regId 사용
```

항동 회귀 테스트는 별도 상위 정책과 동일하게 정확한 코드를 검증한다.

```text
서울특별시 구로구 항동
midTermTaRegId   == 11B10101
midTermLandRegId == 11B00000
```

## 22.7 체감 표현 일치

```text
given:
  thermalSensation = COMFORTABLE

expect:
  Main / Today / Detail / Widget이
  별도 온도 구간을 다시 계산하지 않음
  같은 thermalSensation 의미 사용
```

## 22.8 자연어

고정 케이스:

```text
"오후 15시" 없음
"현재 지금" 없음
"0.1℃ 높지만" 기본 브리핑에서 없음
"자외선 때문에 기온이 높다" 없음
동일 문장 안의 해요체/합니다체 혼용 없음
```

## 22.9 알림 시각 적합성

```text
20:00 요약 알림

expect:
  끝난 낮 UV 준비물 안내 없음
  현재/이후 밤에 유효한 scene만 사용
```

# 27. 최종 결정사항

v2에서는 다음을 기본 결정으로 확정한다.

1. **모든 채널은 같은 Fact/Scene 시스템을 사용한다.**
2. 앱·위젯의 동일 시각 대표 브리핑은 **같은 Canonical Briefing Intent**를 공유한다.
3. 짧은/긴 위젯은 문장 길이만 다르고 **topic·시간·행동 맥락은 동일**해야 한다.
4. 현재 데이터는 최종 데이터 운영정책의 최신 관측 규칙을 따른다.
5. 미래 데이터는 대상 `forecastAt`의 예보를 사용한다.
6. 체감 표현은 한국형 체감온도 v2의 공통 결과를 사용한다.
7. scene마다 `validFrom/validUntil`을 둔다.
8. 일몰, 사건 종료, source stale 등 **시간 경계에서 네트워크 호출 없이도 브리핑을 재평가**한다.
9. 자외선 scene은 낮이 끝나면 제거하고 다음 유효 scene으로 교체한다.
10. 위젯 snapshot에는 현재 문장 하나가 아니라 필요한 **시간별 briefing timeline**을 저장한다.
11. Android/iOS 위젯도 만료 경계를 반영한다.
12. 준비물은 현재 대표 scene과 모순되지 않아야 하며 parent scene의 유효시간을 따른다.
13. 사건형 푸시는 사건 자체가 목적이므로 Main primary와 다를 수 있지만, 같은 scene을 표현할 때 의미는 일치해야 한다.
14. 문장은 해요체를 기본으로 하며, 현재/미래 시제·시간대·인과관계를 자연스럽게 맞춘다.
15. 짧은 문장은 긴 문장을 자르지 않고 의미 기반으로 별도 생성한다.
16. 브리핑 다양화는 랜덤이 아니라 결정적 variant 선택을 사용한다.
17. 지역 변경·GPS 이동·재배포 후에도 상위 캐시/on-demand 정책을 이용해 올바른 위치의 데이터를 사용한다.
18. 자동 테스트는 **숫자뿐 아니라 scene·유효시간·채널 의미 일치·완성된 한국어 문장**까지 검사한다.

# 28. 한 줄 결론

최종 구조는 **“채널마다 문장을 따로 만드는 시스템”이 아니라, 현재 시각과 위치에 맞는 하나의 날씨 의미를 선택한 뒤 앱·위젯·알림이 그 의미를 각자 필요한 길이로 자연스럽게 표현하는 시스템**이다.

따라서 낮에 자외선이 중요했다면 낮에는 모든 채널이 같은 맥락의 자외선 브리핑을 사용하고, 해가 진 뒤에는 그 scene을 만료시켜 저녁에 실제로 의미가 있는 체감·비·바람·대기질 등의 다음 브리핑으로 자동 전환한다.
