- 대상 화면: Flutter 앱 `Main > 지금 날씨`의 기온·체감온도와 안내 문구
- 문서 목적: 현행 동작의 문제를 기록하고, 한국의 계절·기후 적응·습도·바람·복사열·강수·예상 옷차림을 함께 반영하는 `한국형 체감온도 v2`의 목표 계산 및 표현 기준을 정의한다.
- 변경 상태: **설계 기준 반영 완료 / 최종 날씨 운영정책과 정합성 반영 / 코드·API·테스트에는 아직 미적용**
- 상위 데이터 계약: `날씨_항목별_데이터출처_API_및_운영정책_수정본_v2.md`
  - `현재/지금/실시간`, `미래/예상`, 위치 해석, source fallback, freshness, 캐시·수집 정책은 상위 운영정책을 따른다.

  - 두 문서가 충돌할 경우 **데이터의 시각·위치·원본 선택은 상위 운영정책을 우선**하고, 체감 계산·표현은 본 문서를 따른다.
- 중요 구분:
  - `airTemperature`: 실제 관측 기온
  - `kmaApparentTemperature`: 현행 기상청 방식 체감온도
  - `perceivedTemperature`: v2에서 새로 계산할 사람 중심 최종 체감온도
  - `officialWeatherAdvisory`: 공식 폭염·한파 특보 등 위험 정보

## 1. 요약

### 1.1 현행 문제

현재 화면의 `체감 상 조금 덥게 느껴질 수 있어요`는 다음 순서로 만들어진다.

1. 기존 구현은 기상청 초단기실황의 기온·습도·풍속으로 현재 체감온도를 계산한다. **v2 목표 운영에서는 APIHub 10분 격자 실황의 `T1H/REH/WSD`를 우선하고, 결측·공급지연 시에만 최근접 유효 AWS 관측으로 보강한다.**
2. 앱은 서버에서 받은 현재 기온과 체감온도를 각각 소수점 첫째 자리로 표시한다.
3. 앱은 체감온도 절대값이 `20℃ 이상 28℃ 미만`이면 모두 `조금 더움`으로 분류한다.
4. 앱은 실제 기온과 체감온도의 차이가 `0.05℃ 미만`일 때만 `비슷함`으로 판단한다.
5. 앱은 하늘 상태, 실제 기온과의 차이, 체감온도 등급을 한 개의 고정 문장으로 조합한다.

따라서 현재 기온 `25.0℃`, 체감온도 `25.1℃`는 다음처럼 처리된다.

| 판단 항목 | 현재 결과 |
| --- | --- |
| 체감온도 절대값 | `25.1℃` → `20℃ 이상 28℃ 미만` → `조금 더움` |
| 실제 기온과의 차이 | `+0.1℃` → `0.05℃ 이상` → `실제 기온보다 0.1℃ 높지만` |
| 하늘 상태 | `맑음` → `맑은 하늘이 이어지는 날씨예요.` |
| 최종 문구 | `맑은 하늘이 이어지는 날씨예요. 실제 기온보다 0.1℃ 높지만, 체감 상 조금 덥게 느껴질 수 있어요.` |

이 결과는 `25.1℃가 보편적으로 덥다고 검증됐기 때문`이 아니라, 현행 앱의 넓은 고정 구간과 지나치게 작은 비교 임계값 때문에 발생한다.

### 1.2 v2 목표

v2에서는 단순히 체감온도 구간만 바꾸지 않는다.

```text
실제 기온
  + 습도
  + 풍속
  + 태양복사/평균복사온도
  + 하늘 상태
  + 비/눈/진눈깨비
  + UV(복사열 추정 보조값)
  + 최근 기온 이력
  + 예상 의복량
  + 기본 활동량
        ↓
  인체 열수지 기반 PT 계열 계산
        ↓
  강수 젖음·최근 기온 적응 보정
        ↓
  perceivedTemperature
        ↓
  한국형 감각 구간
        ↓
  실제기온과의 차이 + 주요 원인 + 예상 옷차림
        ↓
  자연어 브리핑
```

핵심 원칙은 다음과 같다.

1. **실제 기온과 기상청 체감온도, 사람 중심 체감온도를 분리한다.**
2. **습도·바람·복사열·의복을 동시에 다루는 인체 열수지 기반 계산을 우선한다.**
3. **한국인의 열감각 연구를 고온 구간의 기준점으로 사용한다.**
4. **계절은 월만으로 고정하지 않고 최근 기온 이력으로 실제 옷차림과 적응 상태를 함께 추정한다.**
5. **춥지도 덥지도 않은 구간은 `쾌적함`을 중심 어감으로 표현한다.**
6. **실제 기온과 최종 체감온도의 차이가 의미 있을 때만 그 차이와 원인을 설명한다.**
7. **공식 위험 기준과 일상적인 감각 표현을 분리한다.**

### 2.2 현재 기온과 체감온도 원본 — 최종 운영 계약

`현재`, `지금`, `실시간`이라는 이름을 사용하는 값은 **현재 시각과 가장 가까운 유효 관측값**을 사용한다.

| 항목 | 1순위 원본 | fallback | 시간·위치 규칙 |
| --- | --- | --- | --- |
| 기온 | 기상청 APIHub 10분 동네예보 실황 격자 `T1H` | 최근접 유효 AWS 관측 | 선택한 정확한 `nx/ny`의 최신 10분 실황. fallback이면 실제 GPS/격자 대표점에서 최근접 관측소 |
| 상대습도 | 같은 10분 격자 실황 `REH` | 같은 AWS source set의 습도 | 현재 기온과 **동일 `observedAt`·동일 source set 우선** |
| 풍속 | 같은 10분 격자 실황 `WSD` | 같은 AWS source set의 풍속 | 현재 기온과 **동일 `observedAt`·동일 source set 우선** |
| 풍향 | 같은 10분 격자 실황 `VEC` | 같은 AWS source set의 풍향 | 제공 가능할 때 동일 source set 유지 |
| 강수형태/강수 | 같은 10분 격자 실황 `PTY/RN1` | 레이더·최근접 유효 관측 | 최신 관측/실황 우선 |
| 하늘 상태 | 최근접 유효 관측소의 운량/현천 | 현재 시각 대응 최신 예보 `SKY` | 예보를 쓸 경우 `FORECAST_PROXY`로 명시 |
| 데이터 역할 | `OBSERVATION` | AWS fallback도 `OBSERVATION` + `LOCATION_FALLBACK` | 예보 `TMP`를 현재 기온으로 사용하지 않음 |
| 체감온도 출처 표기 | 관측 source set 기반 서버 계산 | 동일 | 계산 원본의 시각·위치·fallback 여부 추적 |
| 계산식 버전 | `KMA_APPARENT_TEMPERATURE_2026.1` | 동일 | 별도 모델 버전 관리 |

기상청 APIHub 10분 실황 원본은 `nph-dfs_odam_grd`를 사용한다. 현재값 freshness는 상위 운영정책을 따르며 기본 목표는 다음과 같다.

```text
0~20분   : 정상 CURRENT
20~30분  : CURRENT + SOURCE_DELAYED 가능
30분 초과: 10분 격자 실황을 현재값으로 단독 사용하지 않음
           -> 최근접 유효 AWS 관측 fallback
AWS도 허용 freshness 초과 -> OBSERVATION_UNAVAILABLE
```

**core thermal source set 원자성**

현재 체감 계산의 핵심 입력은 `T1H + REH + WSD`를 하나의 source set으로 취급한다.

```text
EXACT_GRID 세 값이 모두 유효
  -> 세 값 모두 EXACT_GRID 사용

EXACT_GRID 중 필수값 일부 결측/시각 불일치
  -> 값별로 AWS/예보를 섞지 않음
  -> 동일 AWS 관측 세트에서 T/RH/WS를 함께 구할 수 있는지 확인
  -> 가능하면 세 값 모두 AWS 세트로 전환
  -> 불가능하면 confidence 하향 또는 계산 불가 처리
```

**금지 규칙**

```text
단기예보 TMP를 현재 기온으로 조용히 대체
기온=T1H 실황 + 습도=다른 시각 AWS + 풍속=예보 WSD처럼 출처를 임의 혼합
다른 nx/ny의 실황을 선택 위치의 정확한 실황인 것처럼 표시
stale 관측을 freshness 표기 없이 현재값으로 표시
```

### 2.3 현재 기상청 방식 체감온도

서버는 계절별로 다음 산식을 사용한다.

- 5~9월: 기온과 상대습도로 Stull 습구온도를 구한 뒤 여름철 체감온도 산식을 적용한다.
- 10~익년 4월: 기온이 `10℃ 이하`이고 풍속이 `1.3m/s 이상`일 때 풍속냉각 산식을 적용한다.
- 해당 조건을 만족하지 않으면 실제 기온과 거의 같은 값이 반환될 수 있다.

이 값은 앞으로도 `kmaApparentTemperature`로 유지한다.

기상청 참고: <https://data.kma.go.kr/climate/windChill/selectWindChillChart.do>

### 2.4 현재·미래 데이터 역할을 섞지 않는 규칙

체감온도 계산도 상위 운영정책의 시간 역할을 그대로 따른다.

#### 현재 체감온도

```text
현재 airTemperature / humidity / windSpeed
  = 가능한 한 같은 observedAt
  + 같은 source set
  + 선택 위치와 일치하는 관측
```

우선순위:

```text
EXACT_GRID 10분 실황
  ↓ 결측/지연
NEAREST_STATION AWS 관측
  ↓ 사용 불가
OBSERVATION_UNAVAILABLE
```

AWS fallback을 사용하면 `sourceLocation`, `stationId`, `stationName`, `distanceKm`, `locationMatch=NEAREST_STATION`, `qualityFlags=LOCATION_FALLBACK`을 남긴다.

#### 미래/예상 체감온도

`N시 예상 체감온도`, `내일 체감` 등 미래값을 계산할 때는 관측값을 복사하지 않는다.

```text
airTemperature = TMP at forecastAt
humidity       = REH at same forecastAt
windSpeed      = WSD at same forecastAt
sky            = SKY at same forecastAt
precipitation  = PTY/PCP/SNO at same forecastAt
```

- 모든 시간별 입력은 **같은 `forecastAt`**을 사용한다.
- 같은 `forecastAt`에 여러 발표분이 있으면 가장 최신 `issuedAt`을 우선하며, 가능하면 `TMP/REH/WSD/SKY/PTY` 등을 **동일한 forecast bundle / 동일 `issuedAt`**에서 구성한다.
- 미래 PT 계산에 필요한 복사환경도 해당 미래 시각의 태양고도·하늘상태·예측자료를 사용한다.
- 현재 실황과 미래 예보를 한 계산 안에 섞지 않는다.

## 3. 현행 표현 로직의 문제

### 3.1 지나치게 넓은 감각 구간

현재 `_apparentTemperatureLabel()`은 다음 경계를 사용한다.

| 조건 | 현재 표현 |
| --- | --- |
| `38℃ 이상` | 위험할 만큼 매우 덥게 |
| `35~37.9℃` | 매우 덥게 |
| `33~34.9℃` | 더위가 강하게 |
| `28~32.9℃` | 꽤 덥게 |
| `20~27.9℃` | 조금 덥게 |
| `10~19.9℃` | 선선하게 |
| `0~9.9℃` | 쌀쌀하게 |
| `0℃ 미만` | 춥게 |

`20~27.9℃`의 8℃ 범위 전체를 `조금 더움`으로 처리하기 때문에 쾌적한 구간이 존재하지 않는다.

### 3.2 실제기온 차이를 과장

현재는 표시값이 `0.1℃`만 달라도 `실제 기온보다 0.1℃ 높지만/낮지만`이라는 표현이 붙을 수 있다.

사람이 의미 있게 느끼기 어려운 차이까지 문장에 노출하므로 정보량은 늘지만 유용성은 떨어진다.

### 3.3 환경 원인을 설명하지 못함

현재 Main 문구에는 다음 값이 직접 연결되지 않는다.

- 습도
- 풍속
- 일사/복사열
- UV
- 비·눈과 젖음
- 최근 며칠의 기온
- 예상 옷차림
- 활동량

따라서 같은 체감온도 구간이면 실제 원인이 달라도 거의 같은 문장을 반복한다.

### 3.4 Main과 Detail 기준 중복

Detail 카드에서도 동일한 경계값을 별도 함수로 정의하므로 Main만 고치면 화면별 결과가 달라질 수 있다.

관련 코드: [`weather_care_app/lib/features/home/widgets/weather_card.dart`](../weather_care_app/lib/features/home/widgets/weather_card.dart)

## 4. 연구 및 최근 한국 기후에서 가져갈 기준

### 4.1 한국형 PT 고온 연구

Kang et al. (2022)은 한국인 대상 고온·고습 환경실험에서 PT(Perceived Temperature)의 한국형 열감각 경계를 제시했다.

- `Slightly warm` 시작점: 약 `20℃ PT`
- `Warm` 시작점: `28℃ PT`
- `Hot` 시작점: `36℃ PT`
- `Very hot` 시작점: `43℃ PT`

PT는 단순한 기온 지수가 아니라 **기온, 상대습도, 풍속, 평균복사온도(Tmrt), 활동량, 의복 단열량(clo)**을 포함하는 열수지 기반 지수다. 연구의 의복 모델도 더운 환경 약 `0.50 clo`에서 추운 환경 약 `1.75 clo`까지 적응한다.

단, 이 연구는 서울 거주 젊은 남성을 대상으로 한 여름철 고온·고습 중심 실험이므로 **28/36/43℃는 고온 감각의 근거점으로 사용하고 한랭 구간까지 임의 외삽하지 않는다.**

- 연구: <https://link.springer.com/article/10.1007/s00484-022-02261-x>
- PubMed: <https://pubmed.ncbi.nlm.nih.gov/35244763/>

### 4.2 한국인의 실제 더위·추위 인식

기존 조사에서는 서울·대구 성인 남성이 실외를 덥다고 느끼기 시작하는 기온이 평균 약 `29~30℃`, 춥다고 느끼는 실외 기온은 평균 약 `7℃`, 중위값 약 `5℃`로 보고됐다.

이 결과는 현행 앱의 `20℃부터 조금 더움`이 일상 감각을 과하게 더운 쪽으로 분류할 가능성을 보여준다.

- 참고: <https://kjcls.or.kr/_common/do.php?a=full&aidx=13101&b=32&bidx=991>

### 4.3 한국 야외 현장 응답

창원·대구 야외 조사에서는 대략 `17.2~23.9℃`에서 응답이 `조금 선선함~따뜻함` 사이에 분포했고, `27.2~29.5℃`에서는 대체로 더운 쪽 응답이 나타났다.

즉 특정 기온 하나를 모든 사람에게 한 단어로 고정하기보다 **환경 요인과 옷차림을 함께 반영해 표현 범위를 부드럽게 만드는 것이 적절하다.**

- 참고: <https://sheridan.geog.kent.edu/icb2014/ICB20Cleveland.pdf>

### 4.4 한국어 열감각 표현

한국인 대상 연구에서 `따뜻하다`는 비교적 쾌적한 어감으로, `약간 덥다`는 일정 수준의 불쾌함을 포함하는 표현으로 인식됐다.

따라서 v2에서는 중립 구간에 `조금 덥다`를 사용하지 않고 다음 표현을 우선한다.

- 쾌적해요
- 선선하고 편안해요
- 포근하고 쾌적해요
- 따뜻하지만 크게 덥지 않아요

- 참고: <https://pubmed.ncbi.nlm.nih.gov/20084522/>

### 4.5 최근 한국 기후와 고정 계절의 한계

기상청에 따르면:

- 2025년 여름 전국 평균기온은 `25.7℃`로 1973년 이후 1위였다.
- 2026년 여름 전국 평균기온은 `25.4℃`로 평년보다 `1.7℃` 높아 3위였다.
- 2025년 10월 전국 평균기온은 `16.6℃`로 평년보다 `2.3℃` 높아 역대 1위였다.

따라서 `9월=가을`, `10월=긴팔`처럼 달력만으로 체감과 옷차림을 정하면 최근의 긴 더위와 늦가을 고온을 반영하기 어렵다.

- 2025 여름: <https://www.kma.go.kr/kma/news/press.jsp?bid=press&mode=view&num=1194521>
- 2026 여름: <https://www.kma.go.kr/kma/news/press.jsp?bid=press&mode=view&num=1194727>
- 2025년 10월: <https://www.kma.go.kr/kma/news/press.jsp?bid=press&mode=view&num=1194563>

### 4.6 최근 기온 이력과 옷차림

실외 옷차림은 현재 한 시점의 기온만이 아니라 **최근에 경험한 지역 기온**에 영향을 받는다는 연구가 있다. 이를 위해 v2에서는 현재 기온과 함께 `최근 7일 이동평균`을 사용한다.

- 참고: <https://www.sciencedirect.com/science/article/pii/S0360132321007927>

한국 다중이용시설 이용자 연구에서는 외기온 `10℃ / 20℃ / 30℃`에서 평균 착의량이 각각 약 `1.00 / 0.77 / 0.55 clo`로 관측됐다. 실내 다중이용시설 연구이므로 야외 옷차림의 절대 기준으로 사용하지 않고, **한국인의 최근 착의량을 추정하는 보조 기준점**으로만 사용한다.

- 참고: <https://www.jkiaebs.org/articles/article/bm50/>

### 4.7 최근 7일 기온의 위치·원본 규칙

`recentMeanTemperature7d`는 옷차림과 열적응 보정에 직접 영향을 주므로, 다른 지역의 캐시나 예보기온을 조용히 재사용하지 않는다.

기본 규칙:

```text
기준 위치 = 현재 요청의 LocationContext

GPS 있음
  -> 실제 lat/lon에서 가장 가까운 유효 관측소

GPS 없음
  -> 선택 nx/ny 대표 좌표에서 가장 가까운 유효 관측소

원본
  -> 최근 7일 실제 관측기온
  -> 미래/예보 TMP 사용 금지
```

함께 기록할 메타데이터:

```text
recentTemperatureSource.stationId
recentTemperatureSource.stationName
recentTemperatureSource.distanceKm
recentTemperatureSource.coverageDays
recentTemperatureSource.fromDate
recentTemperatureSource.toDate
```

권장 품질 규칙:

- 7일이 모두 있으면 정상 사용
- 일부 날짜가 없으면 `coverageDays`를 기록하고 confidence를 하향
- 최소 요구 일수 미만이면 `recentMeanTemperature7d`를 사용하지 않고 적응 보정을 `0`으로 둔다.
- 위치가 바뀌어 최근접 관측소가 달라지면 새 위치 기준으로 통계를 다시 선택한다.
- 항동을 선택했는데 과거에 활성화되어 있던 구로동/부천의 최근기온 캐시를 단순 재사용하는 식의 **지역 오염을 금지**한다.

## 6. v2 계산 순서

### 6.1 1단계 — 입력값 검증

필수 입력:

- 실제 기온
- 상대습도
- 풍속

현재값 계산 시 위 세 값은 **가능한 한 동일한 `observedAt`과 동일 source set**에서 와야 한다. `T1H`만 최신 격자 실황이고 `REH/WSD`는 오래된 다른 관측소 또는 예보값인 식의 임의 혼합은 금지한다.

미래/예상값 계산 시에는 `TMP/REH/WSD`를 **동일 `forecastAt`**에서 가져온다.

권장 입력:

- 하늘 상태
- 강수 종류 및 강도
- UV
- 시간대
- 위치 기반 태양고도
- 최근 7일 기온

최상 품질 입력:

- 실제 태양복사량
- 평균복사온도(Tmrt) 또는 이를 계산할 수 있는 복사 자료

입력 품질에 따라 `perceivedConfidence`를 둔다.

계산 전 데이터 계약 검증도 수행한다.

```text
현재:
  dataRole == OBSERVATION
  observedAt 존재
  airTemperature/humidity/windSpeed의 observedAt 정합
  sourceLocation이 요청 위치와 호환
  freshness 허용 범위 이내

미래:
  dataRole == FORECAST
  forecastAt 존재
  모든 시간별 입력의 forecastAt 동일
```

계약을 충족하지 않는 입력을 억지로 섞어 `HIGH/MEDIUM` confidence로 계산하지 않는다.

| 단계 | 조건 | 신뢰도 예시 |
| --- | --- | --- |
| A | 기온·습도·바람·실제 복사량/Tmrt·강수·최근기온 확보 | HIGH |
| B | 복사량 없음, 하늘+시간+태양고도+UV로 복사환경 추정 | MEDIUM |
| C | 기온·습도·바람만 확보 | LOW |

### 6.2 2단계 — 달력 계절과 체감 계절 분리

`calendarSeason`은 문구 선택에만 사용한다.

- 봄: 3~5월
- 여름: 6~8월
- 가을: 9~11월
- 겨울: 12~2월

반면 실제 계산에는 `thermalSeason`을 사용한다.

`thermalSeason`은 최근 7일 이동평균과 추세를 이용해 현재 사람들이 어떤 기후에 적응해 있는지 추정한다.

제품용 초기안:

| 최근 7일 평균기온 | thermalSeason |
| ---: | --- |
| `< 5℃` | COLD |
| `5~14.9℃` | COOL_TRANSITION |
| `15~22.9℃` | MILD |
| `≥ 23℃` | HOT |

이 경계는 공식 기상학적 계절 정의가 아니라 **의복과 열적응을 추정하기 위한 제품용 휴리스틱**이다.

### 6.3 3단계 — 예상 의복량 계산

PT 계산에는 의복 단열량이 필요하므로 사용자가 직접 옷차림을 입력하지 않는 경우 현재 지역 사람들이 입고 있을 가능성이 높은 옷차림을 추정한다.

기본 입력은 `현재 기온`이 아니라 `최근 7일 평균기온`으로 한다. 갑작스러운 기온 변화에 사람들이 즉시 옷차림을 완전히 바꾸지 않는 점을 반영하기 위해서다.

한국 연구의 `10℃≈1.00 clo`, `20℃≈0.77 clo`, `30℃≈0.55 clo`를 보조 기준점으로 사용하며, 그 사이는 선형 보간하고 범위 밖은 `0.50~1.75 clo`로 제한한다.

권장 구현:

```text
10~20℃ : 1.00 → 0.77 clo 선형 보간
20~30℃ : 0.77 → 0.55 clo 선형 보간
10℃ 미만 : 동일한 감소 추세를 역방향으로 외삽하되 최대 1.75 clo
30℃ 초과 : 동일한 감소 추세를 외삽하되 최소 0.50 clo
```

옷차림 라벨은 다음처럼 연결한다.

| 예상 clo | 예상 옷차림 |
| ---: | --- |
| `≤0.55` | 반팔·얇은 하의 중심 |
| `0.56~0.70` | 반팔 또는 매우 얇은 긴팔 |
| `0.71~0.85` | 긴팔·얇은 가디건 |
| `0.86~1.05` | 니트·가벼운 자켓 |
| `1.06~1.25` | 자켓·코트 |
| `1.26~1.45` | 코트·가벼운 패딩 |
| `>1.45` | 패딩·방한 레이어 |

이 옷차림 명칭은 clo 값을 사용자에게 이해하기 쉽게 풀어쓴 **제품용 표현 기준**이다.

### 6.4 4단계 — 활동량 기본값

사용자의 실제 활동량을 알 수 없으므로 기본 체감온도는 **가벼운 야외 이동/걷기**를 대표 조건으로 계산한다.

권장 기본값:

```text
activityLevel = LIGHT_WALK
metabolicRate ≈ 1.5~1.8 met
```

정확한 구현값은 채택하는 PT/PMV 구현의 기준 조건에 맞춰 고정하고 `perceivedModelVersion`에 포함한다.

앱이 추후 운동/러닝 상태를 알 수 있게 되더라도 기본 날씨 화면에서는 사용자 활동을 임의 추정하지 않는다.

### 6.5 5단계 — 복사열 계산

복사열은 맑은 날 야외 체감에 매우 큰 영향을 줄 수 있으므로 반드시 독립 요소로 다룬다.

우선순위:

```text
1. 실제 태양복사량 또는 Tmrt가 있음
   → 직접 사용

2. 실제 복사자료가 없음
   → 하늘 상태 + 시간 + 태양고도 + UV를 이용해 radiationLevel 추정

3. UV만 있음
   → UV를 열 자체로 사용하지 않고 복사환경 추정의 보조값으로만 사용
```

중요:

```text
UV 8 → 체감온도 +2℃
```

처럼 UV를 곧바로 온도에 더하지 않는다. UV지수는 전체 태양복사열과 같은 개념이 아니다.

UV는 다음과 같은 문구 원인으로 활용할 수 있다.

- `햇볕이 강해 체감이 더 높아요.`
- `강한 햇볕 아래에서는 더 덥게 느껴질 수 있어요.`

### 6.6 6단계 — PT 계열 열수지 계산

가능하면 검증된 PT/PMV 기반 구현을 사용한다.

입력:

```text
airTemperature
relativeHumidity
windSpeed
meanRadiantTemperature / radiation estimate
activityLevel
estimatedClothingClo
```

출력:

```text
basePerceivedTemperature
```

**중요:** 습도, 풍속, 복사열, 의복이 이미 PT 계산에 들어간 뒤 동일 요소를 다시 임의의 `+1℃`, `-2℃`로 더하지 않는다. 이중 보정을 방지한다.

### 6.7 7단계 — 비·눈에 따른 젖음 보정

PT의 기본 환경 입력만으로는 옷과 피부가 젖어 증발·전도 냉각이 커지는 상황을 충분히 나타내기 어려울 수 있으므로 강수는 제한적인 후처리 보정으로 사용한다.

초기 제품용 권장값:

| 조건 | 추가 보정 |
| --- | ---: |
| 더운 환경(`base PT > 24℃`)의 비 | 기본 `0℃`, 문구 중심 처리 |
| `24℃ 이하` 약한 비 | `0~-0.3℃` |
| `24℃ 이하` 보통 비 | `-0.3~-0.6℃` |
| `20℃ 이하` 강한 비 | `-0.6~-1.0℃` |
| 비 + 풍속 `5m/s 이상` | 위 값에 최대 `-0.3℃` 추가 |
| 마른 눈 | `0~-0.3℃` |
| 젖은 눈/진눈깨비 | `-0.3~-0.7℃` |

이 값은 사람 대상 연구에서 확정된 공식이 아니라 **앱용 초기 휴리스틱**이며 실제 로그와 사용자 피드백으로 조정한다.

고온·고습 상태에서 비가 온다는 이유만으로 숫자를 크게 낮추지 않는다.

예:

```text
29℃ / 습도 90% / 비
→ 비 보정으로 억지로 시원한 값으로 만들지 않음
→ "비가 내려도 습도가 높아 후텁지근해요"처럼 표현
```

### 6.8 8단계 — 최근 기온 적응 보정

같은 현재 기온이라도 며칠 전까지 매우 춥거나 매우 더웠다면 사람들이 입은 옷과 신체의 열적응 상태가 다를 수 있다.

초기 제품용 보정안:

| 현재 기준온도와 최근 7일 평균의 차이 | 적응 보정 |
| ---: | ---: |
| `-3~+3℃` | `0℃` |
| 현재가 최근보다 `3~6℃` 높음 | `+0.5℃` |
| 현재가 최근보다 `6℃ 이상` 높음 | `+1.0℃` |
| 현재가 최근보다 `3~6℃` 낮음 | `-0.5℃` |
| 현재가 최근보다 `6℃ 이상` 낮음 | `-1.0℃` |

보정 상한은 `±1.0℃`로 제한한다.

이 보정은 PT의 공식 구성 요소가 아니라 **최근 기후 적응과 실제 옷차림 지연을 반영하기 위한 제품 휴리스틱**이다.

### 6.9 최종 체감온도

```text
perceivedTemperature
= PT/열수지 기반 basePerceivedTemperature
+ precipitationWetnessAdjustment
+ recentTemperatureAdaptationAdjustment
```

모든 계산 후 소수점 첫째 자리로 반올림한다.

## 7. 최종 체감온도 감각 구간

아래 구간은 **앱 문구용 제품 기준**이다. 기상청의 공식 체감온도 등급이 아니다.

고온부는 한국형 PT 연구의 `20 / 28 / 36 / 43℃` 경계를 주요 근거점으로 사용하고, 일상적인 문구 다양화를 위해 중간 구간을 추가한다. 저온부는 한국인 실외 인식 연구와 기존 현장 조사 결과를 참고하되 공식 PT 한랭 경계로 간주하지 않는다.

| perceivedTemperature | 내부 상태 | 기본 어감 |
| ---: | --- | --- |
| `< -5℃` | VERY_COLD | 매우 춥고 매서움 |
| `-5~3.9℃` | COLD | 추움 |
| `4~9.9℃` | CHILLY | 꽤 쌀쌀함 |
| `10~15.9℃` | COOL | 서늘함 |
| `16~19.9℃` | COOL_COMFORTABLE | 선선하고 쾌적함 |
| `20~23.9℃` | COMFORTABLE | 덥지도 춥지도 않고 쾌적함 |
| `24~26.9℃` | WARM_COMFORTABLE | 따뜻하고 쾌적함 |
| `27~27.9℃` | WARM | 제법 따뜻함 |
| `28~28.9℃` | WARM | 따뜻함이 뚜렷함 — 한국형 PT `Warm` 경계 진입 |
| `29~31.9℃` | SLIGHTLY_HOT | 조금 더움 |
| `32~35.9℃` | HOT | 더운 느낌이 뚜렷함 |
| `36~42.9℃` | VERY_HOT | 매우 더움 — 한국형 PT `Hot` 이상 |
| `≥43℃` | EXTREME_HOT | 극심하게 더움 — 한국형 PT `Very hot` 이상 |

### 7.1 기존과 가장 큰 변경점

기존:

```text
20~27.9℃ → 조금 더움
```

v2:

```text
20~23.9℃ → 쾌적
24~26.9℃ → 따뜻하고 쾌적
27~28.9℃ → 따뜻함
29℃부터 → 조금 더움
```

따라서 `25.1℃`를 기본적으로 `조금 덥다`고 단정하지 않는다.

### 7.2 경계 히스테리시스

체감온도가 경계 부근에서 `26.9 ↔ 27.0℃`처럼 오르내릴 때 문구가 매번 바뀌지 않도록 상태 전환에 히스테리시스를 적용한다.

권장 초기값:

```text
현재 상태 유지 허용폭: ±0.3℃
```

예를 들어 `WARM_COMFORTABLE → WARM` 진입은 `27.0℃`, 다시 `WARM_COMFORTABLE`로 내려오는 해제는 `26.7℃` 이하로 설정한다.

## 8. 실제 기온과 최종 체감온도의 차이

비교 대상은 다음과 같다.

```text
delta = perceivedTemperature - airTemperature
```

### 8.1 문구 기준

| `|delta|` | 처리 |
| ---: | --- |
| `<0.6℃` | 차이 언급 생략 또는 `기온과 거의 비슷하게 느껴져요` |
| `0.6~1.4℃` | `기온보다 조금 더 따뜻/서늘하게 느껴져요` |
| `1.5~2.9℃` | 수치 포함 가능: `기온보다 체감은 약 2℃ 높아요` |
| `3.0~4.9℃` | `기온보다 확실히 더 덥게/춥게 느껴져요` |
| `≥5.0℃` | `기온 숫자보다 훨씬 덥게/춥게 느껴질 수 있어요` |

### 8.2 0.1℃ 단위 차이는 기본적으로 말하지 않음

현재처럼 `25.0℃ → 25.1℃`일 때

```text
실제 기온보다 0.1℃ 높지만
```

이라고 말하지 않는다.

권장:

```text
따뜻하지만 크게 덥지 않아 쾌적해요.
```

또는 차이 설명이 필요한 UI라면:

```text
기온과 체감 차이는 거의 없어요.
```

## 9. 체감 차이의 주요 원인 계산

최종 문구가 단순히 `체감 2℃ 높음`에서 끝나지 않도록 **왜 높거나 낮은지**를 함께 설명한다.

### 9.1 단순 가산값으로 계산하지 않음

PT는 여러 변수가 서로 상호작용하므로 아래처럼 단순 합산한 값을 공식 계산으로 사용하지 않는다.

```text
습도 +1.2℃
햇볕 +1.4℃
바람 -0.5℃
= 체감 +2.1℃
```

이 방식은 설명용 개념도일 뿐 실제 PT의 열수지를 정확히 나타내지 못한다.

### 9.2 권장 방식 — counterfactual impact

최종 PT를 계산한 후 한 번에 한 요소만 기준 상태로 되돌려 재계산한다.

예:

```text
finalPT = 모든 실제 조건으로 계산

humidityImpact  = finalPT - PT(습도만 기준값으로 변경)
windImpact      = finalPT - PT(풍속만 기준값으로 변경)
radiationImpact = finalPT - PT(Tmrt를 기온 수준으로 변경)
clothingImpact  = finalPT - PT(중립 의복량으로 변경)
```

기준 상태 예:

- 습도: `50%`
- 바람: `1.0m/s`
- 복사: `Tmrt ≈ airTemperature`
- 의복: 해당 thermalSeason의 중앙값

각 영향값의 절댓값이 큰 순서로 `dominantFactors`를 결정한다.

주의: 변수 간 상호작용 때문에 각 영향값의 합이 최종 `delta`와 정확히 일치할 필요는 없다.

### 9.3 원인 문구 예

- `높은 습도 때문에 더 후텁지근하게 느껴져요.`
- `햇볕의 복사열 때문에 기온보다 더 덥게 느껴져요.`
- `바람이 불어 실제 기온보다 서늘하게 느껴져요.`
- `비와 바람이 겹쳐 체감이 더 낮아요.`
- `최근보다 갑자기 기온이 내려가 더 쌀쌀하게 느껴질 수 있어요.`

## 10. 예상 옷차림을 최종 문구에 반영

### 10.1 원칙

옷차림은 `추천 옷`이 아니라 **현재 한국 사람들이 입고 있을 가능성이 높은 복장 수준을 추정해 체감 설명에 반영**한다.

예를 들어 같은 `18℃`라도:

- 며칠 전까지 추웠던 봄의 18℃: 비교적 두꺼운 옷을 유지할 가능성이 높아 `포근함`이 강조될 수 있음
- 며칠 전까지 더웠던 가을의 18℃: 비교적 얇은 옷을 유지할 가능성이 높아 `선선함/서늘함`이 강조될 수 있음

### 10.2 사용자용 옷차림 문구

| estimatedClothingLabel | 표현 예 |
| --- | --- |
| 반팔·얇은 하의 | `가벼운 옷차림이 자연스러운 날씨예요.` |
| 반팔/얇은 긴팔 | `반팔이나 얇은 긴팔 정도가 편안해요.` |
| 긴팔·얇은 가디건 | `얇은 긴팔이나 가벼운 겉옷이 어울려요.` |
| 니트·가벼운 자켓 | `가벼운 자켓을 입기 좋은 정도예요.` |
| 자켓·코트 | `겉옷이 필요한 쌀쌀한 날씨예요.` |
| 코트·가벼운 패딩 | `따뜻한 겉옷이 있어야 편안해요.` |
| 패딩·방한 레이어 | `두꺼운 방한 옷차림이 필요한 추위예요.` |

문장의 목적은 쇼핑/패션 추천이 아니라 **왜 사용자가 그렇게 느낄지 이해시키는 것**이다.

## 11. 문구 생성 방식

### 11.1 최종 구조

기본 브리핑은 최대 2~3개의 정보 블록으로 구성한다.

```text
[전체 느낌]
+ [실제 기온과 체감 차이 또는 주요 원인]
+ [필요한 경우 예상 옷차림]
```

모든 정보를 항상 한 문장에 넣지 않는다.

### 11.2 쾌적 구간 문구 풀

#### COOL_COMFORTABLE — 16~19.9℃

- `선선하고 쾌적하게 느껴져요.`
- `공기가 선선해 활동하기 편안해요.`
- `약간 선선하지만 기분 좋게 느껴지는 날씨예요.`
- 봄 + 최근 추웠음: `최근보다 포근해져 한결 편안하게 느껴져요.`
- 가을 + 최근 더웠음: `더위가 누그러져 선선하고 쾌적해요.`

#### COMFORTABLE — 20~23.9℃

- `덥지도 춥지도 않아 쾌적해요.`
- `크게 덥거나 춥지 않아 편안해요.`
- `활동하기 무난하고 쾌적한 날씨예요.`
- 건조 + 약풍: `공기가 산뜻하고 쾌적해요.`
- 약한 바람: `바람이 살짝 불어 더욱 쾌적해요.`

#### WARM_COMFORTABLE — 24~26.9℃

- `따뜻하지만 크게 덥지 않아 쾌적해요.`
- `포근하고 편안하게 느껴지는 날씨예요.`
- `따뜻한 편이지만 부담스러운 더위는 아니에요.`
- 낮은 습도: `따뜻하고 산뜻하게 느껴져요.`
- 높은 습도: `약간 습하지만 아직 크게 덥지는 않아요.`

### 11.3 더운 구간 문구 풀

#### WARM — 27~28.9℃

- `제법 따뜻하게 느껴져요.`
- `따뜻함이 뚜렷한 날씨예요.`
- 높은 습도: `따뜻하고 조금 후텁지근하게 느껴져요.`
- 강한 햇볕: `햇볕 아래에서는 더 덥게 느껴질 수 있어요.`

#### SLIGHTLY_HOT — 29~31.9℃

- `조금 더워요.`
- `움직이면 더위가 느껴질 정도예요.`
- 높은 습도: `습도까지 높아 후텁지근해요.`
- 약한 바람 + 햇볕: `바람이 약하고 햇볕이 강해 더 덥게 느껴져요.`

#### HOT 이상

- `더운 느낌이 뚜렷해요.`
- `체감 더위가 강해요.`
- `많이 덥게 느껴지는 날씨예요.`
- `습하고 매우 덥게 느껴져요.`

`EXTREME_HOT`에서는 일상 감각 문구와 별도로 건강 위험 문구를 표시한다.

### 11.4 추운 구간 문구 풀

#### COOL — 10~15.9℃

- `서늘하게 느껴져요.`
- `가벼운 겉옷이 생각나는 서늘함이에요.`
- 바람 강함: `바람 때문에 제법 쌀쌀하게 느껴져요.`

#### CHILLY — 4~9.9℃

- `꽤 쌀쌀해요.`
- `찬 기운이 느껴지는 날씨예요.`
- `바람이 불면 더 춥게 느껴질 수 있어요.`

#### COLD 이하

- `추워요.`
- `차가운 공기가 확실히 느껴져요.`
- `매섭게 추운 날씨예요.`

### 11.5 환경 수식어

기본 감각 문구 뒤에 환경 상태에 따라 하나만 우선적으로 붙인다.

| 조건 | 수식어 예 |
| --- | --- |
| 고습 | 습하고 / 후텁지근하게 |
| 저습 | 산뜻하게 / 건조하게 |
| 강한 바람 | 바람 때문에 / 바람이 강해 |
| 강한 복사열 | 햇볕 아래에서는 / 햇볕이 강해 |
| 비 | 비 때문에 / 비가 내려 |
| 비+강풍 | 비바람 때문에 |
| 눈 | 눈이 내리고 / 차가운 눈바람 때문에 |
| 급격한 기온 하락 | 최근보다 갑자기 쌀쌀해져 |
| 급격한 기온 상승 | 최근보다 포근해져 |

## 12. 문구 다양화 규칙

### 12.1 완전 랜덤 금지

새로고침할 때마다 표현이 바뀌면 상태가 변한 것처럼 보이므로 `Random()`으로 문구를 선택하지 않는다.

### 12.2 결정적 선택

다음 값을 기반으로 seed/hash를 만든다.

```text
regionKey
+ yyyyMMdd
+ 3시간 시간대
+ thermalSensation
+ dominantFactor
```

같은 조건에서는 같은 문장이 유지되고, 시간대나 실제 날씨 조건이 바뀌면 자연스럽게 다른 표현을 선택한다.

### 12.3 같은 문구 연속 사용 제한

서버에서 최근 선택 인덱스를 관리하지 않는다면 최소한 동일 seed 구간에서는 고정하고, 다음 3시간 구간에서 후보가 3개 이상일 경우 직전 후보와 다른 문장을 우선하도록 할 수 있다.

## 13. 공식 위험 기준과 감각 문구 분리

`덥다/쾌적하다/춥다`와 `폭염 위험`은 동일한 개념이 아니다.

따라서 다음을 분리한다.

```text
thermalSensation
→ 일상적인 느낌

thermalRisk / officialWeatherAdvisory
→ 건강 행동 필요 여부
```

예:

```text
체감: "많이 덥게 느껴져요."
위험: "폭염주의보가 발효 중이에요. 야외 활동 시 휴식과 수분 섭취가 필요해요."
```

기상청의 `33/35/38℃` 기반 위험 판단과 실제 발효 특보는 기존의 생활 감각 구간에 섞지 않는다.

## 14. 대표 시나리오

아래 수치는 계산 로직을 설명하기 위한 예시이며 실제 PT 엔진 적용 후 값이 달라질 수 있다.

### 14.1 25℃, 큰 체감 차이 없음

```text
실제기온: 25.0℃
최종 체감 계산 결과 예: 25.3℃
습도: 보통
바람: 약함
강수: 없음
```

권장:

```text
따뜻하지만 크게 덥지 않아 쾌적해요. 반팔이나 얇은 긴팔 정도가 편안해요.
```

하지 않음:

```text
실제 기온보다 0.3℃ 높지만, 체감 상 조금 덥게 느껴질 수 있어요.
```

### 14.2 29℃, 고습 + 강한 햇볕

```text
실제기온: 29℃
최종 체감 계산 결과 예: 32℃대
주요 요인: 습도 + 복사열
```

권장:

```text
습하고 더운 느낌이 뚜렷해요. 기온보다 체감은 확실히 높고, 높은 습도와 강한 햇볕의 영향이 커요.
```

### 14.3 18℃, 비 + 바람

```text
실제기온: 18℃
최종 체감 계산 결과 예: 15~16℃
주요 요인: 바람 + 강수 젖음
```

권장:

```text
비와 바람 때문에 제법 서늘해요. 기온보다 체감은 낮고, 가벼운 겉옷이 있으면 편안해요.
```

### 14.4 봄 18℃ — 최근까지 추웠음

```text
calendarSeason: SPRING
recentMean7d: 10℃
current: 18℃
```

권장 어감:

```text
최근보다 포근해져 한결 편안하게 느껴져요.
```

예상 옷차림은 현재 18℃만 보고 즉시 얇게 잡지 않고 최근 추운 날씨의 영향을 일부 유지한다.

### 14.5 가을 18℃ — 최근까지 더웠음

```text
calendarSeason: AUTUMN
recentMean7d: 24℃
current: 18℃
```

권장 어감:

```text
최근보다 기온이 내려가 선선하고, 바람이 불면 조금 서늘하게 느껴져요.
```

### 15.1 서버가 판단을 단일화

```json
  "providerField": "T1H,REH,WSD",
  "fieldSources": {
    "temperature": { "role": "OBSERVATION", "field": "T1H" },
    "humidity": { "role": "OBSERVATION", "field": "REH" },
    "windSpeed": { "role": "OBSERVATION", "field": "WSD" },
    "sky": { "role": "FORECAST_PROXY", "field": "SKY" }

  "estimatedClothingLabel": "LIGHT",

```

### 15.2 앱 역할

앱은 다음을 수행한다.

- 숫자 표시
- 서버가 준 `thermalSensation`에 따른 아이콘/색상 선택
- 서버가 준 `brief` 표시
- Detail에서도 동일한 `thermalSensation`을 사용

앱에서 별도로 `20/28/33/35/38` 같은 구간을 다시 정의하지 않는다.

현재 카드가 관측 기온과 `FORECAST_PROXY` 하늘상태처럼 여러 source 역할을 함께 포함할 수 있으므로, 앱은 `current.dataRole` 하나만 보고 모든 필드가 관측이라고 가정하지 않는다. 필요 시 `fieldSources`를 사용해 필드별 출처를 판별한다.

### 15.3 서버 역할

서버는 다음을 담당한다.

- 현재/미래 `dataRole` 판정
- APIHub 10분 격자 실황 및 AWS fallback source 선택
- `observedAt/forecastAt/sourceLocation/freshness` 정합성 검증
- 원본 관측값 수집
- 선택 위치 기준 최근 7일 실제 관측기온 통계
- 예상 clo 계산
- 복사환경 추정
- PT/열수지 계산
- 강수 및 적응 보정
- 체감 감각 분류
- dominant factor 계산
- 자연어 후보 선택

## 16. fallback 정책

모든 데이터가 항상 존재한다고 가정하지 않는다. **fallback은 계산식보다 먼저 데이터 source 단계에서 적용**한다.

### 16.0 현재 관측 source fallback

```text
1. 선택 nx/ny의 최신 APIHub 10분 격자 실황
2. 결측/공급지연이면 선택 위치의 최근접 유효 AWS 관측
3. AWS도 freshness 초과/결측이면 OBSERVATION_UNAVAILABLE
```

- `TMP` 단기예보를 현재 기온 fallback으로 사용하지 않는다.
- AWS fallback이면 `LOCATION_FALLBACK`과 관측소 거리 정보를 남긴다.
- 하늘 상태처럼 직접 관측이 항상 가능한 항목이 아니면 예보를 사용할 수 있지만 `FORECAST_PROXY`로 별도 표시한다.
- source fallback 후에도 체감 계산 필수 입력의 시각/source 정합이 맞지 않으면 계산하지 않거나 confidence를 명시적으로 낮춘다.

### 16.1 PT 계산 가능한 경우

```text
perceivedTemperature = KR PT/heat-balance v2
```

### 16.2 복사자료만 없는 경우

```text
하늘 + 시간 + 태양고도 + UV로 radiationLevel 추정
confidence = MEDIUM
```

### 16.3 최근 7일 자료가 없는 경우

```text
calendarSeason + currentTemperature로 의복량 초기 추정
adaptationAdjustment = 0
confidence 한 단계 하향
```

### 16.4 PT 필수 입력이 부족한 경우

기상청 방식 체감온도를 임시 fallback으로 사용하되 한국 PT 경계를 그대로 적용하지 않는다.

이때 `kmaApparentTemperature` 자체도 **유효한 현재 관측 source set**(`T1H/REH/WSD` 또는 동일 AWS 관측 세트)에서 계산된 값이어야 한다. `TMP` 예보값을 현재 관측처럼 넣어 만든 값은 fallback으로 인정하지 않는다.

```text
perceivedTemperature = kmaApparentTemperature
modelSource = KMA_FALLBACK_FROM_OBSERVATION
```

문구도 보수적으로 생성한다.

예:

```text
현재 자료로는 기온과 바람·습도를 중심으로 체감을 계산했어요.
```

## 17. 테스트 기준

### 17.1 경계값 테스트

각 구간에서 바로 아래/정확한 경계/바로 위를 테스트한다.

예:

```text
19.9 / 20.0 / 20.1
23.9 / 24.0 / 24.1
26.9 / 27.0 / 27.1
27.9 / 28.0 / 28.1
28.9 / 29.0 / 29.1
35.9 / 36.0 / 36.1
42.9 / 43.0 / 43.1
```

### 17.2 실제기온 차이 테스트

```text
0.0 / 0.5 / 0.6
1.4 / 1.5
2.9 / 3.0
4.9 / 5.0℃
```

### 17.3 환경 조합 테스트

최소 다음 조합을 고정 테스트한다.

1. 25℃ + 보통 습도 + 약풍 + 흐림
2. 25℃ + 고습 + 무풍
3. 25℃ + 낮은 습도 + 4m/s 바람
4. 29℃ + 고습 + 강한 햇볕
5. 18℃ + 비 + 5m/s 바람
6. 5℃ + 강풍
7. 0℃ + 눈
8. 18℃ + 봄 + 최근 7일 10℃
9. 18℃ + 가을 + 최근 7일 24℃
10. 데이터 일부 결측 fallback

### 17.4 문구 안정성 테스트

- 같은 region/time-slot/상태 → 같은 문구
- 다음 시간 슬롯 → 후보 문구 변경 가능
- 경계 ±0.3℃ 내 작은 변동 → 기존 감각 상태 유지
- 0.1℃ 체감 차이 → 차이 문구를 강제로 붙이지 않음

### 17.5 Main/Detail 일치 테스트

Main과 Detail은 같은 `thermalSensation`과 `perceivedTemperature`를 사용해야 한다.

### 17.6 데이터 source·시각·위치 계약 테스트

아래 테스트는 체감 계산값 자체와 별개로 반드시 자동화한다.

#### 현재값 exact-grid

```text
given:
  requested nx/ny = X/Y
  X/Y의 최신 10분 실황에 T1H/REH/WSD 존재

expect:
  dataRole == OBSERVATION
  sourceLocation.locationMatch == EXACT_GRID
  temperature source == T1H
  TMP를 현재 기온으로 사용하지 않음
  T1H/REH/WSD observedAt 동일
  T1H/REH/WSD가 하나의 core source set에서 구성됨
```

#### AWS fallback

```text
given:
  요청 격자 실황 결측 또는 freshness 초과
  근처 유효 AWS 관측 존재

expect:
  dataRole == OBSERVATION
  sourceLocation.locationMatch == NEAREST_STATION
  qualityFlags contains LOCATION_FALLBACK
  stationId/stationName/distanceKm 존재
  체감 입력이 동일 AWS source set에서 구성됨
```

#### stale 차단

```text
given:
  격자 실황과 AWS 모두 freshness 기준 초과

expect:
  현재값을 TMP 예보로 대체하지 않음
  OBSERVATION_UNAVAILABLE 또는 명시적 unavailable 상태
```

#### 미래 체감

```text
given:
  forecastAt = 2026-09-22T15:00:00+09:00

expect:
  TMP/REH/WSD/SKY/PTY 등 시간별 입력의 forecastAt이 모두 15:00
  가능한 한 동일 issuedAt / 동일 forecast bundle에서 구성
  현재 T1H 관측값을 미래 계산에 복사하지 않음
```

#### 최근 7일 위치

```text
given:
  사용자가 다른 지역으로 이동/변경
  nearest historical observation station이 변경됨

expect:
  recentMeanTemperature7d source도 새 LocationContext 기준으로 재선택
  이전 활성 지역의 7일 평균을 조용히 재사용하지 않음
  station/distance/coverageDays 추적 가능
```

#### 하늘 상태 proxy

```text
given:
  유효 관측소 운량/현천 없음
  현재 시각 대응 SKY 예보 존재

expect:
  SKY 사용 가능
  dataRole/source metadata에 FORECAST_PROXY 명시
```

## 20. 최종 권장 결정사항

v2 적용 시 다음을 기본 결정으로 채택한다.

1. 기존 `apparentTemperature`를 `kmaApparentTemperature` 역할로 명확히 분리한다.
2. 신규 `perceivedTemperature`는 PT/열수지 기반으로 계산한다.
3. 계절은 `calendarSeason`과 `thermalSeason`으로 분리한다.
4. 의복량은 최근 7일 평균기온을 중심으로 추정한다.
5. UV는 직접 ℃ 보정값으로 사용하지 않고 복사열 추정 보조 변수로 사용한다.
6. 비·눈은 중복 보정을 피하고 젖음 효과만 제한적으로 후처리한다.
7. `20~26℃대`에 쾌적/따뜻하고 쾌적한 구간을 명시적으로 둔다.
8. 체감 차이 `0.5℃ 이하`는 기본적으로 말하지 않는다.
9. 큰 체감 차이가 발생하면 `높다/낮다`뿐 아니라 `습도/햇볕/바람/비/최근 기온` 중 주요 원인을 설명한다.
10. 예상 옷차림을 계산에 사용하고 문구에도 필요할 때 포함한다.
11. 문구는 상태별 후보군을 두되 완전 랜덤이 아니라 결정적 seed 방식으로 선택한다.
12. Main과 Detail의 감각 판정을 공통화한다.
13. 일상적인 열감각과 기상청 공식 위험/특보는 별도 레이어로 유지한다.
14. 모든 휴리스틱 경계는 버전 관리하고 실제 서비스 로그와 사용자 피드백을 통해 조정 가능하게 만든다.
15. **현재 기온·습도·풍속은 APIHub 10분 격자 실황을 1순위로 사용하고, 결측/지연 시 최근접 유효 AWS 관측을 사용한다.**
16. **현재 기온에 단기예보 `TMP`를 fallback으로 사용하지 않는다.**
17. 현재 체감 계산의 `T1H/REH/WSD`는 가능한 한 동일 `observedAt`·동일 source set을 사용한다.
18. 미래/예상 체감 계산의 `TMP/REH/WSD` 등 시간 입력은 동일 `forecastAt`을 사용한다.
19. `recentMeanTemperature7d`는 현재 `LocationContext`에서 가장 가까운 유효 실제 관측소 기준으로 계산하고 source/거리/coverage를 기록한다.
20. 현재 하늘 상태가 예보 `SKY` fallback이면 `FORECAST_PROXY`를 반드시 노출한다.
21. 현재/미래 체감 응답에는 원본 시각·위치·fallback을 추적할 수 있는 메타데이터를 함께 제공한다.

## 22. 상태

이 문서는 **현행 구현을 설명하는 문서이면서 v2 구현 기준을 확정하기 위한 목표 설계 문서**로 변경됐다.

아직 실제 코드에 적용되지 않은 항목:

- 신규 PT/열수지 계산
- 최근 7일 기온 기반 의복/적응 모델
- 복사열/Tmrt 추정
- UV 보조 처리
- 비·눈 젖음 보정
- 신규 감각 구간
- 옷차림 문구
- dominant factor 분석
- 결정적 문구 선택
- 서버 API 신규 필드
- Main/Detail 공통 판정
- APIHub 10분 격자 실황 `T1H/REH/WSD/VEC/PTY/RN1` 연동
- 최근접 AWS observation fallback 및 freshness 판정
- 현재 입력의 동일 `observedAt` / 동일 source set 검증
- 미래 입력의 동일 `forecastAt` 검증
- 최근 7일 실제 관측기온의 위치 기반 source 선택
- source/fallback 추적 API 메타데이터
- 신규 회귀 테스트

구현 시 `KR_PERCEIVED_V2_2026.1`과 같이 계산 모델 버전을 응답에 남겨 이후 경계값이나 휴리스틱이 변경되어도 결과를 추적할 수 있도록 한다.

또한 데이터 원본 계약은 상위 `날씨_항목별_데이터출처_API_및_운영정책_수정본_v2.md`와 함께 회귀 테스트하여, 향후 체감온도 로직 변경 때문에 `현재=예보 TMP` 같은 과거 문제가 다시 들어오지 않도록 한다.
