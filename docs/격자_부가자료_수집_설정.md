# 바다·강·낙뢰 자료 수집 설정

## 구현 범위

미니 PC 서버의 별도 작업이 국립해양조사원 관측·예보, K-water 시간별 수위·댐 운영, 한강홍수통제소 하천 유량, 국립수산과학원 해파리 목록·신규 상세, 기상청 낙뢰 좌표를 수집한다. 산의 고도별 바람·구름 높이·운량은 조사표의 제외 결정에 따라 호출하지 않는다. 관측 지점 자료는 지점의 값으로 보관하며 5km 격자 전체의 실측값으로 변환하지 않는다. Data 탭의 별도 조회 API로 제공하며 기존 Today·Week 응답에는 합치지 않는다.

- `grid-hourly`: 매시 06분. 등록된 사용자 위치에서 가까운 조위관측소·해양관측부이와 조석예보 지점을 중복 없이 조회한다. K-water 댐 코드 목록은 성공 시 하루 한 번만 조회하고 실패하면 다음 시간에 다시 시도한다. 확인된 댐 코드는 지점별 운영 자료에 사용한다. 조석 예보와 ROMS는 같은 날짜의 성공본이 있으면 다시 요청하지 않는다. 해파리 목록은 한국 시각 0·6·12·18시에 조회하고, 새 문서의 상세를 한 번 저장한다.
- `grid-lightning`: 매 10분의 05분. 5분 지연을 두고 직전 10분의 전국 낙뢰 탐지 좌표를 조회한다. APIHub 공용 호출·용량 예산을 사용하며 한 응답은 최대 2MB로 제한한다.
- `grid-river-flow`: 매시 19분. 한강홍수통제소의 전국 수위관측소 최신 10분 자료를 한 번 조회하고, 실제 유량값이 있는 지점의 수위·유량을 보관한다. 제공처의 권역별 자료 수집 지연을 고려해 19분에 실행한다.
- `grid_extra_snapshots`에 출처·대상·시각별 결과를 저장한다. 페이지가 모두 도착한 응답만 기록하고 실패 시 이전 성공본을 유지한다. 8일이 지난 스냅샷은 기존 보존 작업에서 삭제한다.

## 사용자에게 표시할 대상 구분

| 선택 대상 | 선택 후 표시할 항목 | 표시 기준 |
| --- | --- | --- |
| 댐·보 | 댐 수위·유입량·방류량 | 사용자가 고른 시설의 `damcode`로 묶는다. 가까운 댐의 값을 사용자 격자 전체의 값처럼 표시하지 않는다. |
| 하천 관측소 | 하천 수위·유량 | 같은 관측소 코드와 관측 시각의 값으로 표시한다. 강이나 격자만으로 특정 관측소 값을 확정하지 않는다. |
| 조위관측소 | 관측 조위·예측 조위·만조·간조 | 선택한 `DT_` 관측소의 관측값과 예보값을 구분한다. |
| 해양관측부이 | 수온·유속·유향 | 선택한 `TW_` 부이의 관측값과 단위를 표시한다. |
| 해수욕장 | 이안류 위험지수 | 해당 해수욕장을 선택했을 때만 표시한다. |
| 해역 또는 보고서 | ROMS 예측 수온·유속·유향, 해파리 정보 | ROMS는 선택한 해역·예측 격자와 시각을, 해파리는 원문 보고서의 해당 해역과 발표일을 표시한다. 두 자료를 한 관측소의 실측값처럼 합치지 않는다. |

낙뢰는 발생 좌표와 시각을 이용한 격자별 **관측 이력**으로 집계할 수 있다. 산의 고도별 풍향·풍속, 구름 높이, 운량 수치는 조사표에서 제외했다. 수집 지점을 사용자 위치로 자동 선정하는 기능과 사용자가 조회할 대상을 선택하는 화면·API는 별개이다. 댐 코드 목록은 코드·이름만 제공하므로 위치 기반 후보를 만들려면 별도 시설 좌표 자료가 필요하다.

### 앱 Data 탭과 조회 API

- Today 다음에 Data 탭을 두고 수집된 자료 종류를 선택한다. `GET /api/v1/weather/extra/catalog?nx=...&ny=...`는 선택 가능한 대상 목록을, `GET /api/v1/weather/extra/records?source=...&targetId=...&nx=...&ny=...`는 해당 대상의 최근 기록을 반환한다. 값이 없는 대상은 임의의 격자값으로 대체하지 않는다.
- 낙뢰는 Data 탭에서 목록·선택·자료 조회 대상에서 제외한다. 서버 수집·저장과 요청 격자 내 발생 건의 시간별 집계 API는 유지한다. 전용 감지 알림과 Today 상세 자료는 아래 기준을 함께 사용한다.
- ROMS는 현재 격자 안에 해양 모델 지점이 있으면 시각별 가장 가까운 지점의 예측값을 표시하고, 별도 해역 선택도 제공한다. 댐·보, 하천 관측소, 조위관측소, 부이, 해수욕장, 해파리 보고서는 저장된 대상 중 사용자가 선택한 것만 표시한다. 시간별 자료와 일자별 자료를 구분하고 원래 관측·예측 시각을 함께 표시한다.
- 댐 목록의 이름은 새로 수집한 코드·이름 스냅샷을 사용한다. 기존 코드 문자열 스냅샷도 수집기는 읽을 수 있다. 한강홍수통제소 자료의 관측소 이름·좌표는 아직 수집하지 않아 선택 목록에는 관측소 코드가 보인다. 이안류·ROMS·K-water 별도 수위관측소는 운영 설정에 수집 대상을 추가해야 목록에 나타난다.
- 현재 운영 서버에 신규 수집 코드와 조회 API는 배포되지 않았다. 앱 탭은 구버전 서버에서 조회 실패 안내를 표시한다. 배포는 별도 작업이다.

## 설정

### 낙뢰 감지 알림·Today 상세 자료 (2026-10-20)

- `GET /api/v1/weather/extra/lightning?nx=...&ny=...`는 저장 DB만 읽어 선택 격자의 최근 낙뢰와 수집 상태를 반환한다. `Cache-Control: no-store`이며 외부 기상청 API를 추가 호출하지 않는다. Today에 진입하거나 새로고침·앱 복귀 시 조회하고, 선택된 Today 화면에서만 최대 1분 간격으로 다시 조회한다. 관측/수집 유효 시간이 먼저 끝나면 그 시각에 화면에서 제외한다.
- 발생 시각 기준 **30분 미만**의 실제 관측만 사용한다. 정확히 30분인 관측, 미래 시각, 잘못된 시각·좌표, 다른 격자와 중복 관측은 제외한다. 수집 시각이나 앱 조회 시각으로 관측 유효 시간을 연장하지 않는다. 새 낙뢰가 관측되면 해당 발생 시각부터 30분을 계산한다.
- 기준 근거는 [기상청 낙뢰 국민행동요령](https://www.weather.go.kr/w/hazard/safety-guide/lightning.do)의 마지막 번개·천둥 후 약 30분 대피 및 [미국 NWS 낙뢰 행동요령](https://www.weather.gov/safety/lightning-outdoors)의 마지막 천둥 후 최소 30분 대기이다. **관측 자료의 30분 만료는 앱의 표시·알림 정책으로 적용한 것이며, 공식적인 안전 판정 시간이 아니다.** 앱은 천둥 소리를 감지하지 않으며, 한 격자 밖의 위험이나 미관측을 배제하지 않는다. 관측 없음·만료를 안전·해제 문구로 표시하거나 해제 알림을 보내지 않는다.
- 수집 상태의 최신 조회 구간 종료/확인 시각이 **20분 이상** 뒤처지면 `STALE`로 처리한다. 10분 수집 주기와 5분 지연에 5분 여유를 둔 운영 신선도 기준이며, 위 30분 대피 지침과 별개이다. 최근 조회 실패는 `FAILED`, 최초 미수집은 `UNAVAILABLE`이다. 이 상태들은 정상 관측 0건과 구분하고 Today에 조회 실패·갱신 지연 및 재시도 안내를 표시한다. 오래된 발생 값은 표시하거나 알리지 않는다.
- `grid-lightning` 수집 직후 별도 낙뢰 알림 작업을 실행한다. 전체 알림과 `lightningEnabled`가 켜져 있고 유효한 설치·FCM 토큰·연령 확인 조건을 만족할 때만 선택 격자의 새 관측을 전송한다. 설치·격자·최근 발생 시각별 원자적 전송 임대와 성공 기록으로 겹친 작업/재수집/한국 날짜 변경의 중복 발송을 막는다. 실패 시에는 다음 실행에서 유효 시간 내 재시도한다. 전송 직전 설정·위치·토큰·시간을 재검사한다.
- FCM Android TTL과 APNs 만료는 관측 30분 만료 및 수집 신선도 만료 중 빠른 시각까지로 제한한다. 앱의 전경 알림도 만료 메시지는 표시하지 않는다. 알림 이동 정보는 `WEATHER_DETAILS`/`LIGHTNING`이며 Today 낙뢰 카드를 펼치고 해당 위치로 이동한다. 카드에는 선택 지역의 기상 격자, 최근 발생 시각, 최근 30분 수집 자료의 관측 횟수와 자료 확인 시각을 한국시간으로 표시한다.
- 배포 시 `0016_lightning_alerts.sql` 마이그레이션이 먼저 필요하다. 기존 전체 알림/개별 항목 기본값과 같이 새 낙뢰 설정도 기본 켜짐이며 앱 로컬 저장·서버 설정 API에 왕복 보존된다. 실제 운영의 정기 수집/FCM 환경이 활성화돼 있어야 알림이 동작한다. 이 구현 작업에서는 서버 배포·정기 수집 활성화·실제 외부 API 호출·실제 푸시 전송을 하지 않는다.

1. 국립해양조사원과 K-water는 기존 `KMA_SERVICE_KEY`에 저장된 공공데이터포털 일반 인증키를 공통으로 사용한다. 제공처별 다른 키를 쓸 때만 `KHOA_SERVICE_KEY` 또는 `KWATER_SERVICE_KEY`로 덮어쓴다. 각 API별 활용승인은 별도로 확인한다. 한강홍수통제소는 별도 인증키가 필요하고 낙뢰는 기존 `KMA_APIHUB_KEY`를 사용한다. 키를 저장소에 넣지 않는다.
2. 사용자별 지점 코드는 입력하지 않는다. 매시 서버의 `installations`에서 등록 위치를 읽고, GPS가 없으면 해당 기상청 격자의 중심 좌표를 사용한다. 국립해양조사원의 공식 관측소 목록에서 40km 안의 가장 가까운 `DT_` 조위관측소와 60km 안의 가장 가까운 `TW_` 부이를 선택한다. 조석예보는 선택된 조위관측소 코드를 사용한다. 여러 사용자가 같은 지점을 선택하면 한 번만 호출하고, 위치가 바뀌면 다음 수집에서 새 지점을 선택한다. 범위 밖의 사용자에게 해양 관측 지점을 억지로 붙이지 않는다.
3. K-water 댐은 거리만으로 사용자에게 대응시킬 수 없으므로 [공식 댐 코드 조회 API](https://www.data.go.kr/data/15099105/openapi.do)로 전국 코드를 가져와 각 댐의 자료를 공유 수집한다. 댐 코드 조회도 별도 활용승인이 필요할 수 있다. 하천 수위·유량은 한강홍수통제소의 전국 조회를 사용한다. `GRID_COLLECTION_CONFIG_PATH`는 이안류 해수욕장 코드·ROMS 영역·K-water의 별도 수위관측소 등 추가 대상을 운영자가 설정할 때만 사용한다.
4. 승인 후 `npm run node:job -- grid-hourly`, `npm run node:job -- grid-river-flow`, `npm run node:job -- grid-lightning`으로 단발 확인한다. 응답 필드와 실제 바이트를 확인한 뒤 운영 설정을 확정한다. 배포는 별도 작업이다.

### 미니 PC에서 인증키 직접 입력

배포할 때 미니 PC의 기존 `/etc/weather-care/weather-care.env`를 `sudoedit`으로 연다. 이 파일은 서버와 스케줄러의 systemd 서비스가 읽는다. 이미 운영 중인 파일을 예시 파일로 덮어쓰지 않는다. 기존 `KMA_SERVICE_KEY`가 공공데이터포털 인증키라면 국립해양조사원·K-water 키를 다시 입력할 필요가 없다. 인코딩된 키도 서버가 한 번 디코딩해서 전달한다. 아래의 별도 발급 키만 필요한 경우 추가한다.

```dotenv
NIFS_API_KEY=국립수산과학원_인증키
HRFCO_API_KEY=한강홍수통제소_인증키
```

기본 조위·부이·조석예보·K-water 댐 수집에는 `GRID_COLLECTION_CONFIG_PATH`가 필요하지 않다. 이안류·ROMS·K-water 별도 수위관측소를 추가로 수집할 때만 운영 설정을 사용한다. 기존 `KMA_APIHUB_KEY`는 낙뢰 수집에 그대로 사용한다. 인증키나 실제 운영 설정 파일을 저장소에 넣지 않는다.

## 명세 확인 결과와 남은 검증

- ROMS 공식 요청에는 예측시각 인자가 없다. 영역 bbox를 페이지 끝까지 조회해 응답의 `predcDt`별로 저장한다. 조사표의 `타일×24회`는 실제 호출 방식이 아니며, 페이지 수를 확인한 후 호출량을 다시 계산해야 한다.
- K-water 시간별 수위 기능의 출력 필드는 `flux`(수위, EL.m)와 `hourwal`(우량, mm)이다. 이 응답의 `flux`를 유량으로 해석하지 않는다. 하천 유량은 한강홍수통제소의 별도 Open API `waterlevel/list/10M.json` 응답 `FW`(㎥/s)에서 수집한다. 이 API는 전체 관측소의 최신 자료를 한 번에 반환하며, 유량값이 빈 지점은 저장하지 않는다.
- [K-water 가뭄 수위관측소 운영정보](https://www.data.go.kr/data/15056576/openapi.do)도 일일 `flux` 유량(㎥/s)을 제공한다. 현재 서버의 시간별 수집에는 한강홍수통제소 자료를 사용한다. `flux`의 뜻은 API마다 다르므로 서로 섞지 않는다.
- 해양부이 `crsp`는 cm/s, 조위관측소 `crsp`는 m/s로 문서화되어 있으므로 단위를 구분해 저장한다.
- 낙뢰 API 예제는 시간폭 인자를 `itv`로, 요청인자 표는 `dtm`으로 표기한다. 실제 승인 키의 응답으로 요청 의미와 빈 시각의 응답 형태를 확인해야 한다. 낙뢰 2MB 상한과 기존 APIHub 공용 4.5GB 보호선에 걸리면 해당 회차 수집은 실패로 기록되고 다음 작업에서 다시 시도할 수 있다.
- 조사표의 지점 50·40·100개는 설계 가정이다. 실제 호출량은 등록 사용자 위치에서 선택된 고유 관측소 수와 댐 코드 수에 따라 바뀐다. 이안류 해수욕장·ROMS 영역·K-water 별도 수위관측소는 아직 자동 위치 선택 대상이 아니며, 설정하지 않으면 호출하지 않는다. `NIFS_API_KEY`, `HRFCO_API_KEY`, `KMA_APIHUB_KEY`는 각각 지점 설정 없이 해당 수집을 실행한다.
- [국립해양조사원 조위관측소 운영 현황](https://www.data.go.kr/data/15146602/fileData.do) 60건과 [해양관측부이 운영 현황](https://www.data.go.kr/data/15146611/fileData.do) 41건의 코드·좌표를 서버 목록에 포함했다. 자동 조회는 최신 관측 API에서 확인된 `DT_` 조위 57곳과 `TW_` 부이 26곳만 대상으로 한다. `HB_`·`YS_`·`KG_` 코드는 해당 부이 API에서 오류 04를 반환했다. 이 목록은 2025-08-18 자료이므로 관측망 변경 시 갱신해야 한다. [K-water 댐 코드 조회](https://www.data.go.kr/data/15099105/openapi.do)는 코드·이름만 제공하므로 댐과 사용자 지역의 관계를 판단하는 자료로 사용하지 않는다.

## 2026-10-14 운영 API 및 격리 실행 검증

- 미니 PC의 운영 인증키를 서버 밖으로 출력하지 않고 실호출했다. 조위 관측(`DT_0018`) 17건, 부이 관측(`TW_0095`) 17건, 고저조 4건, 시간별 조석 24건과 K-water 댐 운영(`2022510`) 16건에서 정상 코드 `00`을 확인했다. 한강홍수통제소 유량과 수산과학원 해파리 목록도 격리 실행에서 저장됐다. 새 해파리 게시물이 없어 상세 조회는 이번 실행에서 발생하지 않았다.
- 새 수집 코드를 미니 PC의 임시 디렉터리와 **메모리 DB**에서 실행했다. 부산 표본 위치에서 `DT_0005`와 `TW_0087`을 자동 선택했고, 조위 관측·조석 시계열·댐 1곳·해파리 목록·하천 유량·낙뢰 일부 회차의 스냅샷 저장을 확인했다. 운영 DB·서비스·배포 디렉터리는 변경하지 않았다.
- 활용신청 전 격리 실행에서는 댐 코드 조회가 HTTP 403/인증 오류 `30`을 반환했다. 신청 완료 후 같은 운영 키로 다시 호출한 결과 HTTP 200·결과코드 `00`, 댐·보 코드·이름 59건을 확인했다. 다만 신규 수집 코드가 아직 배포되지 않아 운영 스케줄러가 전국 댐을 수집 중이라는 뜻은 아니다.
- 해양조사원은 같은 날짜·코드의 재호출에서도 간헐적으로 게이트웨이 오류 `04`를 반환했다. 수집기는 이 오류에 한해 최대 2회 더 재시도하고, 계속 실패하면 해당 스냅샷을 저장하지 않아 다음 실행에서 다시 시도한다. `DT_0005` 고저조와 `TW_0087` 부이는 격리 실행에서 재시도 후에도 실패했다. 운영 안정성은 배포 후 여러 회차의 성공률을 확인해야 한다.
- 기상청 낙뢰 탐지자료는 빈 최근 구간에서 336바이트, 공식 예시의 2015-04-18 09:00 KST ±30분 구간에서 28,611바이트·725행이었다. 현재 2MB/회 상한의 적합성은 낙뢰가 많은 시각의 실측이 더 필요하다. 격리 실행 한 회차는 응답 대기 중 시간 초과됐으며, 예약한 2MB가 사용량 장부에 남았다. 이는 **실제 응답이 2MB였다는 뜻이 아니다**.
- 현재 운영 DB에는 `grid_extra_snapshots` 테이블이 없다. 새 수집 코드와 0015 마이그레이션은 아직 배포되지 않았으므로 운영 스케줄러의 신규 수집 결과로 판단하지 않는다.
