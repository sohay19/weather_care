# 구역별 알림 운영 배포 및 기존 앱 호환 검증

2026년 10월 28일 **15:18:33 KST** 운영 서버 배포를 완료했다. **15:22:19 KST** 최종 확인에서 API·스케줄러가 정상이며 신규 런타임 오류와 실패 작업은 없었다. 배포 대상은 현재 작업 트리의 구역별 알림 기능이며 별도 커밋·push는 수행하지 않았다.

## 적용 범위

- 운영 사용자 DB에 `0004_notification_regions.sql`을 한 번 적용해 구독 설정·구역 목록·구역별 상태·특보 상태 테이블 4개와 관련 트리거를 추가했다. 기존 테이블의 열·행을 변경하지 않았다.
- 운영의 실제 설치 소스를 기준으로 필요한 런타임·마이그레이션 파일 **10개**만 적용했다. 나머지 **172개** 소스·사용자 마이그레이션 파일은 해시가 동일하다. 실행 경로는 `/opt/weather-care/releases/20261023-full-production/weather_care_server`다.
- 운영 전용 FCM 구현을 보존했다. 저장소에만 있던 별도 스토어 알림 URL 처리 등을 함께 배포하지 않았다. 환경 파일·서비스 정의·패키지·잠금·TypeScript 설정도 유지했다.
- 공용 수집기가 아직 구역 구독 테이블이 없는 시험 사용자 DB를 읽을 때 기존 설치 위치만 읽도록 호환 처리를 추가했다. 시험 서버 소스·사용자 DB 스키마·API 프로세스는 변경하지 않았다. 공용 날씨 DB 스키마도 유지했다.

## 기존 앱 동작

구역 구독이 없는 기존 설치는 종전처럼 한 지역의 알림을 받는다. 기존 두 알림 설정 API와 FCM 의미 키·클릭 목적지 계약을 유지한다. 기존 앱이 설정을 저장해도 새 앱에서 선택한 구역 목록을 덮어쓰지 않는다. 새로운 구역별 토글과 알림 클릭 시 지역 전환은 새 앱이 사용한다.

기존 사용자에게 구역별 구독을 자동 생성하지 않았다. 최종 확인에서 새 테이블 4개는 모두 0건으로, 별도 실제 사용자의 기능 선택은 없는 상태다. 알림 제목의 확인된 지역명 추가는 서버에서 적용되지만, 확인되지 않은 GPS의 동 이름은 임의로 만들지 않는다.

## 백업·데이터 보존

- 최초 마이그레이션 전 백업: `/var/backups/weather-care/regions-20261028T061316Z/users-before.sqlite`
- 최종 재배포 전 백업: `/var/backups/weather-care/regions-20261028T061816Z/users-before.sqlite`
- 백업 디렉터리는 0700, DB 파일은 0600이며 서버 안에만 보관했다. 실제 사용자 DB를 내려받지 않았다.
- SQLite 온라인 백업 후 `BEGIN IMMEDIATE` 트랜잭션 안에서 기존 모든 테이블·열·행의 해시와 건수를 비교했다. 알림 설정 **216건**, 설치·인증·토큰·개인 시간·발송 이력을 보존했다.
- `quick_check=ok`, 외래키 오류 0건, 마이그레이션 적용 기록 1건을 확인했다.

## 최초 검사 실패와 복구

첫 배포 후 새 공개 API의 인증 검사에 `User-Agent`를 누락해 Python 기본 요청이 Cloudflare의 기존 Browser Integrity Check에서 HTTP 403 / 코드 1010으로 차단됐다. 검증 도구가 이를 새 API 준비 실패로 판단해 자동으로 이전 서버 소스를 복원했다. 사용자 DB를 과거 백업으로 덮어쓰지 않았으며 추가 테이블은 유지했다.

같은 조건에서 기존 API도 403을 반환하고, 기존 검증용 User-Agent로는 정상 응답함을 확인했다. 검사 헤더와 이미 적용된 마이그레이션의 재검사 처리를 보완한 뒤 다시 배포해 정상 확인했다. 마이그레이션은 중복 적용하지 않았고 Cloudflare 보안 설정도 변경하지 않았다. 서비스 재시작은 기존 선수집 의존성을 유지했다.

복구가 필요하면 서버 백업의 이전 파일을 복원하고 신규 모듈을 제거한 뒤 서비스를 재시작한다. 추가 테이블은 이전 코드와 호환되므로 유지하고, 배포 후 사용자 변경을 잃지 않도록 사용자 DB 전체를 과거 백업으로 교체하지 않는다.
