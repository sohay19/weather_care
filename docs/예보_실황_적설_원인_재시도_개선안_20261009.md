추가로 필요한 진단 로그는 원래 출처 종류, 발표/유효시각/변수, 실제 발신 여부, 연결 신규/재사용 여부, DNS·접속·TLS·첫 헤더·본문 시간, 허용된 연결 오류 코드, 받은 바이트, 선택한 보완 회차다. 기존 예보 요청의 sourceVersion은 `issue:valid` 형식인데 안전 로그 정규식에는 콜론 형식이 없어 하위 전송 로그에서 빠진다. 소스 식별을 유지해야 공급자/서버 경로 원인을 다음 장애에서 정확히 분리할 수 있다. 인증키·URL 원문은 남기지 않는다.

‘비겨울이라 신적설 기록이 없는 상황’과는 부합하지만 ‘겨울이 아니면 API가 중단된다’는 주장은 근거가 없다. 이 API는 정상200 빈목록을 주며 겨울에도 날짜별 빈목록이 존재한다. 기록이 없는 정상 응답을 시간초과/인증실패와 구분해야 한다. 빈목록만으로 모든 GPS의 실제 적설을0으로 확정할 수는 없다. 서버가 월만 보고 임의의0을 넣으면 안 된다.

[기상청 APIHub 적설관측](https://apihub.kma.go.kr/apiList.do?apiMov=%EC%A0%81%EC%84%A4%EA%B4%80%EC%B8%A1&seqApi=2&seqApiSub=244).

해당 전용 API10/8 한 번 검사에서 **403 /149B**를 받아 중단했다. 기존 AWS 일통계 권한은 정상이나 이 적설 전용 서비스에는 현재 키 권한이 없다. 운영에 적용하려면 APIHub ‘지상관측→적설관측→적설관측자료 조회(최심적설·최심신적설)’ 활용신청 승인을 확인해야 한다. 다른 키/제공처/인프라로 우회하지 않았다.

진단은 총4호출:정상2(2,911B),시간초과1(512KB 예약 유지),권한거절1(149B)로 장부증가515,060B다. APIHub 재시도99546807B는 그대로다. 기존예산 래퍼로 실제 신규 진단 질의를 회계 처리했고 일반 수집 캐시/예보/실황을 덮어쓰지 않았다. 첫 진단은response.text()라한글 도움말은 깨졌지만 숫자6열은ASCII이며 원본 행/운영파서 결과의 일치를 검증했다. 저장JSON의 decodedTextUtf8Bytes는 디코딩 후 문자열 크기, responseBytes는 계측된 실제수신량으로 구분했다. 진단helper의후속실행용코드는바이트+EUC-KR변환으로정정했고중복외부요청은하지않았다.403JSON은UTF-8을쓰므로향후Content-Type/JSON판별에따른디코딩이필요하다.

## 4. 서버 개선안 상세

### 대기질 재시도 구조

현재 정상 수집은1시간 캐시를 재사용한다. 실패하면 성공 시각이 갱신되지 않아10분마다 다시 수집한다. 측정소 목록이 신선한 상태에서17개 시도를 모두 재시도하면 이론상17×144=2,448조회/일이며, 정상의17×24=408조회/일보다6배 많다. 측정소 목록·예보·강제 수집은 별도이며 이 숫자는 실제 계정 사용량 집계가 아니라 실패 지속 시의 상한 시나리오다.

현재 동시성3·Promise.all 구조는 한 시도의 실패로 전체 저장이 실패하지만 대기 중인 다른 시도 작업은 계속한다. 일부 성공값도 최신 전국 실측 캐시에 반영하지 못한다. 429의 일일 승인량/순간제한 구분과 어느 시도인지는 현재 로그에 없으므로 HTTP429만으로 특정 지역 책임이나 운영계정 미전환을 단정하지 않는다.

권장 동작:
- 시도별 마지막 정상값·관측시각·수집시각·실패 사유·nextRetryAt을 보존한다. 성공한 시도는 반영하고 실패한 시도의 기존 정상값은 유지한다. 합쳐진 전국 값에 한 가지 collectedAt만 적용하지 않고 관측별3시간 조건을 검사한다.
- 429이면 Retry-After를 우선하며 같은 실측 서비스의 대기 요청을 중단한다. 없으면 예를 들어15→30→60분으로 늘리고 지터를 둔다. 이미 발신한 소수 요청은 별도로 결과를 처리한다. 서버가 더 긴 Retry-After를 주면이를우선한다.
- 시간초과는 해당 시도만5→10→20분간격으로 재시도하는 예시안, 인증/권한오류는 재시도 반복 대신 설정/승인 해결 상태로 전환한다. 정상 회복 후에는1시간 주기로 돌아간다.
- 측정소 목록은 좌표/명칭의 마지막 정상본을 실측과 분리해 관리한다. 목록 갱신 실패 하나가 모든 실측 조회를 막지 않도록하고오래된목록상태·신규측정소미연결은표시한다.
- 로그에 실측/측정소/예보 엔드포인트, 시도, HTTP/resultCode,Retry-After,본문·헤더시간,실수신량,실제발신수,건너뛴수,캐시나이및실패유형을남긴다.토큰과전체URL은기록하지않는다.

### 핵심 실황 재시도 예산 보호

현재 최초24h100MB/이후400MB의 단일공통재시도통에서 실황·예보·과거이력·진단이 경쟁한다. 실패에도 안전예약량(격자파일1MB)을유지하므로장부99.55MB는실수신99.55MB와같지않다. 이 안전회계정책은제공처송신량을확정할수없는중단요청도보수적으로세는구조다.

예를 들어 같은 총액 안에서 아래처럼 용도를 나눈다. 이것은 **제안 배분이며 미적용**이다.

| 재시도 용도 | 최초24h100MB안 | 정상400MB안 |
|---|---:|---:|
| 최신30분 기온·습도·풍속 복구 |50MB |160MB |
| 최신 필수 단기예보 파일 복구 |30MB |120MB |
| 선택 실황·그 외 운영 출처 |15MB |60MB |
| 과거 보충·진단 |5MB |60MB |
| 합계 |100MB |400MB |

과거진단이자기몫을다쓰더라도현재실황몫을침범하지못하게한다. 전체일일18,000호출/4.5GB검사와용도별예약검사를원자적으로함께처리해야하며회계회피를위해provider명만바꾸는방식은안된다. 기존공통재시도와합산관측가능해야한다. 수집우선순위는현재필수3→현재선택3/최신예보→어제비교/낮은우선진단으로정하고회차·변수별임시저장으로이미받은파일을재요청하지않는다. 예산차단이면해제예정시각전에는반복예약도하지않는다.

이 배분은계절전체예산에추가되는예산이아니다. 기존400MB내부정책과4.5GB전역상한을유지하는제안이다. 실제예약량·실패율·겨울필수량을통해분배를검증해야하며어떤한도하에서도제공처장애중완비를보장할수는없다.

### 적설 결측과 다른 일 관측 항목의 가용성 분리

현재 `weatherDataComplete`는 최저기온·최고기온·강수량·적설량을모두요구한다. 적설만없어도false, 무강수(rain=0)+적설undefined이면‘하늘상태관측없음’으로표시한다. 실제기온은이미정상표시되므로모든수치를없애는코드는아니다. 문제가되는것은완비판정과날씨현상해석이다. `completedDates`는4개HTTP요청성공과기온존재로날짜완료를표시하므로적설유효값이없어도이미완료날짜로처리하는의미불일치도있다.

권장구조는최저기온/최고기온/강수/최심신적설의각각에 `AVAILABLE / NO_RECORD / UNAVAILABLE`와출처·날짜·유효값수를둔다. AVAILABLE수치0은그대로0, 정상빈목록은NO_RECORD,시간초과/권한실패는UNAVAILABLE로구분한다. 기온완비및강수완비와적설가용성은독립이다. 과거추천/표시가필요한요소의조건을각각확인하고한항목부재로다른항목을차단하지않는다.

예:최저18°/최고22°/강수0mm/적설NO_RECORD라면기온·강수는제공하고적설만‘관측기록없음’으로남긴다. 강수0은‘강수량0’이라는증거이며공식날씨현상코드없이이를‘맑음’으로바꾸지않는다. 눈은미확보값을0으로만들지않고같은날과거예보로꾸미지도않는다. 수치없는원본빈응답은매10분다시받지않고정상응답상태·제공처갱신시각에따라일단위로관리한다.

겨울에희소한양수적설지점만모아전국최근접으로무제한확장하면멀리있는눈관측이지역의눈처럼보일수있다. 현재nearestMetric은적설도제한없이전국최근접값을고르고적설출처지점은기온출처와별도표시하지않는다. 적설전용전지점응답으로명시적0/결측을구분하고,적설출처/거리/날짜를따로보존하는검증이필요하다. 기온·시정에적용한최근접보충을그대로‘눈발생지점’에적용해서는안된다.
