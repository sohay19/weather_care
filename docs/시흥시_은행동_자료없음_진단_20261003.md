# 시흥시 은행동 ‘자료 없음’ 운영 진단

최신 작업 전제(2026-10-04): **4번 단기예보 호출 한도는 운영계정 전환을 전제로 문제없음으로 분류한다.** 사용자의 계획을 반영한 표기이며 계정 전환 완료를 검증했다는 뜻은 아니다. 아래 개발계정 한도 검토는 전제 변경 전의 조사 기록이다.

2026년 10월 3일 23시대(한국 시각)에 운영 로그, 실제 운영 DB 및 제공처 응답을 확인했다. 은행동은 행정코드 `4139054000`, 예보 격자 `57/124`다.

## 확인된 원인

### 현재 관측·현재 강수·가시거리: 내부 수집 한도 소진

- API·수집기·Cloudflare Tunnel은 모두 실행 중이었다. 수집기 재시작 횟수는 0이며 정기 작업도 계속 완료되고 있었다.
- 실제 운영 DB는 `/var/lib/weather-care/weather-care-release.sqlite`다. 운영 환경의 `NODE_DATABASE_PATH`로 확인했으며 기본 경로의 이전 DB를 근거로 사용하지 않았다.
- 오늘 APIHub 내부 예약량은 **4,499,969,860바이트**다. 코드의 일일 한도 4,500,000,000바이트 중 **30,140바이트**만 남아 있어 다음 수집 예약을 승인하지 못한다. 집계 요청 수 3,447회는 18,000회 내부 제한 아래다.
- 현재 관측 로그에는 `current_observation_budget_denied`가 반복된다. 빠른 재시도의 별도 3.5GB 총량 제한은 12:52부터, 정규 수집의 이전 회차 조회는 18:10부터, AWS 대체 조회는 18:20부터 거절됐다.
- 은행동 마지막 현재 관측은 **18:08**, 저장 시각은 **18:10**이다. 30분 유효기간을 넘겨 기온·체감온도·습도·바람이 응답에서 함께 제외됐다.
- 전국 강수 자료의 마지막 저장은 **17:47**, 관측 시각은 **17:30**이다. 저장 후 40분 유효기간이 지나 GPS 상세의 현재 강수를 확인하지 못했다.
- 은행동 가시거리의 마지막 저장은 **18:30**, 관측 시각은 **17:00**, 관측소 거리는 17km였다. 거리 조건은 충족하지만 관측 후 3시간 유효기간이 지나 표시에서 제외됐다.

예약량은 실제 포털 전송량과 다르다. 제공처 조회 전에 예상 바이트를 누적하며 실패한 조회도 예약량에 남는다. 실제 APIHub 계정의 전송량 한도를 넘었다고 주장하지 않는다.

정규 전국 관측의 최신 회차 조회는 오늘 완료 로그 140회 중 성공 0회였다. 이전 회차 성공은 101회, AWS 대체가 포함된 회차는 70회였다. 정규 작업은 매 10분 시작 시 최신 회차부터 조회하고, 실패하면 이전 회차를 조회한다. 활성 지역에는 2분 재시도도 실행한다. 이 최신 회차 선조회·재시도·대체 조회 비용이 정상 수집량에 추가돼 일일 예산을 소진했다. 이는 오늘의 로그로 확인한 결과이며 모든 날짜의 제공 지연을 동일하게 단정하지 않는다.

### 단기예보: 제공처 일일 요청 횟수 초과

- 단기예보는 `apis.data.go.kr`의 별도 서비스다. 위 APIHub 바이트 제한과 구분해야 한다.
- 로그의 첫 단기예보 HTTP 429는 **18:10**이었다. 은행동에도 20:20부터 같은 오류가 기록돼 있다.
- 진단 중 은행동 20시 발표 조회는 HTTP 429와 다음 내용을 반환했다.

```json
{
  "errMsg": "LIMITED_NUMBER_OF_SERVICE_REQUESTS_EXCEEDS_ERROR",
  "returnAuthMsg": "일일 서비스 요청제한 횟수 초과 에러",
  "returnReasonCode": "22"
}
```

- 전국 예보 캐시 1,633개 중 1,107개는 14시 발표, 526개는 17시 발표에 머물렀다. 은행동은 17시 발표 자료를 사용한다.
- 현재 수집 코드는 전국 격자의 새 발표를 개별 요청하며 제공처의 일일 호출 예산을 별도로 기록·제어하지 않는다. 실패한 격자는 다음 수집 때 다시 요청한다. 해당 계정의 허용 횟수와 실제 누적 횟수는 포털에 접속하지 않아 수치로 확인하지 못했지만, 제공처의 일일 제한 초과 응답 자체는 확인했다.
- 예보 조회 예외가 발생하면 같은 지역 처리 안의 환경·지역 묶음 갱신도 건너뛴다. 따라서 이 오류는 부가 자료의 지역별 갱신에도 영향을 준다. 전국 대기질 공통 원본과 도로 통제는 계속 갱신되고 있었다.

### 기상특보: 실제 응답과 파서 형식 불일치

- 10:10부터 `WARNING_SELECTED_REGION_ROW_INVALID`가 반복됐으며, 한도 소진 전에도 이미 실패했다.
- 특보 공통 캐시는 배포 선수집 시각인 **09:57**에 머물러 45분 유효기간을 넘겼다.
- 실제 제공처 응답은 HTTP 200이며 EUC-KR 인코딩이다. 서울의 10시 건조특보 행에는 `건조, 주의, 발표, ,=` 같은 한글 항목과 추가 열이 있다.
- 서버는 UTF-8 기본값인 `response.text()`로 읽고, 파서는 특보 종류 영문 코드·단계 숫자·발표 명령 숫자로 끝나는 행만 허용한다. 전국 목록에 포함된 서울 행을 해석하지 못하면 전체 특보 수집을 실패 처리해 은행동의 특보 캐시도 갱신되지 않는다.

## 필요한 보완

1. 미발표 최신 관측 반복 조회를 줄이고, 유효한 기존/이전 관측을 고려해 재시도·AWS 대체를 결정한다. 필요한 현재 관측의 예산을 우선 확보하고 하루 전체 수집·재시도 비용을 다시 계산한다.
2. 단기예보 제공처의 실제 일일 허용 횟수를 확인하고 전국 수집·활성 지역 보충 요청·재시도를 함께 제한한다. HTTP 429 때 반복 요청을 억제한다.
3. 특보 응답을 실제 인코딩과 열 형식에 맞춰 해석하고 실자료 형태로 검증한다.
4. 예보 갱신 실패가 별도 환경 자료 갱신까지 건너뛰지 않도록 처리 흐름을 검토한다.

## 시간 초과 추가 조사와 책임 구분

사용자 요청에 따라 23시대에 요청 단계, 서버 자원, 같은 자료의 주소별·클라이언트별 응답 시간을 추가 확인했다.

### 기상청 측 응답 지연을 직접 재현

과거 격자 관측 요청의 시간 초과 96건(00:00~04:50)과 AWS 관측 시간 초과 4건은 모두 **응답 헤더 대기 중** 14,999~15,002ms에 우리 코드의 15초 제한으로 중단됐다. 본문 다운로드나 JSON/격자 파싱 중의 시간 초과는 아니었다.

기상청 APIHub가 연결하는 두 주소에 같은 호스트명·인증·자료·Accept 헤더로 요청했다. HTTPS 호스트명과 인증서 검증은 유지했다.

| 연결 주소 | TCP 연결 | TLS까지 | 첫 응답 | 결과 |
| --- | ---: | ---: | ---: | --- |
| `203.247.96.25` | 0.016초 | 0.049초 | 0.115초 | HTTP 200, 전체 0.187초 |
| `203.247.91.39` | 0.006초 | 0.028초 | 30.046초 | HTTP 504, 본문 0바이트 |

운영과 같은 Node.js 24.15.0 `fetch`에서도 외부 주소 `203.247.91.39`에 연결한 뒤 14.7초 만의 정상 응답과 30.1초 후 HTTP 504를 각각 재현했다. 기본 헤더와 운영 헤더를 모두 사용해 측정했으며, curl에서도 같은 주소의 30초·504가 재현돼 특정 Node 헤더만의 문제로 볼 근거는 없다.

**TCP·TLS는 빠르게 완료되고 기상청 측 연결 대상이 30초 후 504를 반환했다. 이 재현 사례는 외부 서버/게이트웨이의 응답 지연이다.** 기상청 내부의 백엔드 과부하·큐·파일 접근 중 어느 원인인지는 해당 운영 로그가 없어 구분할 수 없다. 이 주소도 정상 응답한 사례가 있으므로 영구 장애라고 단정하거나 특정 IP를 계속 고정할 근거는 없다.

과거 실패 로그에는 상대 주소 및 DNS·TCP·TLS 단계 시간이 없으므로 과거 모든 시간 초과를 이 주소의 동일 장애로 확정하지 않는다. AWS의 별도 `NETWORK_ERROR` 2건도 원인 코드가 없어 DNS/연결 끊김 등을 구분하지 못한다.

### 우리 쪽 문제도 실자료로 확인

- 23:20 회차 기온 조회는 HTTP 200이지만 본문이 `# dfs_file_read error (-1)` 27바이트로, 그 시점에 요청 파일을 제공하지 못했다. 23:10 회차와 과거 00:00 회차는 같은 서버에서 각각 약 0.21초·0.26초에 정상 수신했다.
- `latestGridObservationTime`에는 10분 제공 지연을 고려하는 처리가 있지만 수집기가 다시 **10분을 더해** 새 회차를 먼저 요청한다. 이 선택과 2분 재시도가 미발표 자료·느린 연결의 반복 요청을 늘린다.
- 기온 정상 응답은 341,297바이트, 미제공 응답은 27바이트였다. 내부 예약은 변수당 1,000,000바이트를 조회 전 누적하고 결과에 따른 정산이 없어 실제 수신량보다 크게 쌓일 수 있다. 포털의 실제 과금/전송량 기준은 별도 확인해야 한다.
- 제공처 단기예보 일일 요청 한도 관리와 특보 한글·열 형식 해석 문제는 우리 코드에서 보완해야 하는 사항이다.

우리 서버의 현재 부하는 0.00, 메모리 사용은 전체 약 1.36GB/7.94GB, 사용 가능한 메모리는 약 6.58GB, 디스크 사용률은 23%였다. 수집기 재시작·커널 메모리 부족 기록과 작업 중복 건너뛰기 기록은 없었다. 현재 같은 위치의 대기질·대기질 예보 API도 0.06~0.31초에 HTTP 200으로 응답했다. 지속적인 로컬 자원 부족이나 전체 인터넷 장애를 뒷받침하는 증거는 발견하지 못했다. 과거 모든 시점의 자원·네트워크 상태를 기록한 자료가 있는 것은 아니다.

에어코리아의 과거 6~10초 시간 초과는 세부 요청 단계가 기록되지 않아 최초 지연 위치를 확정할 수 없다. 현재 정상이라는 사실만으로 당시 원인을 우리 쪽 또는 제공처 쪽으로 단정하지 않는다.

### 우리 쪽 해결 방법

1. **미발표 조회 억제:** 기본은 제공 지연을 고려한 확정 회차를 사용한다. 수집기의 `+10분` 선조회와 재시도 기준을 바꾸고, 실제 발표 완료 후에만 새 회차를 요청한다. `dfs_file_read error`는 미제공 상태로 구분한다.
2. **실패 반복·대체 비용 제한:** 같은 회차/변수의 실패를 잠시 공유해 중복 요청을 막고, 2분마다 고정 재시도하는 대신 재시도 간격을 늘린다. 기존 관측이 유효하면 불필요한 AWS 대체를 건너뛴다. 현재 관측·특보 같은 필수 항목에 하루 예산을 먼저 배정한다.
3. **예약량 정산:** 예상 예약량과 실제 수신량을 분리 기록한다. 제공처 사용량 기준을 확인한 뒤 완료 응답의 예약을 정산한다. 시간 초과 요청을 실제 전송량 0으로 간주해 일괄 환급하지 않는다.
4. **제공처 일일 제한 대응:** 단기예보는 전국 1,633격자 × 8회 발표만으로 최소 13,064회/일에 보충·재시도 요청이 추가된다. 계정의 허용량을 확인해 이 수집 계획과 맞추고, 429 때 반복 요청을 억제한다. 예보 수집 실패가 독립 환경 갱신을 막지 않도록 처리한다.
5. **특보 파서 수정:** EUC-KR과 실제 한글 항목·추가 열을 처리하고 실자료 형식으로 검증한다.
6. **외부 지연 대응·추적:** 504·시간 초과에는 연결 재사용과 재시도 간격을 검토하고, 유효 캐시를 보존한다. 특정 주소를 영구 고정하지 않는다. 상대 주소·DNS/TCP/TLS·헤더 대기·본문 읽기 시간과 안전한 오류 코드를 제공처별로 기록해 다음 실패를 정확히 분류한다. 단순히 제한을 늘려도 재현된 30초·504는 해결되지 않는다.

이번 작업은 원인 조사다. 운영 코드·DB 값·서비스 설정은 수정하지 않았다. 진단용 제공처 요청은 단기예보 1회·특보 2회·격자 관측 14회·대기질/예보 3회, 총 수신 약 3.53MB이며 운영 내부 예약 집계에는 추가하지 않았다.

## 2026-10-04 요청한 네 항목의 후속 검토·로컬 수정

상시 SSH 키 인증을 확인했다. 아래 구현 변경은 로컬 작업 트리에 있으며 운영 서버에는 배포하지 않았다. 서버에서는 로그·DB 조회와 작은 제공처 표본 요청만 수행했다.

### 미발표 회차를 먼저 조회한 이유

- 변경은 `e18b3a5`의 `weather_care_server/src/collection/weatherCollectionJob.ts`에 들어 있다. 이전에는 `latestGridObservationTime(now)`가 10분의 제공 여유를 두고 직전 회차를 선택했다. 변경하면서 10분을 더해 현재 구간을 먼저 조회하게 됐다.
- 당시 인계에는 구로동 11:57 현재 관측 결측, 12:01의 11:50 관측 회복과 여섯 변수 중 하나의 오류로 전체 관측을 버리는 문제가 기록돼 있다. 해결을 위해 관측을 예보보다 먼저 실행하고, 활성 설치 격자는 2분마다 재시도하며, 최신→직전→AWS 순서로 시도했다. 코드 주석의 의도도 ‘발표가 빠른 회차는 현재 10분 구간에서 먼저 받고, 미발표면 직전 구간을 쓴다’였다.
- 따라서 지연을 줄이려는 의도는 확인되지만 현재 구간이 정각에 실제 제공된다는 근거를 검증하지 않은 설계였다. 10월 3일 정규 전국 완료 로그 140회에서 최신 회차 성공 0회·직전 성공 101회였다. 빠른 재시도에서는 일부 최신 회차 성공이 있어 항상 미발표라고 단정하지 않는다.
- 기본 수집은 제공 여유를 둔 직전 회차로 되돌리고, 최신 회차 조기 확보가 필요하면 발표 완료 확인 후 제한적으로 시도하는 편이 적절하다. 이번에는 이유 확인 요청에 따라 이 수집 로직 자체는 변경하지 않았다.

### EUC-KR·실응답 특보 파서 수정

- 두 특보 엔드포인트의 `Content-Type: text/plain;charset=EUC-KR`를 재확인했다. 현황은 1,708바이트, AWS 특보구역 매핑은 54,755바이트였다.
- `kmaWarningProvider.ts`가 응답 바이트를 명시된 charset으로 해석하도록 수정했다. charset이 없으면 엄격한 UTF-8을 먼저 시도하고 EUC-KR로 대체한다. 기존 UTF-8 응답도 지원한다.
- 종류 영문 코드와 한글 이름, 단계 숫자와 `예비/주의/경보`, 명령 숫자와 `발표/대치/해제/대치해제/연장/변경/변경해제`를 함께 해석한다. 실제 빈 ED_TM 열·12자리 해제예고 시점·끝의 `=`를 처리한다. 명령 매핑은 [기상청 특보 DB 코드표](https://apihub.kma.go.kr/static/html/attach/wrn_table.html)에 근거한다.
- AWS 매핑의 WRN_KO 뒤에 오는 SFC_STN_ID와 `=`가 지역명에 붙던 오류도 수정했다. 예: `군산(옥도면 제외),140,=` → `군산(옥도면 제외)`.
- 해제·예비·미래 발효 특보는 활성 목록에서 제외한다. 선택 지역의 모르는 형식은 여전히 오류로 처리해 ‘특보 없음’으로 숨기지 않는다.
- EUC-KR 원시 바이트를 담은 UTF-8 JSON 표본과 의미 검증을 추가했다. 전체 서버 테스트 54파일·400개, Node 통합 6파일·17개, 특보 테스트의 Node 별도 실행 15개, TypeScript 검사와 `git diff --check`가 통과했다. `test:worker`는 테스트 런타임이며 운영은 Node.js다.

### 로그로 판단한 타임아웃

10월 3일 한국 날짜의 journal을 다시 집계했다. 상세 요청 실패 102건 중 시간 초과는 격자 96건·AWS 분 관측 4건이었다. 모두 WAIT_HEADERS에서 15초 상한에 도달했으며 READ_BODY 시간 초과는 없었다. 나머지는 AWS NETWORK_ERROR 2건이었다.

현재 로그는 성공 요청의 헤더·본문 시간을 기록하지 않는다. 따라서 실패 시각이 모두 15초라는 사실로 정상 응답의 p95/p99나 최적 상한을 계산할 수 없다. 이전 실측에서는 정상 응답 약 0.17~1.06초와 느린 정상 응답 14.7초, 외부 504 약 30초를 확인했다.

- 격자·AWS 배경 수집은 **20초를 잠정 검토값**으로 제안한다. 14.7초 정상 응답에 여유를 주면서 30초 게이트웨이 실패를 계속 기다리지 않는 선택이다. 통계적으로 검증된 최적값은 아니다.
- 단기예보 기본 8초, 특보 10초, 대기질 6~10초를 일괄 20초로 늘릴 근거는 없다. 제공처별 성공·실패 시간을 따로 확보해야 한다.
- 확정에는 성공 요청도 endpoint·변수·헤더까지 경과시간·본문 시간·총시간·HTTP 상태·해석 성공 여부를 기록해야 한다. 미발표 응답과 정상 데이터 응답을 분리해 p95/p99, 15~20초 사이 정상 회복 비율을 비교한다. 인증키와 전체 요청 URL은 로그에 남기지 않는다.
- 타임아웃만 늘리면 외부 504, 미발표 선조회, 한도 소진은 남는다. 이번에는 시간 상한과 로깅 코드를 변경하지 않았다.

### 전국 기본 단기예보의 주기·한도와 모든 좌표 조건

[공공데이터포털 단기예보 안내](https://www.data.go.kr/data/15084084/openapi.do)는 개발계정 신청 가능 트래픽을 10,000으로 안내하고 운영계정은 증설 신청이 가능하다고 설명한다. 실제 이 계정의 승인 한도는 아직 확인되지 않았다. 사용자에게 현재 활용신청의 일일 허용 횟수를 요청했다. APIHub 내부 4.5GB 제한과 이 서비스의 호출 제한은 별개다.

**현재 1,633개 행정구역 대표 격자에 대한 계산**은 아래와 같다. 추가 일별 보충·재시도·첫 선수집 비용을 제외한 정상 기본 호출 수다.

| 격자별 갱신 간격 | 하루 갱신 횟수 | 기본 요청/일 | 10,000회 한도일 때 |
| --- | ---: | ---: | --- |
| 3시간 | 8 | 13,064 | 기본만으로 초과 |
| 6시간 | 4 | 6,532 | 보충·재시도 여유 3,468회 |
| 12시간 | 2 | 3,266 | 여유 6,734회 |

공식 발표가 3시간 간격이므로 매 발표를 따라가는 현재 기본 수집은 일 8회다. 10분마다 약 90~91개씩 18개 묶음을 돌려 전국 한 바퀴가 3시간 걸린다. 6시간안은 발표 회차를 02·08·14·20시로 고정하고, 발표 후 15분 여유를 둔 다음 모든 묶음을 갱신해야 한다. 단순히 타이머를 6시간으로 바꾸거나 활성 설치 지역만 조회해서는 안 된다. 활성 지역이 나머지 네 발표를 별도로 조회하면 기본 4회 외에 `4 × 활성 고유 격자 수`가 추가되고 일별 보충·재시도도 더해진다. 최악에는 다시 13,064회 이상이 되므로 추가 조회도 같은 일일 예산에 포함해야 한다.

**다만 1,633개는 모든 GPS 격자가 아니다.** 앱 `home_screen.dart`의 GPS 모드는 `KmaGrid.fromCoordinates`로 위치를 직접 격자로 변환한다. API는 해당 격자의 COLLECTED_REGION을 찾고 없으면 WEATHER_CACHE_NOT_READY(503)를 반환한다. 행정구역 대표 목록만 선수집하는 현재 구조는 목록 밖 GPS 좌표의 자료 보유를 보장하지 못한다. 6시간·6,532회 계산만으로 사용자의 ‘모든 좌표에 값을 보유’ 조건을 충족했다고 말할 수 없다.

이 조건에는 [기상청의 전국 단기예보 격자 일괄 조회](https://apihub.kma.go.kr/apiList.do?seqApi=10)를 기본 자료원으로 사용하는 방식이 적합하다. 한 번에 한 변수·한 예보시각의 149×253=37,697격자를 받는다. 23시 발표·다음날 00시 예보를 실측한 결과 TMP와 SKY 모두 HTTP 200, 각각 341,297바이트·37,697개 값이며 약 0.287초·0.217초였다. TMP 유효값은 9,295격자, SKY는 30,364격자였다. 유효 영역 밖에는 -99가 있으므로 37,697개 모두 실제 기온이 있다는 뜻은 아니다.

권장 설계는 다음 조건을 함께 갖춰야 한다.

1. 지원하는 모든 GPS 격자를 대상으로 초기 전수 선수집을 완료하고, 정기 갱신 실패 때 마지막 유효한 예보를 보존한다. 원본 발표시각과 자료 나이를 유지하고 이전 값을 새 관측으로 표시하거나 -99를 0으로 바꾸지 않는다. 원래 자료가 없는 영역은 지원 범위와 근처 자료를 사용하는 기준·출처를 명시해야 한다.
2. 전국 격자 파일은 변수·발표·예보시각으로 중복 요청을 막고 공통 저장한다. 각 좌표 응답은 공통 원본에서 읽는다. 기본 전국 일괄 갱신의 우선 검토 주기는 **12시간**, 예산 개선 후 **6시간**이다. 갱신이 느려도 저장된 시간별 예보를 현재 예보시각에 맞춰 사용하며, 최초 결측 격자를 최신 갱신보다 우선한다.
3. 9개 시간별 변수(TMP·REH·WSD·VEC·SKY·PTY·POP·PCP·SNO)를 기준으로 12시간마다 72시간 범위를 받으면 `9×72×2=1,296회/일`, 표본 크기가 같다는 가정에서 약 **442MB/일**이다. 6시간마다 48시간이면 `9×48×4=1,728회/일`, 약 **590MB/일**이다. 최고·최저기온, 재시도·초기 수집 및 48시간 화면 범위 유지에 필요한 여유 시간은 추가다. 9개 변수 전부·전체 예보 기간의 전송량은 아직 측정하지 않은 추정이다.
4. 이 일괄 방식은 공공데이터포털의 격자별 최소 호출을 크게 줄이지만 **APIHub 용량을 추가로 사용**한다. 10월 3일 내부 4.5GB 예약량이 이미 소진됐으므로 그대로 더하면 안 된다. 미발표·빠른 재시도 비용을 먼저 줄이고, 실제 수신량과 예약량을 분리해 정산한 다음 예보용 예산을 확보해야 한다. 예를 들어 12시간·72시간안은 약 0.5GB를 예보·재시도에 배정하고 나머지를 4.0GB 안에서 운영하는 설계를 검토할 수 있다. 현재 변수당 1MB 예약을 새 수집에도 그대로 적용하면 1,296MB 이상이 되어 이 계산에 맞지 않는다. 실제 제공처 전송량 기준과 파일별 최대 크기 검증이 먼저다.
5. 공공데이터포털 호출은 예산을 원자적으로 예약하고, 일일 초과 코드 22/HTTP 429 때 같은 격자·다른 회차를 반복 호출하지 않는다. 시간당 제한과 일일 제한을 구분하고, 수집 예외가 별도 환경 자료 갱신까지 막지 않도록 분리한다. 최초 수집과 보충도 동일한 예산에 넣는다.
6. ‘값이 DB에 존재함’과 ‘현재/미래 시각의 값이 있음’을 함께 검사한다. 기존 예보는 수집 시 시간별 48개만 저장하므로 갱신 후 6시간이면 미래 슬롯이 약 42개로 줄 수 있다. 48시간 범위를 계속 제공하려면 더 긴 원본을 보관하고 응답 때 필요한 48개를 선택해야 한다. 장기 장애 때 과거 값만 남았다는 사실도 숨기지 않는다.

이번 확인 시 운영 DB에는 예보 캐시 1,633개가 모두 남아 있었다. 23시 발표 188개·14시 1,086개·17시 359개였고 미래 시간별 슬롯이 없는 캐시는 0개, 최소 미래 슬롯 수는 39개였다. 이전 유효 예보는 삭제되지 않았지만, 이 확인은 목록 밖 모든 GPS 격자의 보유나 모든 상세 항목의 최신값 보장을 뜻하지 않는다.

전국 수집 주기·자료원·예산 제어는 이번에 변경하지 않았다. 사용자 필수 조건을 지키려면 대표 격자 주기만 변경하는 수준을 넘어 전국 격자 원본 저장과 전수 완료 검사를 함께 구현해야 한다.

### 2026-10-04 사용자 결정과 추가 구분

- 사용자 지정에 따라 격자 실황·AWS 제공처 기본 타임아웃을 로컬에서 30초로 변경했다. 앞선 20초 제안보다 이 결정이 우선한다. 특보·현재 관측 관련31개 테스트와 TypeScript 검사를 통과했으며 운영에는 아직 배포하지 않았다.
- 최신 회차 작업 실패를 별도 집계하면 TIMEOUT 24건·UNKNOWN 251건, 직전 회차는 TIMEOUT 8건이었다. 전국/빠른 재시도 작업 단위 집계로 변수별 상세 로그와 수가 다르다. UNKNOWN은 원본 실패 본문이 없어 모두 미발표라고 확정할 수 없다. 미발표 조회 경로 자체는 실응답으로 확인했다.
