# 날씨챙겨 Flutter App

이 프로젝트는 내부 개발 명세(앱 버전)를 기반으로 한 초기 스캐폴딩입니다.

## 구조

- `lib/main.dart`: 앱 진입점
- `lib/app.dart`: 라우팅/테마 설정
- `lib/models/*`: Recommendation/Lifestyle/Weather/Settings 모델
- `lib/services/*`: API 클라이언트 및 서비스
- `lib/features/home/home_screen.dart`: Today - Detail - Main - Week - Setting 5탭 Shell
- `lib/features/home/tabs/*`: 한 화면 Main(당겨서 새로고침용 스크롤 표면), 오늘 준비, 시간별 상세, 주간 화면
- `lib/features/settings/*`: 설치/알림 토글 중심의 설정 화면
- `../weather_care_server`: 별도 Cloudflare Workers API 서버

## 실행

```bash
cd weather_care_app
flutter pub get
flutter run
```

## 환경 변수

빌드 모드에 따라 서버를 자동으로 선택합니다. 배포할 때 설정 파일을 바꿀 필요가 없습니다.

- Debug: `https://weather-test-api.codesoha.com`
- Release / Profile: `https://weather-api.codesoha.com`

Debug에서 로컬 서버나 다른 환경을 사용할 때만 `--dart-define`으로 덮어쓸 수 있습니다.
Release / Profile은 실행 인자와 설정 파일의 서버 주소·시험 키를 무시하고 운영 서버를 사용합니다.

```bash
# Windows/macOS/Linux 데스크톱
flutter run --dart-define=SERVER_URL=http://localhost:8787

# Android 에뮬레이터
flutter run -d emulator-5554 --dart-define=SERVER_URL=http://10.0.2.2:8787
```

Git 추적 파일 `config/kma.config.json`은 Debug용 서버 주소와 시험 접근 키를 저장합니다.
별도 실행 인자 없이 IDE에서 Debug를 실행하면 시험 서버에 연결합니다.

```powershell
flutter run -d <기기 ID>
```

시험 서버는 접근 키가 없는 요청을 거부합니다. 시험 빌드는 운영 서버의 설치
인증 정보와 다른 저장 키를 사용합니다. 사용자 요청에 따라 설정 원본은 시험 접근 키를
포함해 저장소에서 관리합니다. 접근 키가 담긴 Debug APK는 공개하지 않습니다.
`config/test-server.define.json`은 삭제했으며 더 이상 사용하지 않습니다.
빌드 시 `tool/build_app_config.dart`가 Release / Profile 자산에서 시험 키를 제거하고
운영 서버 주소만 기록합니다. 원본 JSON은 변경하지 않습니다.

```bash
flutter build appbundle --release
```

현재 로컬 `config/kma.config.json`은 시험 서버로 설정되어 있습니다.
앱은 최초 실행 시 기기별 설치 ID를 생성해 보관하고, 알림 권한이 허용되면 FCM
토큰을 설치 위치와 함께 서버에 등록합니다. Firebase가 토큰을 갱신할 때도 같은
설치 ID로 서버 등록값을 자동 갱신합니다.
알림 설정과 알림 시간은 기기에 영구 저장한 뒤 설치 ID별 서버 설정으로 순서대로
동기화합니다. 서버 연결이 끊기면 로컬 설정을 유지하고 다음 실행이나 설정 변경 때
다시 동기화합니다.
준비물 요약 알림 시간은 **설정 → 알림 → 알림 시간 → 설정 시각**을 눌러
원하는 시·분으로 바꿀 수 있습니다. 오전 7시는 초기값이며, 선택한 시간은 자동으로
저장됩니다. 전체 날씨 알림과 준비물 요약 알림을 켜야 적용됩니다.
서버는 한국시간 기준 10분 단위로 확인하므로, 예를 들어 06:35를 선택하면
06:40에 발송 여부를 확인하며 실제 도착은 늦어질 수 있습니다.
운영 응답에서는 서버가 기상청 단기예보에 생활기상지수 자외선과 에어코리아 PM10·PM2.5를 병합합니다. 앱은 `current.uvIndex`, `current.pm10`, `current.pm25`를 파싱하고, 결측시 `--`를 표시합니다.

앱은 외부 날씨 API를 직접 호출하지 않습니다. `config/kma.config.json`에는
Debug에서 연결할 서버 주소와 시험 서버 접근 키만 저장합니다. 기상청 인증키는 앱에 넣지 않습니다.

```json
{
  "SERVER_URL": "https://weather-test-api.codesoha.com",
  "TEST_ACCESS_KEY": "발급받은 시험 접근 키"
}
```

Debug는 빌드 인자 → JSON → 시험 서버 기본값 순으로 설정을 적용합니다.
Release / Profile은 항상 운영 서버에 연결하며 패키징된 설정에도 운영 주소만 포함합니다.
IntelliJ 실행 구성도 다시 수정할 필요가 없습니다.

첫 날씨 조회에서는 저장된 최근 위치를 먼저 확인하고, 운영 서버의 경량 Main 응답으로
상단 날씨 카드를 우선 표시합니다. Today 상세 자료와 Week 자료는 동시에 계속 조회해
도착하는 순서대로 화면을 갱신합니다.

운영 서버가 연결되지 않거나 중앙 수집 자료가 아직 준비되지 않으면
앱은 날씨를 임의로 대체하지 않고 재시도 안내를 표시합니다. 내장 고정 데이터나
외부 API 직접 조회는 런타임 폴백으로 사용하지 않습니다.

## 광고 개발 설정

- 소형 네이티브 광고 카드는 `Today`의 현재 날씨 카드 아래, `Main`과 `Advanced`(심화 날씨 정보)의 콘텐츠
  제일 하단, `Week`의 주간 요약과 첫 날짜 카드 사이에 표시합니다. iOS에서는 광고 카드와 로딩 자리의
  상하좌우에 12px 여백을 둡니다. 각 탭을 처음 실제로
  보았을 때 해당 위치의 광고만 로드하고, 다른 탭으로 이동해도 같은 인스턴스를
  유지합니다. `Advanced`는 기본적으로 Week 광고 단위를 함께 사용하며 전용 ID를 지정할 수 있습니다.
- 앱 오프닝 광고는 설치 후 최초 실행을 제외하고 두 번째 실행부터 준비합니다. UMP가
  광고 요청을 허용하면 날씨 로딩과 광고 로딩을 병렬로 진행합니다. 광고가 먼저
  준비되면 표시하지만 Main 콘텐츠가 먼저 준비되면 이번 콜드 스타트에서는 표시하지
  않고 다음 전경 진입 기회로 미룹니다. 닫은 뒤에는 다음 전경 진입용 광고를 미리
  로드하며, 4시간이 지난 캐시는 폐기합니다.
- UMP가 현재 요청에서 `canRequestAds=true`를 반환하기 전에는 Mobile Ads 초기화와
  광고 요청을 진행하지 않습니다. 선택 변경·오류·허용 철회 시 로드된 광고를 즉시
  화면에서 제거하고 폐기합니다.
- 모든 네이티브 광고 요청에 비개인화 광고 옵션을 명시하고 광고 콘텐츠 등급 상한은 `G`로
  설정합니다. 비개인화 광고도 IP 등 광고 전송·부정 사용 방지에 필요한 처리가 전혀
  없다는 뜻은 아닙니다.
- Debug/Profile은 Google 공식 Android/iOS 네이티브 테스트 광고 단위만 사용합니다. 운영 광고
  단위 ID를 넣어도 개발 빌드에서는 사용하지 않습니다.
- AdMob 앱에 UMP 메시지가 아직 게시되지 않은 개발 환경에서 광고 위젯 렌더링만
  확인할 때는 `--dart-define=ADMOB_TEST_BYPASS_UMP=true`를 명시할 수 있습니다. 이
  플래그는 Debug/Profile의 공식 테스트 광고에만 적용되고 Release에서는 항상
  무시됩니다. UMP 동의 흐름 검증 결과로 사용하지 않습니다.
- Release에서는 코드에 포함된 플랫폼별 운영 광고 단위 ID를 기본값으로 사용합니다.
  필요하면 아래 `--dart-define`으로 빌드별 ID를 덮어쓸 수 있습니다. 유효한 운영 광고
  단위 ID가 하나라도 있으면 UMP를 확인하고, UMP가 허용한 뒤 해당 ID의 광고를
  요청합니다. ID가 없거나 형식이 잘못된 위치는 광고를 요청하지 않습니다. Week는 기존
  `ADMOB_ANDROID_NATIVE_ID`/`ADMOB_IOS_NATIVE_ID`도 하위 호환하지만 새 빌드에서는
  아래 위치별 이름을 사용합니다.
  - `ADMOB_ANDROID_TODAY_NATIVE_ID`, `ADMOB_IOS_TODAY_NATIVE_ID`
  - `ADMOB_ANDROID_MAIN_NATIVE_ID`, `ADMOB_IOS_MAIN_NATIVE_ID`
  - `ADMOB_ANDROID_WEEK_NATIVE_ID`, `ADMOB_IOS_WEEK_NATIVE_ID`
  - `ADMOB_ANDROID_EXTRA_NATIVE_ID`, `ADMOB_IOS_EXTRA_NATIVE_ID` (Advanced 전용, 미지정 시 Week 단위 사용)
  - `ADMOB_ANDROID_APP_OPEN_ID`, `ADMOB_IOS_APP_OPEN_ID`
- 기존 Android/iOS Week 배너 광고 단위는 2026-09-16 앱 코드에서 사용을 중단했습니다.
  운영 광고 단위는 다음과 같습니다. ID는 비밀값이 아니며 앱 코드의 Release 기본값으로
  포함합니다.
  - Today 네이티브: Android `ca-app-pub-6152243173470406/2970868529`, iOS
    `ca-app-pub-6152243173470406/2609362710`
  - Main 네이티브: Android `ca-app-pub-6152243173470406/3701496264`, iOS
    `ca-app-pub-6152243173470406/8223195209`
  - Week 중형 네이티브: Android `ca-app-pub-6152243173470406/8770437222`, iOS
    `ca-app-pub-6152243173470406/8762698363` (AdMob 단위 이름:
    `날씨챙겨 Week 중형 네이티브`)
  - 앱 오프닝: Android `ca-app-pub-6152243173470406/2388414592`, iOS
    `ca-app-pub-6152243173470406/5946806649`

운영 광고 송출은 UMP 메시지, 공개 방침, 스토어 연령 설정과 실기 검증이 끝날 때까지
완료 상태로 간주하지 않습니다.

## 광고 제거 결제 설정

- 광고 제거는 스토어의 1회 구매형 비소모성 상품으로 처리합니다. 기본 상품 ID는
  `ad_free_lifetime`이며 Play Console과 App Store Connect에 같은 ID의 상품을
  만들어 활성화해야 가격 조회와 구매가 가능합니다.
- 다른 상품 ID를 사용할 때는 실행·빌드 시
  `--dart-define=AD_REMOVAL_PRODUCT_ID=상품_ID`를 지정합니다. 이미 배포한 상품 ID는
  빌드 사이에서 임의로 바꾸지 않습니다.
- 앱은 스토어가 반환한 현지화 가격을 표시하고 구매·복원 결과를 수신한 뒤 구매 권한을
  기기 보안 저장소에 보관합니다. 저장된 권한이 있으면 앱 시작과 포그라운드 복귀 시,
  또는 구매 내역 복원 시 현재 스토어 권한을 다시 확인합니다. 삭제·환불 등으로
  권한이 없어졌다면 저장된 상태도 해제합니다.
  권한이 적용되면 Today·Main·Week 네이티브 광고와 앱 오프닝 광고를 즉시 제거하고
  이후 광고 요청도 차단합니다.
- iOS Sandbox 구매 내역을 지운 뒤에는 기기의 Sandbox Apple 계정에서 로그아웃하고
  다시 로그인해 거래 캐시를 비운 다음 앱을 재실행하거나 `구매 내역 복원`을 누릅니다.
- Android 실제 결제 테스트는 `com.codesoha.weathercare` 앱과 상품을 Play Console에
  등록·게시하고 라이선스 테스터 계정으로 진행합니다. 내부 테스트 설치본 사용을 권장하지만,
  패키지명이 일치하고 기기 계정이 라이선스 테스터라면 Debug/ADB 설치본도 결제 테스트가
  가능합니다.
- 현재 앱은 스토어 SDK가 전달한 구매 상태와 검증 자료를 기기에서 확인합니다. 위·변조와
  환불 상태를 서버에서 강하게 검증해야 하는 운영 정책이라면 Google Play Developer API
  및 App Store Server API를 미니 PC 서버에 연결하는 후속 보강이 필요합니다.

## 글자 크기

- 앱의 기본 글자 배율은 `1.1`이며, iOS·Android 시스템 글자 크기는 최대 `1.3`까지만
  반영합니다. 테마 글자뿐 아니라 화면에서 직접 지정한 작은 글자에도 같은 전역 규칙을
  적용합니다.
- 시스템의 디스플레이 확대는 글자 배율과 달리 화면의 논리 크기 자체를 바꾸므로 앱에서
  임의로 고정하지 않고 각 화면의 반응형 레이아웃으로 수용합니다.

## 앱 시작 경계

- 앱은 별도의 연령 확인 화면 없이 온라인 날씨 기능을 바로 준비합니다.
- Android에서는 FCM·Analytics 자동 시작을 기본 OFF로 두고 Firebase·Mobile Ads의
  조기 초기화 provider를 병합 매니페스트에서 제거했습니다. iOS도 FCM·Analytics 자동
  시작을 기본 OFF로 설정했습니다. SDK 코드는 앱에 포함되며 플러그인 등록 자체까지
  제거한 것은 아닙니다.
- 설치 등록·소유권 이전 요청의 기존 서버 계약 필드는 운영 Worker와의 하위 호환을 위해
  유지합니다. 사용자에게 연령을 질문하거나 답을 로컬에 저장하지 않습니다.

## 이동에 따른 백그라운드 알림 지역·위젯 갱신 (2026-10-21)

- 동의 전 **백그라운드 위치 갱신**은 꺼져 있다. 초기 권한 안내의 **동의하고 계속**을
  선택하면 동의를 저장하고 알림 → 사용 중 위치 → 백그라운드 위치 권한을 차례로 요청한다.
  **백그라운드 제외**를 선택하면 일반 권한만 요청한다. 이전 안내를 확인한 설치에도 새 안내를 한 번 표시한다.
- Android는 **정확한 위치 사용**이 필요하며, Android 11 이상은 별도의 권한/설정 화면에서 **항상 허용**, iOS는 **사용하는 동안 허용** 후
  **항상 허용** 승인이 필요하다. iOS 추가 팝업 시점은 시스템이 결정한다. 거부한 권한은 설정의
  **위치 권한 설정·다시 확인**에서 바꿀 수 있다. 안내와 iOS 시스템 권한 설명에 위젯·알림 목적을 명시했다.
- 항상 위치 권한·GPS 모드·전체 알림·서버 데이터 사용이 켜져 있을 때 동작한다.
- iOS는 Core Location의 큰 위치 변화 감지를 사용한다. 앱이 시스템에 의해 종료된 뒤에도
  위치 이벤트로 실행되면 네이티브 코드가 감시를 복원한다. Android는 Google Play 서비스의
  지오펜스로 현재 위치 반경 1km 이탈을 감지한다. 최초 설정·앱 복귀·재부팅·앱 업데이트에는
  짧은 WorkManager 작업으로 감시를 등록하고, 이탈 이벤트의 유효한 좌표 또는 최대20초의 새 측정으로
  서버에 전송한 뒤 감시 중심을 갱신한다. 감시 등록·위치 확보 실패는 백오프로 재시도한다.
  상시 위치 서비스와 실행 알림은 사용하지 않으며 기존 위치 서비스 전용 알림 채널만 정리한다.
  날씨 푸시 채널·권한·FCM 토큰·알림 선택값은 유지한다. Google Play 서비스가 필요하다.
  반경은 감시 조건이며 실제 감지 거리·갱신 시각을 보장하지 않는다. 강제 종료·절전·권한에 영향을 받는다.
- 이동을 감지해 서버가 위치 갱신을 수락하면 홈 위젯의 조회 위치도 새 격자·좌표로 바꾸고
  최신 날씨를 다시 받아 Android 런처/iOS WidgetKit을 갱신한다. 이전 지역 이름·행정코드와 날씨는
  재사용하지 않는다. 정밀 위치는 새 좌표를 최대 4초 동안 역지오코딩해 새 지역명을 함께 저장한다. 조회 실패 시 이전 지역명을 재사용하지 않고 날씨 조회를 계속한다. 정밀 위치를 허용하지 않으면 위젯 요청에도 격자만 사용한다.
- 수동 지역 선택·더 최신 측정·서버 변경·삭제는 늦은 이동/날씨 응답보다 우선한다. Android는
  네트워크 연결 후 위젯 조회를 최대 5회 재시도하고, iOS는 실패한 최신 위젯 갱신을 다음 이동·앱 복귀에 재시도한다.
- 서버의 최신 위치·기상 격자·알림 지역을 갱신한다. FCM 토큰과 개별 알림
  설정은 변경하지 않고, 이동 경로 이력은 추가하지 않는다. 정밀 위치가 아니면 서버에는 격자만 저장한다.
- Android는 네트워크 연결 후 최신 측정을 재시도한다. iOS는 다음 이동 이벤트·앱 복귀 때
  미전송 측정을 재시도한다. 15분보다 오래된 측정은 전송·반영하지 않는다.
- 기능·전체 알림을 끄거나 수동 지역으로 바꾸거나 서버 데이터를 삭제하면 기기 감시와
  대기 자료와 Android 지오펜스·등록/측정 작업을 중지한다. 서버의 세션 식별값으로 이전 세션·역순 측정의 늦은 반영을 막는다.
- 기기 인증정보·미전송 최신 위치는 Android Keystore 암호화 파일(백업 제외)과 iOS
  Keychain(최초 잠금 해제 후 접근, 기기 한정)에 저장한다. iOS 재설치 시 기존 감시 설정은 폐기한다.
- 앱 배포 전에 서버 DB에 **0017_background_location.sql**을 적용하고 새 서버 코드를 배포해야 한다.
  미니 PC는 기존 운영 절차의 `npm run node:db:migrate`를 사용한다. 이번 작업은 서버 배포와 기기 권한 변경을 실행하지 않았다.
- 검증: Android 네이티브 빌드·자동 검사 및 Flutter/서버 테스트. iOS의 Xcode 빌드와 양 플랫폼
  실기기의 잠금·실제 이동·재부팅·권한 철회·네트워크 복구는 별도 확인이 필요하다.

- 상시 위치 실행 알림이 없어 Android의 **실행 알림 표시 설정** 메뉴는 제거했다. 전체 날씨 알림과 개별 알림 설정은 유지한다.

## 필수 업데이트 안내

- Debug 실행은 시작·업데이트 알림 진입 시 스토어 버전 검사를 생략한다. Release/Profile은 아래 필수 업데이트 정책을 유지한다.
- Android/iOS 앱 시작 시 스토어에서 현재 기기에 설치 가능한 새 버전을 확인하면 업데이트 완료 전까지 홈·권한 안내·광고 시작을 차단한다.
- 팝업에는 ‘업데이트’ 버튼만 제공하며 바깥 터치·뒤로가기·스토어 열기만으로 넘어갈 수 없다. 스토어에서 돌아오면 자동으로 다시 확인한다.
- 업데이트 푸시로 시작하거나 실행 중 푸시를 열어도 같은 확인을 거친다. Release/Profile에서 조회 실패·시간 초과·스토어 미등록·Play 조회 불가 시 홈을 열지 않고 재시도를 제공한다.
- 현재 iOS에서 설치할 수 없는 새 버전은 기존 호환성 기준에 따라 필수 대상으로 보지 않는다. 웹·데스크톱에는 모바일 스토어 확인을 적용하지 않는다.
- 기존 배포 앱에는 이 변경이 소급 적용되지 않는다. 이 코드가 포함된 새 앱을 배포·설치한 뒤부터 적용된다.
- `store/preview_app_update.dart`는 별도 applicationId의 디버그 앱으로 실행하는 예시 진입점이다. 실제 앱 시작 경로에는 예시 응답이 없다.

## 출퇴근 경로 알림 시간

- `설정 → 알림 → 출퇴근 알림 시간`에서 출근과 퇴근의 시작·종료 시각을 각각 지정한다. 기본값은 출근 `07:00~10:00`, 퇴근 `17:00~20:00`이다.
- 시간은 기기에 저장하고 기존 알림 설정 API로 서버에 동기화한다. 서버가 해당 구간 안에서만 도로통제 알림을 발송하며 준비물 요약·다른 날씨 알림은 기존 설정을 따른다.
- 시작 시각은 포함하고 종료 시각은 제외한다. 시작보다 종료가 이르면 다음 날까지 이어지는 구간이다. 시작·종료가 같은 설정은 허용하지 않는다. 기기·통신 상태에 따른 실제 수신 지연은 가능하다.
- 앱을 배포하기 전에 서버의 출퇴근 설정 마이그레이션·API·스케줄러를 먼저 적용해야 한다. 이전 서버의 엄격한 설정 API는 새 시간 필드를 거부한다.
- 창을 띄우지 않는 실제 설정 화면 캡처: `flutter test store/capture_commute_settings_test.dart`. 결과는 `build/previews/notification-settings-{light,dark}.png`, `commute-settings-{light,dark}.png`와 `commute-time-picker-{light,dark}.png`에 저장된다.

## 구역별 알림

- 구역 메뉴의 각 스위치로 현재 위치와 저장 지역의 알림을 별도로 선택한다. 행을 누르는 날씨 조회 지역 선택과 알림 선택은 서로 독립적이다. 새 구역은 기본 OFF이며 기존 앱 설정을 처음 읽으면 이전 알림 대상 한 곳만 유지한다. 전체 알림 OFF가 우선하고 지역별 선택은 보존한다.
- 알림 제목은 확인된 지역명을 동까지 표시한다. 숫자 동 이름의 표시 규칙도 앱과 같다(구로제3동 → 구로3동). 알림을 누르면 발송 당시 격자와 지역명을 열며 알림 구독은 바꾸지 않는다. 앱 종료 상태와 실행 중 클릭 모두 같은 지역 데이터를 사용한다.
- GPS 알림은 화면에서 보고 있는 수동 지역과 분리한다. 다른 지역을 보더라도 허용된 위치를 확인해 현재 위치 알림을 갱신한다. 앱 밖의 갱신에는 기존 백그라운드 위치 설정·권한이 필요하며, 현재 위치 알림/전체 알림을 끄면 감시를 중지한다. 수동 선택한 홈 위젯은 GPS로 덮어쓰지 않는다.
- 기기 저장 뒤 서버 동기화에 실패하면 구역 메뉴에 이전 설정으로 발송될 수 있다는 안내와 재시도 버튼을 표시한다. 지역별 설정은 별도 API를 사용하므로 서버 DB·API·스케줄러를 먼저 업데이트해야 한다. 기존 앱은 기존 API로 한 지역의 알림을 계속 받는다.
