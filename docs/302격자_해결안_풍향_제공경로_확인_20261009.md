# 302격자 해결안과 풍향 파일 제공 경로 확인

2026-10-09 후속 조사. 이번에는 해결 방법의 실자료 검증과 원인 대조를 진행했으며, 런타임 구현·배포·앱 변경은 하지 않았다. 기상청 내부 파일 생성·조회 조건은 문의 제출 승인 및 담당자 답변이 남아 있다.

## 결론과 전수 검증

**302격자는 동일 격자의 공공데이터포털 단기예보로 보충할 수 있다.** 가까운 격자의 값을 복사하기 전에 같은 `nx/ny`의 지점별 예보를 사용한다. 지역명은 기존 실제 GPS 경계 판정을 그대로 유지한다.

대상은 09:20의 10분 실황 기온·습도·풍속이 결측이었던 육지 교차 302셀이다. 기존 운영 `KMA_SERVICE_KEY`로 `getVilageFcst`의 10/9 05시 발표를 전수 조회했다. 인증키·URL·오류 원문은 출력하지 않았다. 같은 격자·같은 발표를 반환했는지도 확인했다.

| 확인 항목 | 결과 |
|---|---:|
| 검사 대상 결측 셀 | 302 |
| 10/9 10시 예보 기온·습도·풍속 유효 | 302/302 |
| 반환된 모든 유효시각의 기온·습도·풍속 누락 | 0셀 |
| 10/12 03~10/13 00의 8시각 풍향·풍속 모두 유효 | 302/302 |
| 인증·요청 실패 | 0 |
| 대조용 정상 셀 포함 실제 요청 | 303회 |
| 본문 수신량 | 36,865,972B |

조도면 `(42,52)`과 태안 근흥면 `(35,106)`은 APIHub 같은 발표의 TMP/REH 파일에서 `-99`지만 지점별 예보에서는 정상이다. 이전의 ‘예보도 283셀 결측’은 **APIHub 전국 격자 파일의 결측**이며, 다른 공식 제공 경로에도 예보가 없다는 뜻은 아니다. 10분 실황 원본의 결측은 여전히 남는다.

검증 자료: [302셀 전수 결과](302격자_지점예보_전수검증_20261009.json), [같은 발표의 전국 격자 대조](302격자_전국격자_지점예보_대조_20261009.json).

## 권장 구현

1. 전국 격자 파일을 기본 원본으로 계속 수집하고 저장한다.
2. 육지 교차 셀에서 핵심 예보가 결측이면 같은 `nx/ny`의 공공데이터포털 단기예보를 발표 회차별로 사전 수집한다. 현재 보수적 확보 대상은 위 302셀이다. 새 경계·제공 범위 갱신 시 대상 목록을 다시 판정한다.
3. 지점별 응답은 별도 원본 캐시에 보관한다. 요청 좌표·발표·유효시각·전체 행 수를 검증하며 다른 발표나 다른 격자를 섞지 않는다. 같은 발표여도 제공 경로별 정밀도 차이가 있으므로 지점별 응답 묶음의 출처를 유지한다.
4. API 요청 시 GPS 지역 판정과 `nx/ny`는 유지하고, 핵심 격자 예보를 사용할 수 없으면 해당 셀의 지점별 캐시를 선택한다. 응답의 역할은 `FORECAST`다. 실황 캐시를 덮어쓰거나 관측으로 표시하지 않는다.
5. 지점별 수집 실패 시 이전 유효 발표의 캐시를 유지하고 나이·결측을 표시한다. 정규 회차별 중복 방지·동시성 제한·30초 타임아웃·재시도 예산·출처별 로그를 둔다.
6. 현재 캐시 조회 계약을 유지하면 이 예보 보충 자체는 서버에서 적용할 수 있다. 10분 실황·어제 동시각 비교를 예보로 만드는 것은 별도 정책이며 이 해결안에 포함하지 않는다.

### 전체 응답과 페이지 처리

전일 17시 발표의 정상 지점 요청은 **1,052행**이다. 기존 `numOfRows=1000,pageNo=1`만 요청하면 마지막 일부 시각·변수가 잘린다. 진단에서 `numOfRows=2000`은 1,052행 전체를 반환했다.

구현에서는 큰 페이지 크기를 사용하더라도 `totalCount`와 실제 수신 행 수를 대조하고 필요 시 추가 페이지를 읽어야 한다. 마지막 날짜까지 있다는 이유만으로 모든 변수가 있다고 판단하면 안 된다. 발표·좌표와 페이지 중복·누락도 검증한다. [17시 발표 전수 응답 대조](풍향_전일17시_지점예보_대조_20261009.json).

이 페이지 제한은 지점별 보충을 구현할 때의 별도 주의점이며, 페이지 인자가 없는 APIHub 전국 VEC 파일의 0B 응답 원인이 아니다.

### 추가 한도 예상

한 요청으로 발표의 전체 기간을 확보할 수 있고, 302셀 모두 매 3시간 발표 8회를 갱신하는 보수적 계산이다. 기존 정상 지점까지 전부 개별 조회하는 계산이 아니다.

| 구분 | 비겨울 | 겨울 |
|---|---:|---:|
| 필수 지점 예보 요청 | 302×8 = 2,416회/일 | 2,416회/일 |
| 재시도 10% 가정 | 242회/일 | 242회/일 |
| 합계 | 2,658회/일 | 2,658회/일 |
| 현재 표본 크기·재시도 가정 기준 수신량 추정 | 약 0.3~0.4GB/일 | 약 0.3~0.4GB/일 |
| 공공데이터포털 공개 개발계정 기준 | 10,000회/일 대비 약 26.6% | 약 26.6% |
| 이 해결안에 따른 APIHub 추가 요청 | 0 | 0 |

공공데이터포털과 APIHub는 호출 한도를 구분해야 한다. 기존 APIHub 장부에 이 지점별 요청을 넣지 않는다. 이 계산은 현행 예보기간·큰 페이지 1회 기준이며, 페이지가 늘거나 다른 동일 서비스 기능을 함께 쓰면 합산한다. 실제 운영키 승인 트래픽은 별도 확인이 필요하다. 공식 안내는 개발계정 10,000, 운영계정은 활용사례 등록 후 증설 신청 가능으로 되어 있다. [공식 서비스·트래픽 안내](https://www.data.go.kr/data/15084084/openapi.do).

### 10분 실황까지 숫자가 필요한 경우

지점 예보 보충은 예보 문제를 해결한다. 302셀의 10분 실황을 원래 관측값으로 복구하지는 못한다.

같은 시각의 유효 실황 셀에서 가장 가까운 곳을 찾은 중심점 거리 결과는 10km 이내 220개, 15km 이내 260개, 20km 이내 280개이고 최대 51.54km다. 무조건 가장 가까운 값을 쓰면 외딴섬에 먼 육지 관측이 붙을 수 있다. 인근 실황을 허용하려면 실제 GPS 기준 거리·원본 격자·시각·보충 표시와 거리 제한을 별도 정책으로 정해야 한다. 원본 셀의 실황으로 저장하거나 비교에 섞지 않는다. [인근 원본 후보 전수](302격자_인근원본_보충후보_20261009.json).

공공데이터포털의 정시 초단기실황은 공식 설명상 대표 AWS 관측값을 제공하며 10분 실황과 주기가 다르다. 사용자 요청으로 제거한 AWS 대체를 되살리는 해결안으로 사용하지 않았다.

## 누락된 8파일의 원인 대조

문제 변수는 풍속 WSD가 아니라 **풍향 VEC**다. 05시 발표의 8시각 WSD 파일은 운영 DB에 모두 저장되어 있으며, VEC만 없다.

같은 발표·시각·정상 지점 `(71,130)`에서 공공데이터포털이 반환한 VEC는 다음과 같다.

| 유효시각(KST) | VEC(도) | APIHub 전국 VEC |
|---|---:|---|
| 10/12 03 | 70 | 빈 응답/시간초과 |
| 10/12 06 | 59 | 빈 응답/시간초과 |
| 10/12 09 | 73 | 빈 응답/시간초과 |
| 10/12 12 | 75 | 빈 응답/시간초과 |
| 10/12 15 | 169 | 빈 응답/시간초과 |
| 10/12 18 | 180 | 빈 응답/시간초과 |
| 10/12 21 | 27 | 빈 응답/시간초과 |
| 10/13 00 | 90 | 빈 응답/시간초과 |

**확인한 범위:** 해당 연장 시각의 풍향 예보는 공식 지점 서비스에서 제공된다. 따라서 전체 풍향 예보 자체가 없거나 우리의 발표 시각이 아직 도래하지 않은 문제로 설명되지 않는다. 문제는 APIHub typ01 전국 VEC 격자의 생성·게시·조회 또는 제공 범위 경로에 있다. 본문 0B는 파싱 전에 수신 단계에서 확인했으므로 우리 인코딩·파서가 값을 버린 원인도 아니다.

APIHub typ02의 지점별 비교는 현재 인증으로 HTTP 403이 나와 1회 후 중단했다. 활용 승인·접근 권한 확인이 필요하며, 해당 경로가 정상 자료를 제공한다고 단정하지 않는다. 위 정상 대조는 먼저 확인된 공공데이터포털의 기존 승인 키로 수행했다. [권한 대조 기록](풍향_지점API_권한대조_20261009.json).

### 아직 확정하지 못한 내부 원인

VEC 격자 파일을 연장일에 생성하지 않는지, 파일은 있으나 조회 프로그램이 예보기간 확대 전 종료 조건을 적용하는지, 지점 API와 다른 제공 정책이 있는지는 기상청 내부 로그·구현 확인이 필요하다. 공개 규격은 예보기간 확대와 풍향을 안내한다. 3개 발표에서 예전 종료 구간 이후만 실패하는 패턴은 범위 조건 문제의 후보지만 내부 코드의 결함으로 확정하지 않는다. [공식 규격](https://apihub.kma.go.kr/apiList.do?seqApi=10).

이 정확한 내부 이유와 수정 계획을 질문하는 [기상청 문의 초안](기상청_풍향_연장격자_문의초안_20261009.md)을 준비했다. 외부 게시판 제출은 사용자 승인 대기이며, 문의 접수·담당자 답변은 아직 없다.

풍향 복구는 먼저 제공처의 격자 경로 수정이 정확한 해결이다. 서버에서 먼저 보완하려면 동일 격자의 공식 지점별 예보를 캐시하거나 UUU/VVV로 유도한 방향임을 표시하는 방법이 있다. 후자는 정밀도·무풍·결측·정상 VEC 대조가 필요하며 공식 VEC와 같은 숫자를 보장하지 않는다. 이번에는 어느 방법도 운영에 적용하지 않았다.

이번 진단의 공공데이터포털 조회는 첫 표본 3회 + 전수 303회 + 17시 발표 1회 = 307회다. APIHub typ02 비교는 1회, 403/149B이며 기존 예산 보호로 정산했다. 운영 소스·캐시 내용·앱은 변경하지 않았다.
