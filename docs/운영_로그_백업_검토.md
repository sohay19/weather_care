# 운영 로그·백업 정책 검토

검토일: 2026-09-11

## 최신 Workers 로그 정책 — 2026-09-11

- 사용자 승인: 개인정보 출력 제거 및 Workers Logs 저장 중단. 이전의 무료 3일 보관은
  신규 로그 저장 정책이 아니라 변경 전에 저장된 로그에 대한 플랫폼 기준이다.
- `observability.enabled=false`, 로그·invocation·persist 및 trace enabled/persist=false로 구성했다.
- 알림 로그에서 설치 ID/지역 키/좌표 키/알림 키를 제거하고 유효한 HTTP 상태만 허용한다.
  날씨 오류 로그의 격자를 제거했다. 오류명은 고정 허용 목록, 메시지/스택/cause는 출력하지 않는다.
- Hono 기본 예외 출력 대신 고정 JSON 오류를 사용하고 cron 예외는 원문 없는 실패로 전달한다.
- Workers 스킬의 기본 로깅 활성화 권장보다 사용자가 승인한 개인정보 최소화 정책을 우선한다.
  공식 문서와 설치된 Wrangler 스키마로 설정을 확인했다.
- 코드/로컬 검증 완료, 운영 배포 결과는 다음 기록에서 확인한다. 과거 로그 삭제, Cloudflare
  내부 보안 기록 삭제, 실시간 tail/다른 외부 수집기까지 차단했다고 확대하지 않는다.
  실시간 운영 tail은 사용자 요청 정보가 보일 수 있어 기본 검증 수단으로 사용하지 않는다.

아래 표의 변경 전 코드 상태는 조사 이력이며 현재 구현보다 우선하지 않는다.

최신 확정: 미니PC **릴레이 로그만 분리해 3일 보관**하도록 사용자 동의를 받았다.
`weather_care_relay/deploy/install-relay-logging.sh`와 전용 journal·정리 타이머를 준비했다.
직접 SSH 인증은 거부됐지만 사용자가 수정 스크립트를 실행해 **운영 설정을 적용했다**.
제공 결과에서 health 200, relay active, 전용 namespace, 3day/15min 설정 및 타이머
최근·다음 실행시각을 확인했다. 정리 서비스 상태 확인 후 사용자가 성공을 보고했다.
3일 경과 삭제 실증은 별도 미확인이다. 적용·검증·복구 절차는
[릴레이 README](../weather_care_relay/README.md#릴레이-로그만-3일-보관)를 따른다.
공용 journal/rsyslog와 기존 공용 로그는 그대로 둔다. 파일 회전·정리 주기로 인한
삭제 지연이 있어 개별 로그의 정확한 72시간 즉시 삭제를 보장하지 않는다.
아래의 미니PC 기간 미확정 기록은 이 확정 이전의 검토 이력이다.

상태: **무료 요금제 기준 확정, 실제 설정 확인·구현은 별도 진행**. 2026-09-11 사용자가 무료 요금제 기준 진행을 선택했다. Workers Logs 3일, D1 복구 이력 7일을 기준으로 한다. 요금제를 실제 조회·변경하거나 설정 변경·배포를 완료한 문서가 아니다. 미니PC의 기간과 복원 방식 등 나머지 권장안까지 이 답변만으로 확정하지 않는다. 정식 개인정보처리방침 또는 법적 준수 검토를 대신하지 않는다.

- `서버 내 나의 데이터 삭제`는 운영 DB의 해당 설치 데이터를 인증 후 삭제한다. 로그·백업·외부 SDK 정보까지 즉시 삭제하는 기능은 아니다.
- 이번 항목은 앱 서버의 장애 진단 로그, 복구용 DB 이력, 복원 후 삭제 정보의 재사용 방지를 다룬다. Firebase/광고 서비스 설정은 다음 별도 항목이다.

## 플랫폼이 제공하는 기간

2026-09-11 공식 문서 기준이다. 계정의 실제 요금제와 설정을 확인한 뒤 공개 방침에 정확한 기간을 반영해야 한다.

| 구분 | Workers Free | Workers Paid | 출처 |
| --- | --- | --- | --- |
| Workers Logs | 3일 | 7일 | [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/) |
| D1 Time Travel 복구 가능 이력 | 7일 | 30일 | [D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/) |

Time Travel은 자동으로 제공되며, 과거 시점으로 복원해도 더 오래된 복원 지점이 함께 삭제되지는 않는다. DB 내보내기를 별도로 저장하면 기본 복구 기간보다 오래 남길 수 있으므로 별도 점검 대상이다. 복구 가능 기간을 제공자의 모든 내부 사본에 대한 즉시 물리 파기 보장으로 표현하지 않는다.

## 권장안

### 1. 운영 로그 — Workers 3일 기준, 미니PC는 별도 확인

- 오류 종류, 처리 결과, 응답 상태, 소요 시간, 집계 건수처럼 장애 진단에 필요한 항목만 허용한다.
- 설치 식별자, 사용자 좌표/격자, FCM 토큰, 인증키, 인증 헤더, 원본 요청·응답 본문은 기록하지 않는다. 사용자 값이 포함된 전체 URL이나 오류 메시지도 그대로 기록하지 않는다.
- 자동 호출 로그 및 플랫폼이 붙이는 메타데이터도 확인한다. `invocation_logs` 하나를 끄는 것만으로 모든 로그에서 사용자 정보가 사라진다고 단정하지 않는다. 요구를 충족하지 못하면 해당 로그 수집을 끄는 방안까지 검토한다.
- Workers Logs는 사용자가 선택한 무료 기준 3일로 진행한다. 별도 장기 보관용 전송·다운로드를 운영 관행으로 추가하지 않는 것을 권장한다.
- 미니PC의 앱 릴레이 로그도 최대 7일을 목표로 실제 저장 경로와 회전/만료 방식을 확인한다. 다른 서비스의 시스템 로그나 백업을 일괄 삭제·변경하지 않는다.
- 변경 전에 남은 로그가 소급해서 정제되거나 즉시 삭제된다고 안내하지 않는다.

### 2. 복구용 DB 이력 — D1 기본 제공 범위만 이용

- D1 Time Travel은 사용자가 선택한 무료 기준 7일로 진행한다. 개인 데이터가 포함된 별도 장기 DB 백업은 새로 만들지 않는 것을 권장한다.
- 운영 데이터 삭제 이후에도 기존 복구 이력에는 삭제 전 정보가 한동안 남을 수 있음을 구분해서 안내한다. 평상시 조회·알림 발송에 사용하지 않는다.
- 계정 내 내보내기와 미니PC/Proxmox에 앱 사용자 데이터 사본이 있는지 추가 확인한다. 발견 시 위치·권한·만료를 따로 정하며, 존재를 확인하지 않고 삭제 완료를 약속하지 않는다.
- 릴레이 설정·비밀값 백업은 사용자 DB 백업과 구분해 점검한다. 이 권장안으로 미니PC의 모든 백업을 없애지 않는다.

### 3. 복원 — 과거 사용자 정보는 운영에 재투입하지 않음

- 삭제 정보가 다시 살아나는 일을 막기 위해, 과거 DB에서 사용자 등록정보·인증·설정·발송 이력을 복구해 그대로 서비스하지 않는 방식을 권장한다.
- 공용 기상자료 등 필요한 비개인 데이터만 복구하는 것을 우선한다. DB 전체 복원이 불가피하면 API와 예약 발송을 중단하고, 복원된 개인 데이터가 남지 않았음을 확인한 뒤 서비스를 재개하는 절차가 필요하다.
- 이 방식에서는 삭제하지 않았던 이용자의 서버 등록도 복구하지 못할 수 있다. 기기에 남은 지역·설정·체크 기록과는 별개이며, 이용자가 명시적으로 서버 기능을 다시 사용하도록 하고 알림은 꺼진 상태에서 시작한다.
- 복원 안내와 재등록의 실제 앱 동작은 구현·검증이 필요하다. 이번 검토에서는 실제 DB 복원이나 사용자 정보 삭제를 수행하지 않는다.
- 사용자별로 선별 복원하는 방식을 선택하려면 복원 대상 DB 밖에 별도 삭제 기록을 두는 등 추가 설계·보유정책이 필요하다. 이번 권장안에는 영구 삭제 식별자 기록을 추가하지 않는다.

## 확정 이후 작업

1. 실제 요금제, 로그 전송·다운로드, 미니PC 보관/백업 설정을 읽기 전용으로 확인한다.
2. 승인된 로그 항목 제한과 자동 로그 설정을 구현하고 민감한 요청값이 남지 않는지 합성 데이터로 검증한다.
3. 복구 절차와 서비스 중단·재개 조건, 사용자 재등록 안내를 구현·검증한다. 운영 DB를 시험 복원하지 않는다.
4. 확인된 범위만 앱 안내와 개인정보처리방침 준비 문서에 반영하고, 코드 변경은 테스트·커밋 후 배포한다.

## 미니PC에서 확인할 내용

무료 요금제의 3일/7일은 Cloudflare 기준이며 Ubuntu/Proxmox에 자동 적용되지 않는다.

1. Ubuntu 릴레이 로그가 journal 또는 별도 파일 중 어디에 기록되는지, 보관기간·용량 제한이 있는지 확인한다. 로그 원문이나 `/etc/weather-care-relay.env`의 비밀값은 공유하지 않는다.
2. Proxmox의 Datacenter → Backup에서 Ubuntu VM이 대상인지, 주기·보관 규칙·저장 위치를 확인한다. 해당 VM의 Backup과 Snapshots에서 실제 남아 있는 백업/스냅샷도 확인한다. 다른 VM 설정을 변경하지 않는다.
3. 별도 NAS/외장 저장소/수동 파일에 DB 내보내기나 릴레이 로그·환경설정 사본이 있는지 확인한다. 파일 내용이나 인증키를 보내지 않고 사본 유무·위치 종류·기간만 확인한다.

첫 확인은 Ubuntu에서 아래 읽기 전용 명령으로 수행한다. 시스템 전역 journal 설정이므로 다른 서비스에도 영향을 주는 설정을 즉시 바꾸지 않는다.

```sh
systemctl show weather-care-relay.service -p StandardOutput -p StandardError -p LogNamespace
systemd-analyze cat-config systemd/journald.conf | grep -E '(^# /|^[[:space:]]*(Storage|MaxRetentionSec|SystemMaxUse|RuntimeMaxUse|MaxFileSec)[[:space:]]*=)'
```

`LogNamespace`가 있으면 해당 네임스페이스 설정을 추가 확인한다. 기간 설정이 출력되지 않는다고 로그가 없거나 이미 삭제됐다고 판단하지 않는다. 실제 운영 PC에 이 명령을 실행하거나 보관/삭제 설정을 변경한 상태는 아니다.

### 사용자 제공 결과 — 2026-09-11

- `StandardOutput=journal`, `StandardError=inherit`, `LogNamespace=`: 릴레이 표준 출력/오류는 기본 journal을 사용하며 별도 로그 네임스페이스는 없다.
- 설정 조회의 지정 항목(Storage/MaxRetentionSec/SystemMaxUse/RuntimeMaxUse/MaxFileSec)에는 활성 설정이 출력되지 않았다. 이 항목을 명시적으로 덮어쓰지 않은 것으로 보이며, 실제 보관기간·무기한 보관·로그 부재를 뜻하지 않는다.
- `/usr/lib/systemd/journald.conf.d/syslog.conf`가 목록에 있다. 파일명만으로 syslog 전달이 켜졌다고 단정하지 않는다. 기존 필터가 ForwardToSyslog를 제외했으므로 다음으로 해당 설정과 rsyslog 실행 여부를 확인한다.
- 다음 읽기 전용 명령: `systemd-analyze cat-config systemd/journald.conf | grep -E '^[[:space:]]*ForwardToSyslog[[:space:]]*='`, `systemctl is-active rsyslog.service`. 출력이 없거나 inactive여도 다른 로그 수집 경로 전체가 없다는 증거는 아니다.
- 공용 journal 보관기간을 바꾸면 다른 서비스 로그에도 영향을 줄 수 있으므로 아직 전역 설정 변경이나 기존 로그 삭제를 안내하지 않는다. 필요하면 릴레이 로그 분리를 검토한다. [systemd 공식 설명](https://www.freedesktop.org/software/systemd/man/252/journald.conf.html)

### syslog 추가 결과 — 2026-09-11

- 사용자 제공 결과 `ForwardToSyslog=yes`, `rsyslog.service=active`로 전달 활성화와 서비스 실행을 확인했다. 실제 릴레이 로그가 특정 파일에 저장됐는지, 보관기간이 얼마인지는 아직 확인하지 않았다.
- 다음은 rsyslog 설정에서 `/var/log/` 경로가 있는 활성 줄과 `/etc/logrotate.d/rsyslog`의 회전 설정을 읽기 전용으로 확인한다. 경로 필터는 동적 경로·다른 위치·추가 조건/전달 규칙을 전부 보여주지는 않는다. 기본 회전 파일이 없으면 오류 그대로 확인하며 임의 생성하지 않는다.
- journal과 syslog 파일 사본은 별도 관리 대상이다. 공용 journal 설정만 바꾸어 전체 로그 보관정책을 완료했다고 판단하지 않는다. 실제 로그 원문·인증값은 공유하지 않는다. [rsyslog 파일 설정](https://docs.rsyslog.com/doc/getting_started/basic_configuration.html), [Ubuntu logrotate 설명](https://manpages.ubuntu.com/manpages/jammy/man8/logrotate.8.html)

### syslog 저장·회전 규칙 결과 — 2026-09-11

- 사용자 출력에서 `50-default.conf`의 `*.*;auth,authpriv.none -/var/log/syslog`를 확인했다. 일반 로그를 syslog 파일로 보내는 규칙이 존재한다. 필터 앞의 중단 규칙이나 실제 릴레이 기록까지 확인한 것은 아니다.
- `/etc/logrotate.d/rsyslog`: syslog/mail/kern/auth/user/cron 로그 묶음에 `weekly`, `rotate 4`, `missingok`, `notifempty`, `compress`, `delaycompress`, `sharedscripts` 및 rsyslog 회전 후처리가 설정됐다.
- 주 단위 회전·이전 파일 4개 보관이며 현재 파일은 별도다. 정상 주간 회전이 계속되는 경우 약 4~5주 범위의 기록이 남을 수 있으나 정확한 28일 또는 35일 만료 보장은 아니다. 빈 파일의 회전 생략, 작업 실패/중단과 추가 전역 설정에 따라 달라지며 실제 작업 성공·파일 목록은 미확인이다. 압축은 삭제가 아니다.
- 이 규칙을 일괄 수정하면 인증·커널 등 다른 시스템 로그에도 영향을 준다. 릴레이 로그만 별도 관리하는 설계를 우선 검토하며 이번에는 변경하지 않는다. 다음 사용자 확인은 Proxmox Datacenter → Backup의 예약 작업 목록이다. 목록이 비어 있어도 수동 백업/스냅샷이 없다고 단정하지 않고 VM별로 이어 확인한다.

### Proxmox 예약 백업 확인 — 2026-09-11

- 사용자가 Proxmox 데이터센터 → 백업의 빈 작업 목록 화면을 제공하고 백업을 정한 적 없다고 설명했다. 현재 화면상 예약 백업 작업 없음으로 기록한다. 이번 점검을 위해 백업을 새로 만들지 않는다.
- 이 화면만으로 VM별 수동 백업·스냅샷 또는 다른 저장소의 사본 부재까지 확인한 것은 아니다. 해당 범위는 미확인으로 남기고 당장 추가 백업 설정이나 삭제를 수행하지 않는다.
- 다음 작업은 기존 요청인 Ubuntu 릴레이 전용 로그 분리·보관 설정이다. 미니PC 보관기간은 Cloudflare 무료 기준과 별도로 미확정이며 3일로 맞출지 사용자 확인이 필요하다. Proxmox 관리 화면 진입과 예약 백업 점검은 사용자 제공 화면으로 확인했으나 에이전트가 원격 설정을 변경하지 않았다.
