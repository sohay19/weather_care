# 전국 모든 좌표 수집·캐시 설계와 API 한도 계산

> 2026-10-04 후속: 전국 GPS 전환의 로컬 구현을 완료했다. 이 문서의 미완료 표기·이전 예산은 작업 이력이다. 최신 구현·예산·제약은 [전국 GPS 전환 검증](전국_GPS_전환_구현_검증_20261004.md)을 기준으로 한다. 운영에는 아직 미배포다.


작성일: 2026-10-04. 모든 표시 항목과 파생 문구를 대상으로 한다. 사용자의 단기예보 운영계정 전환 전제를 유지한다.

## 1. 이번 작업의 실제 변경과 전환 설계 구분

- **로컬 수정 완료:** 현재 10분 구간 선조회 제거, T1H 파일 검증 후 나머지 변수 요청, 미제공 파일과 전 격자 결측 파일의 후속 요청 차단. 요청별 타임아웃 30초는 유지한다. 운영 미배포다.
- **실측 완료:** 자외선 V5 전국 4페이지·3,851개 고유 구역·동일 발표시각 조회, 단기예보 전국 파일 일부 표본, 버전 조회의 현재 인증/응답 상태.
- **아래 내용은 전 항목 전환 설계다.** 전국 예보 배열 영구 저장·전국 관측소 원본 저장·행정/예보구역 공간 매핑·조회 API 전환은 아직 구현하지 않았다. 기존 1,633 대표 격자 수집을 모든 격자 수집 완료로 표현하지 않는다.

## 2. 준비된 10분 실황을 요청하는 방법

현재 자료는 APIHub `nph-dfs_odam_grd`의 T1H·REH·WSD·VEC·PTY·RN1이다. 같은 명칭을 쓰는 공공데이터포털 초단기실황은 정시 기반이므로 두 API의 발표 완료를 같은 것으로 취급하지 않는다.

### 적용한 변경

1. `latestGridObservationTime(now)`에 다시 10분을 더하던 코드를 제거한다. 예를 들어 11:24에는 11:10부터 확인한다. 11:20을 먼저 요청하지 않는다.
2. T1H 파일만 먼저 받는다. HTTP 200이어도 `# dfs_file_read error (-1)`, 잘못된 배열 크기, 유효 기온이 전혀 없는 배열이면 나머지 5개를 요청하지 않는다.
3. 정상 T1H를 재사용하면서 REH·WSD·VEC·PTY·RN1을 받는다. 정상 회차는 여전히 6회이고 추가 준비 확인 호출은 없다. 빠른 재시도는 핵심 3회다.
4. 핵심 세 값은 동일 회차·동일 격자일 때만 관측으로 게시한다. 선택 변수의 실패와 핵심 변수 실패를 구분한다. 실패 시 마지막 유효 캐시는 덮어쓰지 않는다.
5. 파일 미제공은 로그에서 `NO_USABLE_DATA`로 구분한다. 파일 오류 자체가 반드시 발표 전이라는 뜻은 아니므로 원인을 단정하지 않는다.

**이 변경은 ‘미제공 회차에 6개를 일괄 요청’하는 낭비를 줄인다. 최초 T1H 확인 요청까지 없애거나 나머지 모든 파일의 준비를 보장하지는 않는다.** 최소 10분 경과 또한 완성 보장이 아니다. 첫 요청과 나머지 요청은 순차이므로 최악의 한 회차 처리 시간은 요청별 30초보다 길 수 있다.

### 엄격하게 준비 완료 후에만 받기 위한 추가 조건

- 10분 격자 실황에 대응하는 완료 회차/변수 목록을 확인할 수 있어야 한다. 공개된 `getFcstVersion`은 후보이나 실제 10분 격자 파일과 일치하는지 검증이 필요하다.
- 2026-10-04 운영 PC 확인: APIHub 버전 조회는 HTTP 403, ‘활용신청이 필요한 API’였다. 포털 버전 조회는 11:30·11:00 모두 HTTP 200/결과코드 01 `APPLICATION_ERROR`였다. 성공한 완료 메타데이터를 확인한 상태가 아니다.
- 따라서 지금 버전 API만 붙여 ‘미발표 요청 0회’라고 주장할 수 없다. 활용신청 후 실제 10분 회차와 각 변수 준비 시각을 대조해야 한다. 확인되면 작은 메타데이터만 조회하고 준비된 새 회차에만 본문을 받는다. 메타데이터를 얻지 못하면 원본 최신 캐시를 유지한다.
- 이후 전국 수집기는 회차별 상태를 `WAITING → COLLECTING → READY`로 저장하고, 이미 받은 회차·변수는 건너뛴다. 실패는 2→4→8분으로 간격을 늘려 재시도하되 같은 회차를 두 작업이 동시에 받지 않도록 공통 잠금을 사용한다. 전체 회차가 정상인데 일부 격자가 영구 미제공인 경우를 파일 미발표와 구분한다.

## 3. 대표 격자 의존을 없애는 공통 구조

```text
기상청/환경공단/ITS 전국 원본 수집
    → 원본 형식·시각·지원 범위 검증
    → SQLite에 원본과 마지막 유효값 영구 보관
    → 완료한 원본 버전만 조회 대상으로 게시
    → 임의 GPS에서 정확한 격자 / 해당 공식 구역 / 관측소 / 도로 선택
    → 현재·오늘·주간·비교·위젯·알림·추천 조합
```

- 격자판 149×253=37,697개를 **파일 한 개에서 모두** 보관한다. 37,697번 개별 API 요청을 하지 않는다. 대표 목록 `NATIONWIDE_FORECAST_GRIDS`는 수집 범위, 조회 허용 목록, 준비 완료 기준에서 제거한다.
- 대기질·시정 등은 전국 관측소를 저장하고 실제 GPS에서 최근접 유효 관측소를 선택한다. 대표 격자에 미리 할당된 관측소 값을 재사용하지 않는다.
- 자외선·중기예보·대기질 예보·특보는 각각의 공식 구역 원본을 모두 보관한다. GPS→공식 구역은 공간 경계 자료 또는 검증된 구역 매핑으로 해결한다. 가까운 대표 격자의 구역을 대신 사용하는 기존 방식은 완료 기준에 포함하지 않는다.
- 조회 API가 `COLLECTED_REGION_nx_ny` 부재를 이유로 먼저 503을 반환하는 경로를 바꾼다. 공통 원본에서 해당 위치의 묶음을 구성한다. 기본 예보의 일부 실패가 이미 보유한 대기질·특보·도로 정보 전체를 차단하지 않도록 부분 상태를 제공한다.
- 파생 결과의 캐시가 없어도 원본 캐시에서 계산한다. 새 GPS 등록이나 사용자의 조회 때문에 외부 API 호출이 늘지 않는 구조를 목표로 한다.
- 캐시를 보존하는 것과 ‘현재 자료’로 표시하는 것은 구분한다. 자료 시각·출처·최신성·지원 여부를 함께 반환한다. 만료한 관측을 최신 실황으로 표시하지 않는다.

## 5. 모든 좌표에서 ‘값 보유’의 현실적인 조건

- 배열 37,697개 중 바다·제공 영역 밖·변수별 비지원 영역에는 원래 숫자가 없다. 이전 TMP 표본의 유효값은 9,295개였다. SKY/VEC 표본은 30,364개였다. 전체 배열 보관을 모든 항목의 숫자 37,697개 확보라고 표현하지 않는다.
- 첫 초기 수집 전, 제공처가 한 번도 값을 준 적 없는 셀에는 마지막 유효값도 없다. 원본 실패만 캐시 보존으로 해결할 수는 없다.
- 가시거리 30km 밖, 중기 육상예보 비지원 지역, 제공 도로 밖의 공식 도로살얼음에는 해당 위치의 공식 값이 없을 수 있다. 값을 0 또는 정상으로 채우지 않는다.
- 사용자가 대체를 허용하면 가까운 유효 관측소/공식 예보구역 값을 출처·거리·시각·대체 표시와 함께 사용한다. 그래도 해당 항목 자체가 없는 경우는 공식 미제공 상태가 필요하다. 이 정책을 사용자에게 질문했다.
- 초기 준비 검사에서는 모든 지원 셀·공식 구역·관측소·도로의 커버리지와 미제공 이유를 검사한다. 등록된 위치나 대표 1,633개만 통과시켜 전수 준비 완료로 선언하지 않는다.
- 정확한 GPS 구역 해석에는 행정·예보·특보 경계/구역 자료가 추가로 필요하다. 기존 대표점 목록은 경계 데이터가 아니므로 이를 대체할 수 없다.

## 6. 캐시 영구 보존 설계

SQLite에 다음 원본 테이블과 버전 목록을 둔다. 압축은 저장공간 절약용이며 외부 API의 내려받기 용량을 줄이는 것으로 계산하지 않는다.

| 저장 대상 | 키/메타데이터 | 값 |
|---|---|---|
| 격자 파일 | 원본 종류·발표시각·발효시각·변수·149×253·형식 버전·체크섬 | 압축 Float32 배열, 유효값 마스크, 수신량 |
| 관측소 원본 | 종류·관측시각·관측소 ID·좌표 | 실제 값과 원본 결측 상태 |
| 공식 구역 원본 | 종류·발표시각·공식 구역 ID | 자외선/중기/대기질/특보 원본 |
| 구간 원본 | 종류·수집시각·도로/이벤트 ID | 구간 좌표, 시작/종료, 공식 위험/통제 |
| 공개 버전 목록 | 원본·회차·수집 상태·필수 파일 목록·지원 범위 | 검증이 완료된 파일 묶음에 대한 참조 |
| 마지막 유효값/버전 | 원본·셀 또는 구역/관측소·자료 시각 | 최신 오류가 덮어쓸 수 없는 마지막 정상 참조 |
| 좌표 해석 자료 | 행정·예보·특보 경계 버전 | 공간 인덱스, 실제 GPS→공식 구역 |

1. 새 파일을 임시 버전으로 기록한다. 크기·시각·코드·핵심 변수 일치를 검증한다.
2. 필요한 파일이 준비된 뒤 SQLite 트랜잭션으로 공개 버전 참조를 바꾼다. 중간 실패 때 이전 공개 버전을 유지한다.
3. 핵심 실황은 격자별 동일 회차 T1H/REH/WSD 묶음이 완성될 때만 교체한다. 선택 변수와 일 최저/최고는 각각 실제 자료 시각을 보존한다.
4. 새 파일의 -99/결측으로 기존 정상 셀을 덮어쓰지 않는다. 공식 특보 해제나 종료한 통제는 유효 상태 변화이므로 오래된 활성 이벤트를 유지하지 않는다.
5. 예보의 원본 시간축을 전부 저장한다. 응답의 48시간 제한은 조회 시 적용한다. 수집 때 48시간만 저장하면 6/12시간 후에는 48시간 제공 조건을 만족하지 못한다.
6. 최소 최신·직전 원본과 현재 날짜의 과거 시간 슬롯을 유지한다. 청소는 사용 중인 버전, 날짜별 마지막 유효값, 비교용 관측을 건드리지 않는다. SQLite 파일과 함께 백업한다.
7. Node 메모리에는 필요한 배열/파일만 제한된 캐시로 올린다. 캐시 키에 발표·발효·변수를 넣어 새 회차가 이전 시간값으로 읽히지 않게 한다.

Float32 파일 하나는 `37,697 × 4 = 150,788바이트`다. 실황 6변수는 회차당 약0.905MB다. 예보를 최대104시간·9변수·일 최고/최저 최대10파일로 넉넉하게 보관하면 한 버전 약142.65MB, 두 버전 약285.3MB다. 이는 압축 전 배열만의 크기다. 현재/직전/수집 중 버전, 관측 원본, DB/WAL, 백업을 포함해 초기 공간 예산 2GB 이상을 따로 잡고 실제 사용량을 측정한다.

## 7. API 호출·용량 계산 전제

- **공공데이터포털 단기예보 호출 한도: 운영계정 전환 전제로 문제없음.** 실제 운영 키 전환을 수행한 것은 아니다.
- 별도로 현재 서버 내부 APIHub 상한은 `18,000회/일`, `4,500,000,000바이트/일`이다. 이는 코드의 예약 제한이고 현재 계정의 공급자 승인량 자체를 확인한 숫자는 아니다.
- 단기예보 전국 파일 표본은 341,297바이트다. TMP/SKY의 이전 표본 및 이번 SKY/VEC 표본으로 확인했다. 9변수 전체·전체 시간축의 평균/최대 용량을 확인한 것은 아니므로 아래는 표본 기반 예상치다.
- 공식 제공 시간 범위의 끝까지 보관한다. 2024-11-28 이후 오전/14시 회차는 글피 자정, 17/20/23시는 그글피 자정까지다. 72시간 고정 계산만으로 오늘∼최대5일 전체 자료를 확보했다고 하지 않는다.
- 시간별 9변수를 모든 미래 시간에 받는 보수적인 계획치다. 연장 구간의 실제 3시간 간격·미제공 변수는 공식 형식 검증 후 요청 목록에서 제외해야 한다. 일 최고/최저는 회차당 최대10파일을 추가했다.
- 오늘의 이미 지난 시간/최저기온 보충과 초기 수집, 메타데이터, 인증 실패, 재시도는 정상 반복 수집과 구분한다.
- 1GB는 10억 바이트다. 용량 추정에는 내려받기 본문을 사용하고 전송/제공처 과금 차이는 여유분으로 처리한다.

## 8. 한도 내에서 실제로 운영하려면 필요한 변경

1. 현재 실황은 파일당1MB를 예약해 정상864회도864MB로 집계한다. 실측 예상295MB와 큰 차이가 난다. 첫 파일만 요청하고 중단한 나머지 요청까지 예약 소비로 남는다. 예보까지 같은 방식으로 추가하면 위 실제 수신량 기반 계산대로 운영되지 않는다.
2. 요청 전에 호출/용량을 원자적으로 예약하고, 완료해서 확인한 본문 바이트로 정산한다. 실제 전송하지 않은 요청은 취소한다. 시간 초과로 수신량을 확인하지 못한 요청을 무조건0바이트로 처리하지 않는다. 호출 시도와 성공 파일 수를 별도 집계한다.
3. 전국 원본 종류별 일 예산과 필수 수집 여유를 확보한다. 활성 GPS의 빠른 재시도가 전국 초기/정규 예보 예산을 먼저 소진하지 못하게 한다.
4. 회차·변수·발효시각별 중복 억제, 공통 잠금, 실패 간격 증가, 429/일 용량 초과 후 동일 회차 반복 중단을 적용한다. 정상으로 받은 원본을 활성 위치용으로 다시 받지 않는다.
5. 관측소 목록·공식 구역 목록·경계 자료는 따로 오래 보관한다. 신규 GPS마다 외부 역지오코딩을 반복해 호출량 계산을 무너뜨리지 않는다.
6. 원본별 성공/실패 로그에 발표/발효시각, 헤더 대기·본문 수신·파싱 시간, 실제 바이트, 상태코드, 준비 여부를 기록한다. 인증키·URL 전체는 기록하지 않는다. 성공의 p95/p99를 모아30초 초과 정상 응답과 제공처504를 분리한다.
7. 초기 전수 수집은 일 정규 예산과 별도 산정한다. 기본 예보 첫1회는 약750∼940파일+일 극값(표본 기준약260∼320MB), 실제 파일 목록 검증 전 예상이다. 캐시 없이 시작하는 모든 위치를 완료 검사에 포함한다.

## 9. 전환 완료 검사

- 대표 목록 밖의 지원 격자·섬·행정 경계·서로 다른 관측소가 가까운 좌표에서도 조회가 가능하다.
- 가입자가0명이어도 원본 전수 수집을 수행한다. 신규 GPS1만개를 조회해도 외부 API 호출 수가 증가하지 않는다.
- 현재·오늘·주간·비교·추천·위젯·알림이 같은 위치 해석 함수를 사용한다. 개별 화면만 전수 지원으로 바꾸고 알림이 대표 격자 캐시에 남는 일을 막는다.
- 새 회차의 필수 파일 실패/일부 셀 결측/부분 페이지/잘못된 발표시각에도 마지막 정상 자료가 보존된다. 특보 해제·통제 종료는 정상 반영된다.
- 재시작 후 배열·관측소·공식 구역·도로 캐시를 복구한다. 수집 중 버전이 공개되지 않으며 청소가 공개 버전을 삭제하지 않는다.
- 숫자가0인 정상 자료, 공식미제공, 과거자료, 대체자료를 구분한다. 근거 없는 ‘모든 항목 숫자 확보’ 완료 판정을 하지 않는다.

## 10. 근거

## 11. 단기예보 최신성을 고려한 보완 후보

사용자가 단기예보의 변경 빈도를 질문했다. 공식 발표는3시간마다 새 회차이며, 실제 같은 격자·같은 미래 시각의 값이 얼마나 자주 바뀌는지는 회차별 원본 비교가 필요하다. 은행동의 변경 비율은 아직 측정하지 않았다.

위6/12시간 주기안은 전체 미래 시간축을 매번 갱신하는 용량 절충안이다.6시간마다 받으면 중간1개 발표,12시간마다 받으면 중간3개 발표를 놓친다.05시 자료를17시까지 쓰면08·11·14시 변경사항을 늦게 반영한다.

우산·외출 안내의 최신성을 위해서는 **가까운24∼48시간은3시간 새 회차마다, 먼 날짜는6∼12시간마다 갱신**하는 방식을 추가 후보로 검토한다. 전국 모든 격자는 계속 보관하고 미래 시간 범위에 따라 갱신 빈도를 나누는 설계다. 혼합안의 중복 파일 제거·일 극값 보충·겨울 다른 원본 예산을 포함한 비용은 아직 계산하지 않았으므로 기존 표의 예산으로 한도 내 운영을 보장하지 않는다. 수집 주기를 실제 변경한 것은 아니다.

## 12. 모든 제공처·대체·초기 수집을 포함한 재계산

2026-10-04 사용자가 모든 API 한도를 포함하도록 요청했다. **이 절이 7절의 비용 판단을 보완한다.** 7절은 정상 반복 수집 중심이며 AWS 분 관측 대체·준비 메타데이터·사용자 요청별 비교·초기 보충을 합계에 포함하지 않았다. 모든 GPS 지원을 위한 전국 원본 전환안의 예상치이며, 현재 운영 수집량이나 구현 완료를 뜻하지 않는다.

APIHub 밖 정상 합계는 **601회/29.537MB**다. 에어코리아 현재 관측+예보는424회, 20%호출 여유를 잡으면509회로 기본500회 안내를 넘는다. 측정소 목록은 실제 현재 코드가 전국 대기질 수집 때마다 요청하므로 시간 수집에서24회/3.725MB이고, 위1회/0.155MB는 영구 목록 캐시로 변경한 뒤의 수치다. 관측소 증가로 시도별1000행이나 목록1000행을 넘으면 추가 페이지를 모두 포함해야 한다. 현재 표본에서는 모두 한 페이지다.

### AWS 대체 수집까지 포함한 합계

AWS 분 자료는 실황 실패/결측 보충용이다. 전국 분 자료를10분마다1회, 관측소 목록은 일1회 공유하면 **최대144회차+목록1회=145요청**이다. 성공 분 자료 크기는 이번 측정에서도30초 헤더 대기로 실패해 확정하지 못했다. 실패를0바이트로 계산하지 않고, 현재 예약값을 참고해 **분 자료 회차당3MB+목록1MB=433MB/일**를 별도로 배정한다. 이는 매 회차 대체가 필요한 시나리오이며 실제 응답 상한이 아니다. 필요한 회차가 F개라면 F요청·3F MB+목록1회·1MB로 줄어든다.

가까운24시간 혼합안에 AWS와 추가 재시도/오차20%를 잡으면 APIHub는 **비겨울6,562회/3.923GB, 겨울7,253회/5.375GB**다. 호출 수는18,000 이하지만 겨울 용량은 내부4.5GB·일반회원5GB 모두 넘는다. 전체12시간도 AWS+20%에서 겨울4.819GB로 내부4.5GB를 넘는다. 따라서 앞선 ‘겨울12시간이면20%여유까지 가능’은 AWS 대체까지 포함한 보장으로 사용할 수 없다. 20%는 임의의 계획 여유이며 실제 장애율을 측정한 수치도, 무한 재시도 보장도 아니다.

**가까운24시간 혼합안의 겨울 정상 수집 후 내부 잔여는454.243MB/일**이다. 매 회차 AWS 배정433MB를 사용하면21.243MB만 남는다. 정상 수집이 가능하다는 것과 실패·보충에도 모든 자료 최신성을 유지할 수 있다는 것은 다르다. 현재 레이더/분석 비겨울15분을 유지하면 해당 표의 비겨울 항목에48회차·96요청/1.444GB를 추가한다. 주기·용량 정산·전국 캐시 전환은 아직 운영에 적용하지 않았다.

## 13. 제공처별 필수 호출과 재시도 예상 합계

사용자 요청에 맞춰 APIHub·에어코리아·ITS를 제공처별로 합산했다. 전국 캐시 전환 설계의 반복 수집 예상치이며 실제 운영 호출 통계가 아니다. 가까운24시간 예보3시간/나머지12시간, 전국 강수분석·레이더30분 전제는12절과 같다. 최초 과거자료 보충과 사용자별 외부 호출을 제거한 뒤의 반복 예산이다.

**최신 사용자 전제:** 에어코리아는 운영계정 신청을 통해 한도 문제없음, ITS도 한도 문제없음으로 처리한다. 아래 개발계정500회 비교와 ITS 승인량 미확인 기록은 이전 조사 근거이며 현재 수집 설계의 한도 장애로 취급하지 않는다. 계정 신청·승인·키 변경을 이번 작업에서 수행한 것은 아니다.

준비 메타데이터는 아직 미도입·사용 권한 미확정이므로 **필수 호출에서720회/1,474,560바이트를 제외**한다. 따라서12절의 정상5,323/5,899회와 이 표의 필수4,603/5,179회는720회 차이가 난다. 도입 시 별도720회/일, 추가20% 여유까지864회/약1.769MB를 더하면12절의 합계와 일치한다.

재시도는 실제 실패율 실측이 아니라20% 계획 여유다. APIHub에는 전국 AWS대체144회차+목록1회=145회/433MB 배정도 함께 포함한다. 계산은 `ceil((필수+AWS145)×1.2)-필수`이며 이를 ‘재시도·대체 추가’로 표시한다. AWS145회를 반드시 매일 호출한다는 뜻은 아니다. 에어코리아는 서비스별, ITS는 자체 서비스에서 `ceil(필수×0.2)`를 추가한다.

ITS는 일173회를 잡으면30일5,190회·31일5,363회로 내부월9,000보다 작다. 앞선 월5,357처럼 월 합계에 한 번20%를 붙이는 계산과는 일별 올림 때문에 차이가 있다. 코드의 월9,000을 제공처 공식 한도로 표현하지 않는다.

APIHub 겨울은 호출 수는 충분하지만 용량 총5.373GB로 내부4.5GB·일반회원5GB를 넘는다. 비겨울은 위 전제에서 재시도 여유까지 내부 한도 이하이다. 이 결과를 현재 비겨울15분 강수 주기·기존 빠른 재시도·지점 보충을 그대로 병행하는 운영에 적용하지 않는다. 포털 자외선과 포털 기상청 단기예보 서비스는 이번3개 제공처 집계와 별도이며 이전12절에 보존한다.

## 14. AWS 대체와 준비 확인의 의미

- **AWS 대체:** AWS는 기상청 자동기상관측장비다. 격자 실황 최신 회차→직전 회차에도 기온·습도·풍속 등을 확보하지 못한 위치에 대해 주변 실제 관측소 자료를 이용하는 보완 경로다. `collectCurrentObservations`에 이미 있는 경로이며 동일 격자값을 확보했다는 뜻은 아니다. 좌표와 관측소의 거리·관측시각·출처를 보존해야 한다. 전국 전환안은 전국 분 관측을 회차별1번 공유하고 목록을 영구 캐시한다. 145회/433MB는 매10분 회차144개 모두 대체가 필요한 경우와 목록1회에 대한 보수적 배정으로, 정상 수집 때 무조건 발생하는 호출이 아니다. 실패 시 다른 원본을 추가로 받는 비용이므로 재시도·대체 열에 포함했다.
- **준비 확인:** 본 자료6변수를 요청하기 전에 해당10분 회차가 제공 준비됐는지 확인하는 절차다. 별도 버전/상태 메타데이터를2분마다 조회하는 후보에 최대720회/일 예산을 배정했으나 현재 키 사용 권한과 실제10분 완료 회차 지원이 검증되지 않아 도입하지 않았다. 실제 필수 요청에서 제외한다.
- **현재 로컬 수정안:** 예정 시각을 앞당겨 조회하던+10분을 제거하고, 필수 기온 T1H 파일을 먼저 받아 정상 여부를 확인한 뒤 나머지5변수를 받는다. 성공한 T1H는 그대로 재사용해 정상6요청이며 별도 준비 확인 API 호출은0이다. 첫 파일 확인도 실제 요청이므로 미발표 요청0회를 보장하지 않는다. 이 수정안은 아직 운영에 배포하지 않았다.

## 15. AWS 공유 한도와 실황 시각·제공 지연 구분

- 현재 AWS 분 관측과 관측소 목록은 모두 APIHub 호스트에 같은 APIHub 키로 요청한다. 따라서 APIHub 일반회원 공식20,000회/5GB와 서버 내부18,000회/4.5GB의 공유 예산에 포함한다. 코드상 AWS대체 전용 추가 일 한도를 따로 확보하지 않는다. 앞서145회/433MB는 전환안 사용량 배정이며 제공처 한도가 아니다.
- 공식 실황 명세는 tmfc가10분 간격 발표임을 안내한다. 확인한 명세/개선 공지에는 회차 시각+4분 또는+10분에6변수 파일 제공이 완료된다는 보장이 없다. 발표 회차와 API 파일이 준비된 실제 시각을 구분한다. 발표 직후 제공되지 않을 가능성을 배제할 수 없지만,11:24에11:20파일이 미제공이었던 직접 실측은 이번에 하지 않았다.
- 로컬 latestGridObservationTime은 ‘현재 시각-10분’을10분 단위로 내림한다. 11:24→11:14→11:10이며11:30→11:20이다. 이는 기존 코드의 보수적인 여유이며 기상청이 발표 지연10분을 고정으로 규정한 근거가 아니다. 11:24에11:20파일이 이미 정상이어도 이 정책은11:10부터 조회한다.
- 최신성을 높이려면 실제 회차별 기온 파일 최초 성공 시각과 나머지 변수 완료 시각을 측정해 여유를 줄이거나 준비 메타데이터를 검증해야 한다. 최신 후보11:20의 첫파일을 직접 확인하는 방법도 가능하지만 미제공 시 첫요청은 발생한다. 성공 시 그파일재사용→나머지변수,실패시마지막정상11:10유지로설계한다. 시간 초과를 모두 미발표로 단정하지 않는다.
