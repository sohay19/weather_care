# 알림·위젯·앱 브리핑/멘트/표현 현행 구조

- 작성 기준: 2026-09-22 현재 작업 트리
- 목적: 사용자가 보는 동적 날씨 문장이 어디서 생성되고, 앱·홈 위젯·알림에서 어떻게 재사용되는지 정리한다.
- 상태: 현행 구현 조사 문서이며 코드와 문구 정책은 변경하지 않았다.
- 범위: 날씨 요약, 체감 표현, 준비물·행동 제안, 특보·도로·현재 강수 안내, 시간별·주간 요약
- 제외: 단순 메뉴명, 권한·법률 안내, 네트워크 오류와 로딩 문구

## 1. 용어를 이렇게 구분하는 것이 적절하다

현재 코드에서는 `brief`, `message`, `title`, `description`, `stateLabel` 등이 섞여 사용된다. 기획 문서에서는 다음처럼 구분하면 의미가 명확하다.

| 권장 용어 | 의미 | 예시 |
|---|---|---|
| 날씨 브리핑 | 여러 날씨 조건 중 중요한 한 가지를 골라 만든 대표 요약문 | `비가 올 수 있으니, 오후 3시~5시 외출한다면 우산을 챙기세요` |
| 상태 안내 | 현재 또는 특정 시간대의 상태를 설명하는 문장 | `맑은 하늘이 이어지는 날씨예요` |
| 체감 표현 | 온도나 습도 등을 사람의 느낌 단어로 바꾼 표현 | `조금 덥게`, `쌀쌀하게`, `후텁지근하게` |
| 행동 안내 | 날씨에 따라 사용자가 할 일을 제안하는 문장 | `물을 준비하세요`, `속도를 줄이세요` |
| 준비물 추천 | 체크리스트와 위젯에 노출되는 물건 단위 추천 | 우산, 선크림, 물, 겉옷, 마스크 |
| 근거 문장 | 행동 안내의 근거가 된 공식값·계산값·자료 상태 | `예상 체감온도는 33℃예요` |
| 알림 문구 | 푸시 알림의 제목과 본문으로 최종 조합된 문장 | `오늘 준비할 내용` + 최대 3줄 본문 |

따라서 화면 상단의 큰 문장은 **날씨 브리핑**, `체감 상 조금 덥게`는 **체감 표현**, 체크리스트는 **준비물 추천**, 푸시는 **알림 문구**라고 부르는 것이 좋다.

## 2. 전체 흐름

```text
기상·환경·도로 자료
        │
        ├─ 서버 종합 브리핑 선택 ── today.brief ──┬─ 앱 Main 상단
        │                                           └─ 큰 홈 위젯
        │
        ├─ 서버 생활 규칙 ── 생활 인사이트 ──┬─ 준비물 추천 ── 앱 체크리스트/위젯/아침 알림
        │                                      ├─ 생활 문장·근거 ── 앱 Detail
        │                                      └─ 시간별 상태 ── 앱 타임라인
        │
        ├─ 공식 특보·현재 강수·도로 자료 ── 앱 Detail + 사건형 푸시 알림
        │
        └─ 현재 기온·체감온도 ── 앱이 별도 문장 생성 ── Main의 "지금 날씨"
```

핵심은 모든 화면이 하나의 문장을 공유하는 구조가 아니라는 점이다.

- 앱 Main 상단과 큰 위젯은 서버의 `today.brief`를 공유한다.
- Main의 `현재 기온/현재 체감온도` 아래 문장은 Flutter 앱이 별도로 만든다.
- 아침 알림은 `today.brief`를 사용하지 않고 준비물 추천과 가시거리·습도 문장을 다시 조합한다.
- Detail은 서버의 생활 문장과 공식·계산 근거를 보여준다.
- 중간 위젯은 대표 준비물이 있으면 브리핑보다 준비물 문장을 우선한다.

| 큰 위젯 | 현재/체감 + 서버 브리핑 2줄 + 준비물 최대 3개 + 다음 예보 | 앱이 만든 스냅샷, 브리핑 원문은 서버 | 앱이 스냅샷을 다시 저장할 때 |
| 준비물 요약 알림 | 제목 + 최대 3줄의 준비물·환경 안내 | 서버 `notificationBuilder.ts` | 설정 시각에 하루 1회 |

## 4. 앱 Main 상단의 서버 날씨 브리핑

### 4.1 선택 우선순위

서버는 현재값과 앞으로 최대 24시간의 시간별 값을 살핀 뒤 아래 순서에서 처음 맞는 장면 하나만 고른다.

| 순서 | 장면 | 대표 판정 | 현재 문장 방향 |
|---:|---|---|---|
| 1 | 눈 | 눈 종류 또는 적설 예상 | 도로·대중교통 확인 |
| 2 | 비/소나기 | 강수확률 40% 이상 또는 비 종류 | 우산 준비 |
| 3 | 낮은 가시거리 | 1,000m 미만 | 감속·주변 확인 |
| 4 | 나쁜 대기질 | PM10 81 이상, PM2.5 36 이상 또는 나쁨 등급 | 보건용 마스크 준비 |
| 5 | 더위/강한 자외선 | 기온 또는 체감 33℃ 이상, 자외선 6 이상 | 물 또는 양산·모자 준비 |
| 6 | 추위 | 기온 12℃ 이하 또는 체감 10℃ 이하 | 겉옷 준비 |
| 7 | 강한 바람 | 9m/s 이상 | 소지품 고정 |
| 8 | 높은 습도 | 80% 이상 | 후텁지근함 또는 눅눅함 안내 |
| 9 | 낮은 습도 | 35% 이하 | 코·목 건조 안내 |
| 10 | 좋은 가시거리 | 현재 20km 이상 | 먼 건물까지 보이는 시야 안내 |
| 11 | 기본 | 위 조건 없음 | 시간별 예보 확인 안내 |

### 4.2 시간 표현과 만료

- 현재 진행 중이면 `지금`, 앞으로 시작하면 `오전/오후 N시` 또는 강수 구간을 붙인다.
- 앞으로 시작할 사건은 시작 시각에, 진행 중인 사건은 종료 시각에 브리핑이 만료된다.
- 앱 Main은 만료 시 `안내 시간이 지났어요. 화면을 아래로 당겨 최신 예보를 확인하세요.`로 바꾼다.
- `내일`, `모레`, `글피`, `다음 날`이 들어간 과거 서버 문구는 오늘용 기본문장으로 대체한다.

### 4.3 반복되는 이유

- 장면별 실제 문장 템플릿이 현재 1개뿐이다.
- `WeatherBriefContext`에 지역·날짜 필드가 있으나 현재 문장 선택에는 사용하지 않는다.
- 같은 장면·시간 표현이면 지역이나 날짜가 달라도 같은 문장 형태가 나온다.
- 우선순위가 고정되어 있어 비가 있는 날에는 뒤의 체감·습도·시야 장면이 브리핑에서 빠진다.

즉, 이 브리핑은 현재 **다양한 표현을 순환하는 카피 시스템**이 아니라 **조건별 고정 문장 선택기**다.

## 5. 앱 Main의 현재 날씨·체감 문장

이 문장은 서버 브리핑이 아니라 앱의 `_weatherSummaryMessage()`가 만든다.

### 5.1 조합 방식

```text
[하늘 상태] + [실제 기온 대비 체감온도 차이] + [체감온도 단계]
```

예를 들어 현재 구현에서 기온 25.0℃, 체감 25.1℃이면 다음 형태가 된다.

> 맑은 하늘이 이어지는 날씨예요. 실제 기온보다 0.1℃ 높지만, 체감 상 조금 덥게 느껴질 수 있어요.

### 5.2 현재 체감온도 구간

| 체감온도 | 내부 단계 | 문장 표현 |
|---:|---|---|
| 38.0℃ 이상 | 위험한 더위 | 위험할 만큼 매우 덥게 |
| 35.0~37.9℃ | 더위 경계 | 매우 덥게 |
| 33.0~34.9℃ | 더위 주의 | 더위가 강하게 |
| 28.0~32.9℃ | 더움 | 꽤 덥게 |
| 20.0~27.9℃ | 조금 더움 | 조금 덥게 |
| 10.0~19.9℃ | 선선한 편 | 선선하게 |
| 0.0~9.9℃ | 쌀쌀한 편 | 쌀쌀하게 |
| 0.0℃ 미만 | 추움 | 춥게 |

### 5.3 실제기온과 체감온도 차이

- 화면 표시값을 각각 소수점 첫째 자리로 반올림한 뒤 비교한다.
- 절댓값 차이가 `0.05℃ 미만`일 때만 `실제 기온과 비슷하지만`이라고 쓴다.
- 그 외에는 차이가 0.1℃여도 `실제 기온보다 0.1℃ 높지만/낮지만`이라고 정확히 말한다.

따라서 사용자가 지적한 25.1℃ 문구는 계산 오류라기보다 다음 두 정책이 겹친 결과다.

1. 20.0~27.9℃ 전체를 `조금 더움`으로 묶는다.
2. 사실상 같은 수준인 0.1℃ 차이도 의미 있는 차이처럼 말한다.

세부 분석과 변경 제안은 [체감온도 브리핑 현행 구현 현황](./체감온도_브리핑_현행_구현_현황.md)에 별도로 정리되어 있다.

## 6. 준비물 추천과 행동 문장

### 6.1 준비물 종류

서버 추천 엔진은 생활 인사이트를 다음 17개 준비물/행동 유형으로 바꾼다.

- 비: 우산, 우비, 장화
- 자외선: 선크림, 양산, 선글라스
- 더위: 물, 휴대용 선풍기, 쿨링제품
- 추위: 두꺼운 겉옷, 목도리, 핫팩
- 눈: 스노우체인, 방한부츠, 보조배터리, 많은 눈 대비
- 대기질: 마스크

앱 Check List는 `recommended == true`인 항목을 보여준다. 큰 위젯은 우선순위가 높은 서로 다른 항목을 최대 3개만 보여준다.

관련 파일:

- [추천 규칙](../weather_care_server/src/recommendations/recommendationEngine.ts)
- [추천 문장 카탈로그](../weather_care_server/src/recommendations/recommendationTemplates.ts)
- [앱 체크리스트](../weather_care_app/lib/features/home/widgets/recommendation_bag_section.dart)

### 6.2 문장 변형 방식

- 대부분의 준비물 종류마다 설명 후보가 3개 있다.
- 무작위로 매번 바뀌는 구조는 아니다.
- 활성화된 생활 인사이트 종류를 문자값으로 합산한 고정 시드로 후보를 고른다.
- 날씨 조건 구성이 같으면 선택 결과도 같으므로 같은 멘트가 계속 보일 수 있다.
- 강풍+비의 우산, 강풍+자외선의 양산, 추위의 겉옷은 별도 고정 예외 문장이 있다.

## 7. 앱 Detail의 생활 안내와 근거

Detail은 단순 카피 목록이 아니라 하나의 항목을 역할별 문장으로 나눠 보여준다.

| 역할 | 의미 | 예시 |
|---|---|---|
| 앱 제안 | 날씨챙겨가 권하는 행동 | `외출한다면 물을 준비하세요` |
| 영향/가능성 | 사용자에게 생길 수 있는 영향 | `후텁지근하게 느껴질 수 있어요` |
| 공식 사실 | 기상청·에어코리아·도로기관 자료 | `기상청은 ... 예보했어요` |
| 계산 사실 | 앱 서버가 공식 입력값으로 계산한 값 | `예상 체감온도는 33℃예요` |
| 자료 상태 | 값이 없거나 일부 자료가 누락된 이유 | `강수량 자료를 받아오지 못했어요` |

생활 안내 범주는 비·눈·자외선·오존·대기질·더위·추위·강풍 외에도 비가 그치는 시간, 외출하기 나은 시간, 반려견 산책, 빨래 회수, 창문 닫기, 젖은 도로, 급격한 기온 하락, 야간 수면, 도로살얼음, 도로 통제를 포함한다.

### 체감 문장 카탈로그의 실제 연결 상태

[체감 문장 카탈로그](../weather_care_server/src/presentation/sensationMessages.ts)에는 더위·추위·자외선·대기질 표현 후보가 있다. 그러나 현재 연결 상태는 다음과 같다.

- 사용 중: 후텁지근함, 자외선 직접 체감 한계, 양산 효과, 미세먼지 직접 체감 한계, 오존 직접 체감 한계
- 미사용: `HEAT_MILD`, `HEAT_CLEAR`, `HEAT_STRONG`과 모든 `COLD_*` 단계

따라서 이 카탈로그의 `조금 덥게 느껴질 수 있어요`를 바꿔도 Main의 25.1℃ 문장은 바뀌지 않는다. Main의 체감 표현은 Flutter 코드에 별도로 들어 있다.

## 8. 앱 타임라인과 주간 요약

### 8.1 시간별 타임라인

타임라인은 시간마다 다음 세 층을 보여준다.

1. 상태 문장: 비·눈·자외선·추위·대기질·더위·바람·습도·최고/최저·기온 급변·하늘 상태 중 하나
2. 상세값: `예상기온 N℃ / 하늘 상태`
3. 추천 준비물: 해당 시간의 상위 최대 3개

상태 문장은 준비물 종류가 있으면 그것을 먼저 반영하고, 없으면 강수 → 바람 → 일중 최고/최저 → 직전 시간 대비 ±3℃ → 습도 → 하늘 상태 순으로 고른다.

### 8.2 Week 요약

Week의 `주간 날씨 요약`은 서술형 브리핑이 아니다. 다음 세 지표를 집계한다.

- 예상 강수일
- 예상 주중 최고기온
- 준비물이 예상되는 날짜 수

따라서 Week에는 현재 Main과 같은 자연어 대표 브리핑 생성기가 없다.

## 9. 홈 위젯 문장

### 9.1 크기별 차이

| 크기 | 문장 노출 |
|---|---|
| 작은 위젯 | 브리핑 문장 없음 |
| 중간 위젯 | `shortMessage` 한 줄 |
| 큰 위젯 | 서버 `brief` 최대 2줄 + 준비물 최대 3개 |

### 9.2 중간 위젯의 `shortMessage`

1. 추천 준비물이 있으면 가장 우선순위가 높은 항목을 `우산을 챙기세요` 같은 고정 짧은 문장으로 표시한다.
2. 추천이 없으면 서버 브리핑의 첫 문장을 사용한다.
3. 첫 문장이 22자를 넘으면 21자 뒤에 말줄임표를 붙인다.

따라서 중간 위젯과 큰 위젯은 같은 시각에도 서로 다른 문장을 보여줄 수 있다.

### 9.3 갱신과 만료의 현재 한계

- 앱이 날씨·주간 자료나 지역명을 적용할 때 위젯 스냅샷을 저장한다.
- Android 위젯의 자체 주기 갱신은 `0`, iOS 타임라인 정책은 `.never`다.
- 위젯 스냅샷에는 `briefExpiresAt`이 들어 있지 않다.
- 결과적으로 앱 Main에서는 만료된 브리핑을 숨겨도, 위젯은 앱이 다시 갱신하기 전까지 이전 시간 문장을 계속 표시할 수 있다.
- 저장 자료가 없으면 `날씨챙겨를 열어 최신 날씨를 확인하세요.`를 표시한다.

## 10. 푸시 알림 문구

서버의 핵심 수집·알림 작업은 10분마다 실행된다. 알림 전체 사용 설정, 기기 토큰, 개별 항목 설정, 중복 발송 이력을 확인한 뒤 FCM으로 보낸다.

### 10.1 준비물 요약 알림

| 항목 | 현행 동작 |
|---|---|
| 식별자 | `MORNING_BRIEF` |
| 시각 | 사용자가 정한 시각을 다음 10분 슬롯으로 올림 |
| 횟수 | 해당 지역 날짜 기준 하루 1회 |
| 제목 | 추천이 있으면 `오늘 준비할 내용`, 없고 환경 문장만 있으면 `오늘 날씨 안내` |
| 본문 | 최대 3줄 |
| 줄 우선순위 | 환경 문장 첫 항목 → 준비물 설명들 → 남은 환경 문장. 가시거리 문장이 있으면 환경 첫 항목이 됨 |
| 탭 이동 | Main |

중요하게도 이 알림은 Main 상단의 `today.brief`를 재사용하지 않는다. 같은 날 앱·위젯·알림의 대표 문장이 서로 달라질 수 있다.

### 10.2 사건형 알림

| 종류 | 제목 예시 | 본문 구성 | 탭 이동 |
|---|---|---|---|
| 현재 강수 | `현재 강수 안내` | 비 가능성 + 지금 우산 준비 | Detail 강수 |
| 많은 눈 대비 | 추천 제목 | 발생 시간대 + 대설 행동 문장 | Detail 눈 |
| 공식 특보 발효 | `호우주의보 발효` 등 | 행동 안내 + 지역의 공식 발효 사실 | 해당 Detail 항목 |
| 공식 특보 변경 | `호우특보 변경` 등 | 행동 안내 + 이전/현재 단계 | 해당 Detail 항목 |
| 공식 특보 해제 | `호우주의보 해제` 등 | 지역 + 해제 사실 | 해당 Detail 항목 |
| 도로살얼음 | `블랙아이스(도로살얼음)` | 위험 단계별 행동 + 기상청 도로 구간 사실 | Detail 도로살얼음 |
| 도로 통제 | `출퇴근 경로` | 우회 행동 + 국가교통정보센터 사실 | Detail 출퇴근 |

공식 특보 행동 문장은 강풍, 호우, 한파, 건조, 해일, 지진해일, 풍랑, 태풍, 대설, 황사, 폭염, 안개, 열대야 유형별로 따로 정의되어 있다.

### 10.3 현재 강수와 도로 알림의 조건

- 현재 강수는 정밀 위치가 있고 관측분석자료와 레이더가 일치해야 한다.
- 우산 알림과 소나기·약한 비 설정이 모두 켜져 있어야 사용자에게 발송한다.
- 비가 그쳤다가 다시 감지되는 상태 변화를 기준으로 재발송한다.
- 도로살얼음과 도로 통제는 정밀 위치 및 해당 공식 자료가 있어야 한다.
- 공식 특보와 도로 알림은 준비물 요약의 설정 시각과 별도로 상태 변화를 확인한다.

### 10.4 알림 본문의 줄바꿈

- 알림 생성기가 직접 `\n`을 넣은 문장은 그대로 여러 줄로 보낸다.
- FCM 발송 직전에는 마침표·물음표·느낌표 뒤 공백도 줄바꿈으로 바꾼다.
- 따라서 앱 안에서 한 문단인 추천 설명이 알림에서는 여러 줄로 보일 수 있다.

## 11. 현재 문장 체계에서 확인된 불일치·반복 지점

| 지점 | 현행 상태 | 사용자에게 보일 수 있는 결과 |
|---|---|---|
| Main 상단 vs 현재 체감 문장 | 서버와 앱의 서로 다른 생성기 | 상단은 시야를 말하고 아래는 `조금 덥게`라고 말할 수 있음 |
| Main vs Today 체감 단계 | 비슷한 구간 코드가 두 파일에 중복 | 한쪽만 수정하면 화면별 표현이 달라질 수 있음 |
| 앱 vs 서버 체감 문장 | Flutter 구간과 서버 감각 카탈로그가 분리 | 서버 카탈로그를 수정해도 Main 문장은 그대로임 |
| 서버 브리핑 반복 | 장면당 템플릿 1개 | 같은 조건에서 계속 같은 문장 |
| 추천 문장 반복 | 고정 시드로 후보 선택 | 조건 구성이 같으면 같은 후보가 반복됨 |
| 아침 알림 vs 브리핑 | 알림이 `today.brief`를 사용하지 않음 | 같은 날 대표 메시지가 채널마다 달라짐 |
| 중간 vs 큰 위젯 | 준비물 우선 문장과 서버 브리핑을 각각 사용 | 위젯 크기를 바꾸면 대표 문장이 달라짐 |
| 앱 Main vs 위젯 만료 | Main만 `briefExpiresAt` 검사 | 끝난 비·눈 문장이 위젯에 남을 수 있음 |
| 강한 조건이 여러 개일 때 | 서버 브리핑은 첫 장면 1개만 선택 | 두 번째 이하의 중요한 조건은 대표 브리핑에서 생략됨 |

## 12. 문장 정책을 다시 정리할 때의 권장 기준

아직 적용하지 않은 정리 방향이다.

1. **의미를 먼저 통일한다.** 서버가 `장면`, `위험도`, `시간`, `근거`, `행동`, `만료시각`을 구조화해 제공한다.
2. **화면 길이만 다르게 렌더링한다.** 앱은 긴 문장, 중간 위젯은 짧은 문장, 알림은 제목+본문으로 바꾸되 의미는 같게 유지한다.
3. **체감 표현의 단일 원본을 둔다.** Main, Today, Detail, 위젯이 같은 체감 단계와 무시구간을 사용한다.
4. **안전 임계값과 일상 표현을 분리한다.** 폭염·한파 위험 기준과 `선선/조금 덥다` 같은 쾌적감 표현은 목적이 다르므로 별도 정책으로 관리한다.
5. **반복 완화는 무작위보다 안정적 변형을 사용한다.** 같은 의미의 후보를 날짜·장면 기준으로 고르되, 한 화면 안에서는 문장이 흔들리지 않게 한다.
6. **모든 시간 민감 문장에 만료 계약을 붙인다.** 위젯과 알림 후속 화면도 만료 여부를 같은 방식으로 판단한다.
7. **용어를 고정한다.** 기획·코드·디자인에서 `브리핑`, `체감 표현`, `행동 안내`, `준비물 추천`, `근거 문장`, `알림 문구`를 구분한다.

## 13. 한 줄 결론

현재는 하나의 통합 브리핑 시스템이 아니라 **서버 종합 브리핑, 앱 체감 문장, 추천 문장, Detail 근거 문장, 알림 조합기, 위젯 축약기**가 함께 존재하는 구조다. 그래서 25.1℃를 `조금 덥게`라고 하는 문제와 같은 문장이 반복되는 문제는 한 파일의 문구만 고쳐서는 전체 채널에 일관되게 반영되지 않는다.
