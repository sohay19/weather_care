# 시정 직전 회차 정책과 여행지 조회 실패 확인

## 시정 변경

- 사용자 요청에 따라 한국 시각 매 정각 기준으로 직전 정시의 ASOS VS 자료를 수집한다.
- 13:00~13:59 → 12:00, 14:00~14:59 → 13:00, 00:00~00:59 → 전날 23:00.
- 기존 90분을 뺀 뒤 정시로 내리는 방식은 시정 수집에서 제거했다. 어제 비교에 남아 있는 기존 ASOS 함수는 이번 변경 범위에서 제외한다.
- 정상 수집한 회차는 재호출하지 않는다. 실패하면 이전 성공 캐시를 보존하며 관측 시각이 실제 현재 시각보다 3시간을 초과하면 제공하지 않는다.
- 전국 캐시와 이전 지역 캐시 모두 이번 정시 자료가 직전 회차 정책을 넘으면 응답에서 제외한다.
- 전국 VS 정상 수집은 하루 24회로 동일하다. 1시간 지연만으로 제공처 장애가 사라진다고 보장하지 않으며, 재시도는 기존 APIHub 예산 보호를 따른다.
- 수정은 로컬 코드에 반영했다. 운영 서버 배포는 아직 하지 않았다.

## 여행지 실패 원인

- 사용자 제공 좌표 `(37.697249, 127.660949)`를 앱과 같은 기상청 DFS 변환으로 계산하면 `(71,130)`이다.
- 운영 서버 journal을 한국 시각 2026-10-06 00:00~2026-10-08 00:00 범위로 읽기 전용 조회했다.
- 10월 6일 08:58:10~11:12:35 해당 격자의 요청 75건을 확인했다: 메인 9, 오늘 33, 주간 33.
- 75건 모두 HTTP 503, `WEATHER_CACHE_NOT_READY`. 서버 처리 시간은 0~102ms였다.
- 10월 7일 같은 격자에 기록된 요청은 없으므로 그날의 개별 요청 결과는 직접 확인할 수 없다.
- 현재 운영 서버에는 전국 원본 저장 테이블과 `nationwideWeatherCache.ts`가 없다. 기본 예보 캐시는 대표 1,633격자 방식이다.
- `(71,130)`은 운영 대표 격자 목록에 없고, 점검 시 해당 격자의 지역 캐시·활성 지역 행도 없었다.
- 운영 메인 API는 지역 캐시가 없으면 전국 실황을 합성하기 전에 503을 반환한다. 따라서 확인한 실패는 **우리 서버 수집 범위와 캐시 선차단 문제**다. 75건의 직접 실패 원인을 기상청 타임아웃으로 분류할 근거는 없다.
- 로컬 전국 원본 구현에서 해당 좌표와 격자로 메인·오늘·주간 API를 호출하는 회귀 검증을 추가했다. 외부 API 호출과 지역 대표 캐시 없이 세 응답 모두 200, 메인·오늘의 현재 기온 반환을 확인했다. 합성 원본을 이용한 코드 검증이며 운영 개선 완료를 의미하지 않는다.
- 운영 문제를 해결하려면 기존 전국 원본 수집·읽기 구현과 스키마를 배포하고 초기 수집을 완료한 뒤 실제 GPS 응답을 확인해야 한다.
