# 실황 재시도와 대기질 적설 처리 개선 및 운영 배포

2026년 10월 9일 17:11 KST에 첫 배포 후 기존 캐시의 상태 해석까지 보완해 `20261009-collection-recovery-v2`를 배포했으며, 17:27에 서비스 정상 전환을 확인했다. 성공한 실황 파일을 보존하고 누락 파일만 재시도하며, 대기질 부분 수집과 적설의 독립 가용성을 적용했다. 운영 API 응답과 전국 육지 4,728격자의 핵심 실황을 검증했다. 제공처 원본 결측과 실제 429 장애는 별도로 남는다.

## 실황과 예보 수집

기존에는 기온을 정상으로 받아도 습도나 풍속 하나가 실패하면 전체 회차를 저장하지 않았다. 이제 같은 회차의 성공 파일을 즉시 임시 캐시에 저장한다. 다음 시도는 임시 캐시와 게시된 원본을 합쳐 실패 파일만 요청한다. 병렬 응답의 저장은 직렬로 처리해 먼저 받은 값이 사라지지 않게 했다.

사용자 조회용 전국 스냅샷은 동일 회차의 기온·습도·풍속이 갖춰지고 같은 격자에 정상 핵심값이 존재할 때 게시한다. 핵심값만 보충하는 요청도 이미 받은 풍향·강수형태·강수량을 보존한다. 원본의 공간 결측은 인근 실황 보충 규칙으로 처리하며 예보를 관측으로 바꾸지 않는다.

최신 요청 시각은 이전 정책대로 10분 전 회차다. 11:50~11:59에는 11:40 회차를 요청한다. 시간초과는 30초로 유지한다. 실패는 2→4→8분부터 최대 6시간 간격으로 늦추고, 예산 차단 시에는 예산 회복 예정 시각까지 대기한다.

정규 10분 수집 뒤에 보관 시작 이후 72시간 이내의 누락 회차를 찾아 최대 2회차씩 보충한다. 어제 비교에 가까운 시각을 우선하며 핵심 3개 파일만 요청한다. 이 작업은 과거 보충 예산을 사용한다. 임시 파일과 재시도 상태는 72시간이 지나면 삭제한다. 기존 수집이 한 번도 시작되지 않은 더 이전 시각까지 전부 요청하지 않는다.

전국 예보는 최신 발표를 먼저 처리하고 성공 파일은 기존처럼 별도 보존한다. 예산 차단 시 파일 임대의 재개 시각도 조정한다. 05시·17시 발표 연장 구간의 풍향 8파일 제외 정책은 유지한다.

로그는 원래 제공처, 재시도 용도, 회차 또는 발표·유효시각, 변수, 헤더·본문 단계, 응답 시간, 수신·예약 바이트, 연결 오류 코드, 예산 회복 시각을 남긴다. 예보의 `발표:유효시각` 형식도 안전한 로그 식별자로 허용했다. DNS·TCP·TLS 개별 단계나 공급자 내부 처리 시간까지 수집하는 기능은 이번 변경에 포함되지 않았다.

## 재시도 예산

하루 내부 안전 상한 18,000호출·4.5GB와 최초 24시간 100MB·이후 400MB 재시도 총량을 유지했다. 용도별 예약과 전체 예약을 한 SQL에서 검사하므로 동시 요청도 상한을 공유한다.

| 용도 | 최초 24시간 | 이후 |
|---|---:|---:|
| 최신 핵심 실황 기온·습도·풍속 | 50MB | 160MB |
| 전국 단기예보 | 30MB | 120MB |
| 선택 실황과 다른 운영 항목 | 15MB | 60MB |
| 과거 보충과 진단 | 5MB | 60MB |
| 재시도 총량 | 100MB | 400MB |

기존 `APIHUB_RETRY` 장부와 새 용도별 장부를 모두 합산한다. 이름 변경으로 기존 사용량을 숨기거나 예산을 초기화하지 않았다. 이전 실패의 예약량도 그대로 남는다. 과거 보충 큐의 호출은 최초 시도여도 낮은 우선순위 예산으로 예약한다.

기존 필수 수집량 추정에 재시도 총량을 전부 사용하는 경우의 계산은 다음과 같다. 제공처 실제 데이터 크기와 실패 횟수에 따라 달라지며, 운영 코드의 4.5GB 검사도 함께 적용된다.

| 계절 | 기존 필수 수집 예상 | 재시도 최대 예약 | 합계 | 4.5GB 대비 여유 |
|---|---:|---:|---:|---:|
| 비겨울 | 2.715GB | 0.400GB | 3.115GB | 1.385GB |
| 겨울 | 3.771GB | 0.400GB | 4.171GB | 0.329GB |

정상 격자 파일 약 341,297B만으로 재시도 400MB를 소진한다고 가정하면 약 1,172호출이다. 필수 호출 추정 비겨울 4,208·겨울 4,333에 더하면 각각 약 5,380·5,505호출이다. 작은 오류 응답이나 빈 응답이 섞이면 이 호출 추정은 성립하지 않으므로 18,000호출 제한도 별도로 유지한다. 공공데이터포털 지점 예보는 별도 9,000호출 장부로 제한한다.

## 대기질 수집

17개 시도를 각각 저장한다. 한 시도가 실패해도 성공한 시도의 값을 전국 캐시에 반영한다. 성공한 시도는 1시간 동안 재사용하고 실패한 시도만 재시도한다. 실패한 측정소의 이전 정상값은 실제 관측시각이 3시간 이내일 때만 제공한다. 합쳐진 전국 캐시의 갱신 시각으로 오래된 관측을 새것처럼 취급하지 않는다.

동시 요청은 최대 3개다. 429 또는 권한 오류를 확인하면 대기열의 추가 요청을 중단하고, 이미 보낸 요청의 결과는 처리한다. 429는 `Retry-After`가 있으면 이를 우선하며, 없으면 15→30→60분과 지터를 사용한다. 동시에 실패한 요청도 실패 횟수에 반영하므로 첫 3개가 모두 429이면 전역 대기가 약 60분으로 늘어난다. 시간초과 등은 해당 시도에 5→10→20분부터 최대 60분 대기를 적용한다.

관측소 목록은 마지막 정상본을 별도 저장한다. 목록 갱신이 일시 실패해도 이전 좌표 목록이 있으면 측정값 수집을 계속한다. 목록 갱신 시각은 로그에 남기며, 새 목록에 없는 관측소는 위치 선택에 사용하지 않는다. 수집 임대는 SQLite에서 공유해 스케줄러와 준비 작업이 중복 수집하지 않게 했다.

재시도 상태는 프로세스 재시작 뒤에도 유지한다. 401·403 등 권한 실패는 자동 재시도를 중단하고 설정 복구를 기다린다. 오류 로그에 시도, 측정값·목록 구분, HTTP/결과 코드, 실패 유형, `Retry-After`, 다음 시도를 남긴다. 정상 수집 요약은 실제 발신 수와 성공·건너뛴 시도 수를 포함한다.

## 적설과 다른 일 관측의 독립 가용성

기존 AWS 일통계 API를 사용하며, 최심 신적설 `sd_day_max`를 현재 지면의 전체 적설과 혼동하지 않는다. 텍스트는 EUC-KR로 읽고 JSON 오류·UTF-8 응답은 해당 형식으로 읽는다.

각 일 관측 항목에 다음 상태를 추가했다. 기존 캐시에 응답 성공 여부가 없고 수치도 없는 경우는 UNAVAILABLE로 보수적으로 해석한다.

| 상태 | 의미 |
|---|---|
| `AVAILABLE` | 정상 수치가 있음. 명시적 0도 포함 |
| `NO_RECORD` | 정상 응답에 해당 항목의 관측 기록이 없음 |
| `UNAVAILABLE` | 요청 실패 등으로 자료를 확보하지 못함 |

`weatherDataComplete`는 최저기온·최고기온·강수량의 가용성으로 판단한다. 적설이 없는 이유로 기온과 강수까지 미완비로 만들지 않는다. 적설 기록이 없으면 `snowfallDataAvailable=false`이고 공개 API에 적설량 숫자를 넣지 않는다. 무강수와 적설 미확보만으로 하늘 상태를 ‘맑음’이라고 만들지 않는다.

눈이 기록된 먼 관측소를 무제한으로 찾아 다른 지역의 적설로 제공하는 처리는 제거했다. 현재 선택한 기온 관측소의 같은 날짜 적설값만 사용하며, 그 관측소에 눈 기록이 없으면 기록 없음으로 표시한다.

일 관측 캐시는 지표별 상태와 정상값을 보존한다. 재수집에서는 성공한 지표를 재사용하고 실패한 지표만 요청한다. 정상 빈 적설 응답도 처리 완료 상태로 남긴다. `completedDates`는 핵심 일 관측이 갖춰진 날짜, `settledDates`는 적설을 포함한 요청 상태까지 처리한 날짜다.

주간 API 예시는 다음과 같다.

```json
{
  "weatherDataComplete": true,
  "observationAvailability": {
    "minTemperature": "AVAILABLE",
    "maxTemperature": "AVAILABLE",
    "precipitationAmount": "AVAILABLE",
    "snowfallAmount": "NO_RECORD"
  }
}
```

적설 전용 `kma_snow_day.php`는 현재 활용 권한이 없어 403인 상태다. 이 경로는 배포하지 않았다. 적용하려면 APIHub의 지상관측 → 적설관측 → 적설관측자료 조회 활용신청 승인이 필요하다. 기존 일통계 API와 가용성 개선은 적용됐다.

## 검증과 현재 운영 상태

- 타입 검사 통과. Node 94개와 기존 414개, 총 508개 테스트 통과.
- 정상 실황 5파일 보존 후 실패한 습도 1파일만 재요청하고 같은 회차를 게시하는 테스트 통과. 핵심값 보충에서도 선택 항목을 보존한다.
- 용도별 예산 보호, 기존 장부 합산, 동시 예약 상한, 과거 핵심 3항목 보충, 대기질 부분 성공·429 대기·403 중단·좌표 목록 재사용·3시간 제한, 적설 빈 응답·실패·0·먼 지점 확대 방지 검증 통과.
- 운영 소스 13파일 해시가 배포 묶음과 일치한다. API·스케줄러·터널 모두 active이며 내부·외부 health 200.
- 17:28 전국 육지 4,728/4,728격자의 핵심 실황·풍향·강수형태·강수량 제공 정상. 이 중 원본 공간 결측 302격자는 인근 실황을 사용한다. 위치명 연결 3,559/3,559, 자외선·중기 연결도 정상이다. 302개의 실제 GPS Today 요청도 모두 200이며 실황 6항목·지점 예보·GPS 지역명 정상. 외부 메인·오늘·주간·어제 비교 16요청 모두 200이며 어제 비교 표본 4곳 모두 비교 가능이다.
- 4,728격자 모두 과거 7일 기온·강수 완비 판정 정상. 적설은 모든 날짜 기록 없음으로 남는다. 여행지 주간 API의 과거 5일에도 항목별 가용성이 반영됐다.

17:14에 미확보였던 선택 회차의 강수량 RN1은 17:20 수집한 17:10 회차에서 복구됐다. 최종 전국 검사에서 강수형태·풍향·강수량 누락은 각각 0격자다. 현재 계획의 예보 미저장 파일도 0개다. 앞서 실패한 14시 발표 3파일은 이전 발표 원본에 미저장으로 남지만, 최신 17시 발표가 해당 예보 구간을 제공하므로 현재 계획은 옛 발표 파일을 다시 요청하지 않는다.

기존에 확인한 실황 10회차(10:50·11:10·12:00·12:10·12:20·12:50·13:20·13:40·14:00·14:30)는 17:28에 모두 핵심 3항목 원본을 복구했다. 운영 예산·임대·부분 파일 저장 경로를 그대로 사용한 일회성 보충이다. 30호출·10,238,910B를 `APIHUB_RETRY_HISTORY`로 회계 처리했다. 이 회차들의 풍향·강수형태·강수량까지 과거 원본을 모두 채운 것은 아니다.

최초 24시간은 17:27:01에 종료됐으며 이후 기존 정책의 400MB 한도를 적용했다. 장부를 초기화하거나 일일 한도를 늘리지 않았다. 17:28 APIHub 합계는 5,320호출·2,999,498,437B, 전체 재시도 합계는 750호출·110,468,311B로 각 내부 상한 이내다. 실수신량과 실패 예약량을 포함한 시점 집계이며 하루 최종 사용량은 아니다. 이력·선택 항목 재시도 상태는 61건이 남아 순차 처리한다. 저장 시작 이후의 공백 등도 포함하므로 모두 이번 신규 실패라고 해석하지 않는다.

대기질 실측은 운영에서 서울·부산·대구 3요청 모두 429를 반환했다. 이후 14시도는 발신하지 않았고 전역 다음 재시도는 18:11:48 KST다. 운영계정 승인 여부나 일일·순간 제한 중 어느 조건인지는 HTTP 429만으로 확정할 수 없다. 대기질 예보와 실측은 별개다.

앱 업데이트 없이 기존 API 필드는 유지하고 항목별 상태를 추가했다. 앱에서 새 상태 문구를 직접 표시하려면 별도 앱 반영이 필요하다. 2026 공식 경계 원본은 다운로드 대기 상태이며 이번 배포로 경계가 2026 자료로 바뀐 것은 아니다.
